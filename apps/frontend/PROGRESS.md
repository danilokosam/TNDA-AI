# TNDA-AI Frontend — Progress

## 1. Architecture & Planning (2026-08-06)

Before any code was written, the backend's actual API surface was re-verified directly from its route/schema/service source (not from memory), and current library versions were checked against the npm registry rather than assumed. This surfaced six real gaps between the spec and what the backend actually provides — no list/history endpoint, no refresh endpoint, no logout endpoint, original files never persisted, no `document_type`/confidence columns on `document_jobs`, and (the one gap that's actually an opportunity) `document_jobs` RLS already scopes `select` to the caller's own org, usable directly from the frontend.

A second-opinion review (independent agent pass reading the real backend source) then stress-tested the proposed auth architecture specifically and found several concrete implementation problems worth correcting before writing code: the backend's IP-keyed rate limiter becomes a bucket shared across *all* users once every call is proxied through one Next.js server (relevant because job-status polling is the app's highest-volume traffic pattern by design); Server Components can't write cookies, so refresh has to be centralized in `proxy.ts`, not scattered per-caller; naive multipart proxying via `request.formData()` would fully buffer uploads in memory; and logout needs to actually revoke the refresh token server-side, not just clear cookies, to be consistent with the reason httpOnly cookies were chosen in the first place.

A subsequent self-review pass (done deliberately before implementation, hunting for unnecessary complexity rather than confirming the first draft) cut a generic catch-all `/api/backend/[...path]` proxy in favor of small purpose-built Route Handlers (the "generic" proxy was never actually generic — upload needs stream-passthrough handling and billing needs URL injection, so it would've special-cased its own traffic anyway), dropped a since-unnecessary `/api/auth/refresh` route, found that Dashboard needs an aggregate stats query that's genuinely separate from the paginated History endpoint (an aggregate can't be correctly derived from one page of a paginated list), and switched History pagination from offset to keyset/cursor-based (offset pagination drifts under concurrent inserts — a real case here, since a user can upload a new batch while paging through their own history).

**Decisions made, with reasoning kept here rather than scattered across commit messages:**

- **Document preview (Results page) is session-only for v1.** The backend intentionally never persists uploaded files, so a *persistent* preview isn't possible without new infrastructure. The just-uploaded file is cached client-side and shown via a blob URL through the immediate upload→processing→results flow; opening an older job from History shows an explicit "preview unavailable" state instead of a broken image. Built behind a `DocumentPreviewSource` abstraction (`session-blob` / `remote-url` / `unavailable`) specifically so a persistent backend-provided URL can replace the session-only source later without touching `DocumentPreviewPanel` or any other UI — this was an explicit requirement, not an implementation nicety.
- **Auth session lifecycle:** the backend's `/auth/signup`/`/auth/login` still do all real orchestration (organization + profile creation, with rollback on partial failure) — calling `@supabase/ssr`'s own signup/login directly would bypass that and leave orphaned `auth.users` rows with no `profiles` row. Instead, immediately after the backend responds, `@supabase/ssr`'s `setSession()` hydrates a server-side Supabase client, which then owns the cookie/refresh lifecycle from that point on (`getUser()`-based refresh centralized in `proxy.ts`, on every request, not per-caller). Logout calls `supabase.auth.signOut()` server-side to actually revoke the refresh token, then clears cookies.
- **Type safety across the API boundary uses Elysia Eden, not hand-written DTOs or an OpenAPI codegen step.** `backend/src/index.ts` already ends with `export type App = typeof app` — Elysia's own convention for exactly this. `types/api.ts` re-exports types derived from a type-only `import type { App } from ".../backend/src/index"`, erased entirely at compile time (nothing backend-side is bundled or executed differently). A backend field rename becomes an immediate frontend type error instead of a silent runtime mismatch.
- **Rate limiting is a real, backend-side ceiling this frontend can manage but not fix** (100 req/60s, keyed by IP — shared across all users once proxied, since `rate-limit.middleware.ts` sees the Next.js server's IP, not each end user's). Job-status polling uses a backoff schedule (~2s/3s/5s/8s, capped ~10s, stopping at any terminal status) rather than a fixed fast interval — necessary, not just gentler UX. The real fix (keying the backend's limiter on user ID instead of IP) is out of scope since it requires a backend change.
- **Call paths are fixed and enforced, not just documented.** Server Components import `services/*.service.ts` directly; Client Components only reach it indirectly through this app's own `/api/*` Route Handlers. Every file under `services/` starts with `import "server-only"` so an accidental Client Component import fails the build instead of silently risking a path to backend tokens in a client bundle.
- **CSRF is covered by `SameSite=Lax` + all-mutations-are-POST, deliberately, not a token.** `SameSite=Lax` was already required for a different reason (Stripe Checkout/Portal redirect back to the app via top-level GET — `Strict` would silently log the user out right after they pay), and combined with every mutating route here being POST, that already closes the practical CSRF gap without adding a separate token mechanism.
- **Optimistic updates were checked against every real mutation in the app and don't fit v1 anywhere** (upload-queue entries are already transient client-only state; "mark as reviewed" is explicitly local-only since there's no backend endpoint to persist it to; a plan change redirects to Stripe and can't be optimistically shown before payment succeeds; History has no mutations). Recorded so this reads as a considered decision, not a skipped requirement.

## 3. Stage 1: App shell + auth (2026-08-06)

### Architecture change: the planned Eden Treaty type-sourcing doesn't work — discovered by testing, not assumed

The plan's "Type safety across the boundary" section called for a type-only `import type { App } from "backend/src/index"` (Elysia's Eden Treaty pattern) so `types/api.ts` would need zero hand-written DTOs. Tested directly before writing any real code, and it fails: `backend/src/index.ts` transitively imports every route module via the backend's own `@/*` alias (`@/config/env`, `@/modules/auth/auth.routes`, etc.). TypeScript resolves those imports using the **importing project's** `tsconfig.json` `paths`, not the imported file's own — so once pulled into a frontend file, `@/config/env` resolves against `frontend/@/*` (`./*`) instead of `backend/@/*` (`src/*`), and fails outright. This isn't fixable without either editing the backend's `tsconfig.json` (not allowed) or a formal TS project-references/monorepo restructuring (out of scope, and would also touch the backend).

The fallback considered next — `openapi-typescript` codegen against the backend's own mounted `@elysiajs/swagger` (`/docs/json`) — was also tested against the live endpoint and doesn't work either: `@elysiajs/swagger` is serializing raw Zod-internal `_def` trees (`{"_def":{"unknownKeys":"strip","typeName":"ZodObject",...}}`) instead of real JSON Schema for every request body, and every response schema comes back as a bare `{}` — confirmed by fetching and inspecting `http://localhost:3000/docs/json` directly, not just the request bodies but response bodies too (`GET /documents/jobs/{id}` → `"responses":{"200":{}}`). `openapi-typescript` would generate either build errors or meaningless types from this.

**Landed on a hybrid that's arguably more robust than either original option:**
- Files with zero internal imports — `backend/src/config/database.types.ts` (the `Database` type) and `backend/src/utils/errors.ts` (`AppErrorCode`) — **do** resolve cleanly as type-only cross-project imports (verified directly, including a deliberate-break test to confirm the check isn't a false pass — see below). These are type-only imported for real, with zero hand-duplication.
- Everything else (request bodies, and response shapes that are service-layer inventions rather than raw DB rows — `AuthResponse`, `UsageSummary`, `SubscriptionResponse`, `JobDto`, `BatchResult`, etc.) is hand-written as Zod schemas in `types/api.ts`, verified field-by-field against the real route/service/schema source (re-read directly, not from memory — `auth.schema.ts`, `auth.service.ts`, `organization.service.ts`/`.repository.ts`, `billing.schema.ts`/`.service.ts`, `documents.schema.ts`/`.service.ts`, `database.types.ts`).
- Where a hand-written schema mirrors a type-importable DB row (`organizations`, `plans`, `subscriptions`), an `AssertExact<A, B>` compile-time check (`export const _checkX: AssertExact<z.infer<typeof xSchema>, XRow> = true`) makes a future drift a build error, not just a hope. **This actually didn't work on the first attempt** — the first version used `declare const _checkX: AssertExact<...>` (an ambient declaration), which type-checks successfully regardless of what `AssertExact` resolves to, since declaring a variable of type `never` isn't itself an error. Caught this by deliberately breaking a field (`price_monthly: z.number()` → `z.string()`) and confirming `tsc` still passed — it did, silently, which meant the "safety net" was inert. Fixed by switching to a real assignment (`export const _checkX: AssertExact<...> = true`), which forces TypeScript to actually validate `true` against the computed type; re-ran the same deliberate-break test and confirmed it now fails the build as intended, then restored the correct version.
- `lib/api/backend-client.ts` (server-only) and `lib/api/http.ts` (client-safe, calls this app's own `/api/*` routes) both parse every response through the matching Zod schema via a shared `parseApiResponse` helper — so a real backend/schema drift is caught at runtime too, at the exact call site, not just hoped not to happen. This is arguably a stronger guarantee than Eden would have given (compile-time only, no runtime check).
- `@elysiajs/eden` was removed from `package.json` (installed in Stage 0 for the approach that didn't pan out).

### Auth implementation

- **Session lifecycle**: `/api/auth/{signup,login}` call `services/auth.service.ts` (thin wrapper over `backendFetch`, no validation of its own — validation happens once, at the Route Handler, via `parseJsonBody` against the matching Zod schema, mirroring the backend's own routes-validate/services-trust layering), then call `@supabase/ssr`'s `setSession()` to hydrate cookies from the returned tokens. `/api/auth/logout` calls `signOut()` (real server-side revocation, not just cookie clearing) — idempotent by design.
- **`proxy.ts`**: one `getUser()` call per request (transparent refresh + re-cookie), then three outcomes depending on path — `/` redirects based on auth state; `/api/*` paths 401 (JSON, not a redirect — these are `fetch()` callers) if unauthenticated, except `/api/auth/*` itself; every other page redirects to `/login` if unauthenticated, or `/login`↔`/signup` redirect to `/dashboard` if already authenticated (the reciprocal redirect). Matcher covers everything except `_next/static`, `_next/image`, and `favicon.ico` — deliberately includes `/api/*`, or polling requests later would bypass the refresh guarantee entirely.
- **Call-path rule enforced, not just documented**: every `services/*.service.ts` file starts with `import "server-only"`. Server Components (`(dashboard)/layout.tsx`) call services directly; the one Client-Component-reachable path so far (`features/auth/hooks.ts`) goes through `lib/api/http.ts` → this app's own `/api/*` routes → the same service functions.
- **Dashboard shell**: `(dashboard)/layout.tsx` (Server Component) fetches the current user once and passes it down as a prop to `AppSidebar`/`UserMenu` — deliberately **not** a `useCurrentUser()` query hook + `HydrationBoundary` yet, since nothing client-side independently needs to refetch this data in Stage 1. That pattern is worth introducing once something actually does (e.g. Stage 2's usage numbers, refetched after an upload) — building it now for a duplicate-fetch problem that doesn't exist yet would be exactly the kind of premature abstraction the spec warns against. Sidebar built on shadcn's own `sidebar.tsx` (collapsible, icon mode, mobile sheet) rather than hand-rolled. shadcn's `form.tsx` registry item turned out to be an empty stub in the installed CLI/registry version (`shadcn view form` returns a bare `{"name":"form"}` with no file content) — login/signup forms use React Hook Form's `register()`/`formState.errors` directly against the `Input`/`Label` primitives instead of the `FormField` wrapper; a contained, easy swap later if the registry gets real content.
- Fixed two real lint findings before considering this done: (1) `features/auth/hooks.ts`'s logout originally used a hard `window.location.assign()` reload specifically to guarantee TanStack Query's cache doesn't leak a just-logged-out user's data into a next login in the same tab — Next's linter flagged this; switched to `queryClient.clear()` + `router.push()`, which achieves the same guarantee through the correct tool instead of a hard reload. (2) shadcn's own generated `hooks/use-mobile.ts` fails `react-hooks/set-state-in-effect` — the flagged line is a deliberate SSR-hydration-safety pattern (server and the client's first render must both start from the same `undefined` value, corrected only after mount), not an oversight, so switching to a `useState` lazy initializer (the "fix" the rule implies) would have reintroduced a real hydration-mismatch risk; kept the original pattern with a scoped, documented `eslint-disable-next-line`.

## 4. Stage 2: Dashboard (2026-08-07)

Picked up the plumbing the project-level `PROGRESS.md`'s own "Next Session" section had already scoped: extended `types/api.ts` (`documentType`/`averageConfidence` on the job schema; new `organizationStatsSchema`, `documentsListResponseSchema`, `ListDocumentsParams`), added `services/documents.service.ts` (`listDocuments`) and `services/billing.service.ts` (`getSubscription` only — full `plans`/`checkout`/`portal` deferred to Stage 6), extended `services/organization.service.ts` with `getJobStats`, and added three thin BFF routes (`app/api/organization/stats`, `app/api/documents` GET-only, `app/api/billing/subscription`) matching the existing `app/api/organization/route.ts` pattern exactly.

Then the Dashboard page itself (`app/(dashboard)/dashboard/page.tsx`) — an async Server Component, not a client-side query, same precedent as `(dashboard)/layout.tsx`'s own user fetch: nothing here needs client-side refetching yet, so it calls `services/*` directly rather than its own BFF routes (which exist anyway, for Stage 5/6 and any future client interaction on this page). Fetches `getOrganizationOverview`, `getJobStats`, `getSubscription` in parallel via `Promise.all`, then renders either the empty state or:
- Three `StatTile`s (documents processed, success rate, avg. processing time) — `null` stats render as `"—"` with a "No completed jobs yet" subtext, never a fabricated `0` (mirrors the backend's own `null`-not-`0` convention through to the UI).
- `DocumentsTrendChart` — a hand-rolled inline SVG line+soft-area chart (not a charting library; see below), with a pointer- and keyboard-operable crosshair/tooltip and a table-view toggle.
- `CurrentPlanCard` — plan name/price, a subscription-status `Badge`, and two `UsageMeter`s (documents/pages used vs. plan limits).

**Color**: this theme (`shadcn init`'s neutral base, Stage 0 above) had never used a real hue — `--chart-1..5` were unpopulated grays. Used the `dataviz` skill's validated default categorical slot 1 (blue) for the single-series chart, but didn't take the skill's example surfaces on faith: wrote a small throwaway OKLCH→sRGB conversion script to get this theme's *actual* computed card-surface hex (`#ffffff` light, `#171717` dark, from its real `oklch()` tokens), then ran `scripts/validate_palette.js` against those real surfaces. `--chart-1` updated in `app/globals.css` for both modes; `chart-2..5` untouched.

**Chart implementation**: hand-rolled SVG, not shadcn's `chart.tsx`/Recharts. Worth flagging plainly against this file's own Stage 0 section above, which said the plan anticipated shadcn's own chart primitives specifically for a shared token system: checked the original plan file directly and it never mentions charts at all, so that was this project's own Stage-0-session inference, not a real requirement from planning. The token-system goal is still met (the chart reads `var(--color-chart-1)`, the same variable the rest of the theme uses) — but the rendering approach is a genuinely different call, made without having re-read that note first. No dependency was added; a single-series line chart with the `dataviz` skill's specific interaction requirements (arrow-key-operable crosshair, a table-view twin) didn't need one. Revisit if a later stage's charting needs (multi-series, more chart types) outgrow what's reasonable to hand-roll.

**Two real fixes from a deliberate second review pass**, done before committing rather than treating the first implementation pass as final: `UsageMeter` had used `role="progressbar"` (semantically wrong — a meter, not an in-progress operation) with an unclamped `aria-valuenow` (could exceed `aria-valuemax` if usage ever exceeds the plan limit); switched to `role="meter"` with a clamped value and an explicit `aria-valuetext`. The Dashboard's empty-state gate checked only `stats.totalJobs` (terminal jobs) — verified directly against `0010_document_analytics.sql`'s actual SQL that `dailyCounts` uses the identical status filter, so that part was already consistent — but an org with a job still `pending`/`processing` would incorrectly see "no documents yet"; added the already-fetched `usage.documentsUsed` (which does count pending/processing) to the gate.
