# TNDA-AI Frontend — Progress

## 1. Architecture & Planning (2026-08-06)

Before any code was written, the backend's actual API surface was re-verified directly from its route/schema/service source (not from memory), and current library versions were checked against the npm registry rather than assumed. This surfaced six real gaps between the spec and what the backend actually provides — no list/history endpoint, no refresh endpoint, no logout endpoint, original files never persisted, no `document_type`/confidence columns on `document_jobs`, and (the one gap that's actually an opportunity) `document_jobs` RLS already scopes `select` to the caller's own org, usable directly from the frontend.

A second-opinion review (independent agent pass reading the real backend source) then stress-tested the proposed auth architecture specifically and found several concrete implementation problems worth correcting before writing code: the backend's IP-keyed rate limiter becomes a bucket shared across *all* users once every call is proxied through one Next.js server (relevant because job-status polling is the app's highest-volume traffic pattern by design); Server Components can't write cookies, so refresh has to be centralized in `proxy.ts`, not scattered per-caller; naive multipart proxying via `request.formData()` would fully buffer uploads in memory; and logout needs to actually revoke the refresh token server-side, not just clear cookies, to be consistent with the reason httpOnly cookies were chosen in the first place.

A subsequent self-review pass (done deliberately before implementation, hunting for unnecessary complexity rather than confirming the first draft) cut a generic catch-all `/api/backend/[...path]` proxy in favor of small purpose-built Route Handlers (the "generic" proxy was never actually generic — upload needs stream-passthrough handling and billing needs URL injection, so it would've special-cased its own traffic anyway), dropped a since-unnecessary `/api/auth/refresh` route, found that Dashboard needs an aggregate stats query that's genuinely separate from the paginated History endpoint (an aggregate can't be correctly derived from one page of a paginated list), and switched History pagination from offset to keyset/cursor-based (offset pagination drifts under concurrent inserts — a real case here, since a user can upload a new batch while paging through their own history).

**Decisions made, with reasoning kept here rather than scattered across commit messages:**

- **Document preview (Results page) is session-only for v1.** The backend intentionally never persists uploaded files, so a *persistent* preview isn't possible without new infrastructure. The just-uploaded file is cached client-side and shown via a blob URL through the immediate upload→processing→results flow; opening an older job from History shows an explicit "preview unavailable" state instead of a broken image. Built behind a `DocumentPreviewSource` abstraction (`session-blob` / `remote-url` / `unavailable`) specifically so a persistent backend-provided URL can replace the session-only source later without touching `DocumentPreviewPanel` or any other UI — this was an explicit requirement, not an implementation nicety.
- **Auth session lifecycle:** the backend's `/auth/signup`/`/auth/login` still do all real orchestration (organization + profile creation, with rollback on partial failure) — calling `@supabase/ssr`'s own signup/login directly would bypass that and leave orphaned `auth.users` rows with no `profiles` row. Instead, immediately after the backend responds, `@supabase/ssr`'s `setSession()` hydrates a server-side Supabase client, which then owns the cookie/refresh lifecycle from that point on (`getUser()`-based refresh centralized in `proxy.ts`, on every request, not per-caller). Logout calls `supabase.auth.signOut()` server-side to actually revoke the refresh token, then clears cookies.
- **Type safety across the API boundary uses Elysia Eden, not hand-written DTOs or an OpenAPI codegen step.** `backend/src/index.ts` already ends with `export type App = typeof app` — Elysia's own convention for exactly this. `types/api.ts` re-exports types derived from a type-only `import type { App } from ".../backend/src/index"`, erased entirely at compile time (nothing backend-side is bundled or executed differently). A backend field rename becomes an immediate frontend type error instead of a silent runtime mismatch.
- **Rate limiting is a real, backend-side ceiling this frontend can manage but not fix** (100 req/60s, keyed by IP — shared across all users once proxied, since `rate-limit.middleware.ts` sees the Next.js server's IP, not each end user's). Job-status polling uses a backoff schedule (~2s/3s/5s/8s, capped ~10s, stopping at any terminal status) rather than a fixed fast interval — necessary, not just gentler UX. The real fix (keying the backend's limiter on user ID instead of IP) is out of scope since it requires a backend change.
- **Call paths are fixed and enforced, not just documented.** Server Components import `services/*.service.ts` directly; Client Components only reach it indirectly through this app's own `/api/*` Route Handlers. Every file under `services/` starts with `import "server-only"` so an accidental Client Component import fails the build instead of silently risking a path to backend tokens in a client bundle.
- **CSRF is covered by `SameSite=Lax` + all-mutations-are-POST, deliberately, not a token.** `SameSite=Lax` was already required for a different reason (Stripe Checkout/Portal redirect back to the app via top-level GET — `Strict` would silently log the user out right after they pay), and combined with every mutating route here being POST, that already closes the practical CSRF gap without adding a separate token mechanism.
- **Optimistic updates were checked against every real mutation in the app and don't fit v1 anywhere** (upload-queue entries are already transient client-only state; "mark as reviewed" is explicitly local-only since there's no backend endpoint to persist it to; a plan change redirects to Stripe and can't be optimistically shown before payment succeeds; History has no mutations). Recorded so this reads as a considered decision, not a skipped requirement.

## 3. Stage 1: App shell + auth (2026-08-06)

### Architecture change: the planned Eden Treaty type-sourcing doesn't work — discovered by testing, not assumed

The plan's "Type safety across the boundary" section called for a type-only `import type { App } from "backend/src/index"` (Elysia's Eden Treaty pattern) so `types/api.ts` would need zero hand-written DTOs. Tested directly before writing any real code, and it fails: `backend/src/index.ts` transitively imports every route module via the backend's own `@/*` alias (`@/config/env`, `@/modules/auth/auth.routes`, etc.). TypeScript resolves those imports using the **importing project's** `tsconfig.json` `paths`, not the imported file's own — so once pulled into a frontend file, `@/config/env` resolves against `frontend/@/*` (`./*`) instead of `backend/@/*` (`src/*`), and fails outright. This isn't fixable without either editing the backend's `tsconfig.json` (not allowed) or a formal TS project-references/monorepo restructuring (out of scope, and would also touch the backend).

The fallback considered next — `openapi-typescript` codegen against the backend's own mounted `@elysiajs/swagger` (`/docs/json`) — was also tested against the live endpoint and doesn't work either: `@elysiajs/swagger` is serializing raw Zod-internal `_def` trees (`{"_def":{"unknownKeys":"strip","typeName":"ZodObject",...}}`) instead of real JSON Schema for every request body, and every response schema comes back as a bare `{}` — confirmed by fetching and inspecting `http://localhost:3000/docs/json` directly, not just the request bodies but response bodies too (`GET /documents/jobs/{id}` → `"responses":{"200":{}}`). `openapi-typescript` would generate either build errors or meaningless types from this.

**Landed on a hybrid that's arguably more robust than either original option:**
- Files with zero internal imports — `backend/src/config/database.types.ts` (the `Database` type) and `backend/src/utils/errors.ts` (`AppErrorCode`) — **do** resolve cleanly as type-only cross-project imports (verified directly, including a deliberate-break test to confirm the check isn't a false pass — see below). These are type-only imported for real, with zero hand-duplication.
- Everything else (request bodies, and response shapes that are service-layer inventions rather than raw DB rows — `AuthResponse`, `UsageSummary`, `SubscriptionResponse`, `JobDto`, `BatchResult`, etc.) is hand-written as Zod schemas in `types/api.ts`, verified field-by-field against the real route/service/schema source (re-read directly, not from memory — `auth.schema.ts`, `auth.service.ts`, `organization.service.ts`/`.repository.ts`, `billing.schema.ts`/`.service.ts`, `documents.schema.ts`/`.service.ts`, `database.types.ts`).
- Where a hand-written schema mirrors a type-importable DB row (`organizations`, `plans`, `subscriptions`), an `AssertExact<A, B>` compile-time check (`export const _checkX: AssertExact<z.infer<typeof xSchema>, XRow> = true`) makes a future drift a build error, not just a hope. **This actually didn't work on the first attempt** — the first version used `declare const _checkX: AssertExact<...>` (an ambient declaration), which type-checks successfully regardless of what `AssertExact` resolves to, since declaring a variable of type `never` isn't itself an error. Caught this by deliberately breaking a field (`price_monthly: z.number()` → `z.string()`) and confirming `tsc` still passed — it did, silently, which meant the "safety net" was inert. Fixed by switching to a real assignment (`export const _checkX: AssertExact<...> = true`), which forces TypeScript to actually validate `true` against the computed type; re-ran the same deliberate-break test and confirmed it now fails the build as intended, then restored the correct version.
- `lib/api/backend-client.ts` (server-only) and `lib/api/http.ts` (client-safe, calls this app's own `/api/*` routes) both parse every response through the matching Zod schema via a shared `parseApiResponse` helper — so a real backend/schema drift is caught at runtime too, at the exact call site, not just hoped not to happen. This is arguably a stronger guarantee than Eden would have given (compile-time only, no runtime check).
- `@elysiajs/eden` was removed from `package.json` (installed in Stage 0 for the approach that didn't pan out).

### Auth implementation

- **Session lifecycle**: `/api/auth/{signup,login}` call `services/auth.service.ts` (thin wrapper over `backendFetch`, no validation of its own — validation happens once, at the Route Handler, via `parseJsonBody` against the matching Zod schema, mirroring the backend's own routes-validate/services-trust layering), then call `@supabase/ssr`'s `setSession()` to hydrate cookies from the returned tokens. `/api/auth/logout` calls `signOut()` (real server-side revocation, not just cookie clearing) — idempotent by design.
- **`proxy.ts`**: one `getUser()` call per request (transparent refresh + re-cookie), then three outcomes depending on path — `/` redirects based on auth state; `/api/*` paths 401 (JSON, not a redirect — these are `fetch()` callers) if unauthenticated, except `/api/auth/*` itself; every other page redirects to `/login` if unauthenticated, or `/login`↔`/signup` redirect to `/dashboard` if already authenticated (the reciprocal redirect). Matcher covers everything except `_next/static`, `_next/image`, and `favicon.ico` — deliberately includes `/api/*`, or polling requests later would bypass the refresh guarantee entirely.
- **Call-path rule enforced, not just documented**: every `services/*.service.ts` file starts with `import "server-only"`. Server Components (`(dashboard)/layout.tsx`) call services directly; the one Client-Component-reachable path so far (`features/auth/hooks.ts`) goes through `lib/api/http.ts` → this app's own `/api/*` routes → the same service functions.
- **Dashboard shell**: `(dashboard)/layout.tsx` (Server Component) fetches the current user once and passes it down as a prop to `AppSidebar`/`UserMenu` — deliberately **not** a `useCurrentUser()` query hook + `HydrationBoundary` yet, since nothing client-side independently needs to refetch this data in Stage 1. That pattern is worth introducing once something actually does (e.g. Stage 2's usage numbers, refetched after an upload) — building it now for a duplicate-fetch problem that doesn't exist yet would be exactly the kind of premature abstraction the spec warns against. Sidebar built on shadcn's own `sidebar.tsx` (collapsible, icon mode, mobile sheet) rather than hand-rolled. shadcn's `form.tsx` registry item turned out to be an empty stub in the installed CLI/registry version (`shadcn view form` returns a bare `{"name":"form"}` with no file content) — login/signup forms use React Hook Form's `register()`/`formState.errors` directly against the `Input`/`Label` primitives instead of the `FormField` wrapper; a contained, easy swap later if the registry gets real content.
- Fixed two real lint findings before considering this done: (1) `features/auth/hooks.ts`'s logout originally used a hard `window.location.assign()` reload specifically to guarantee TanStack Query's cache doesn't leak a just-logged-out user's data into a next login in the same tab — Next's linter flagged this; switched to `queryClient.clear()` + `router.push()`, which achieves the same guarantee through the correct tool instead of a hard reload. (2) shadcn's own generated `hooks/use-mobile.ts` fails `react-hooks/set-state-in-effect` — the flagged line is a deliberate SSR-hydration-safety pattern (server and the client's first render must both start from the same `undefined` value, corrected only after mount), not an oversight, so switching to a `useState` lazy initializer (the "fix" the rule implies) would have reintroduced a real hydration-mismatch risk; kept the original pattern with a scoped, documented `eslint-disable-next-line`.

## 5. Test infrastructure + Stage 3: Upload + Processing (2026-08-08)

### Test infrastructure

Asked to follow an incremental TDD workflow for Stage 3 (types/contracts → failing tests → minimal implementation → full-workspace verify, per feature category: services, hooks, state management, components) — the frontend had no test runner at all before this. Added `vitest`, `@testing-library/react`, `@testing-library/user-event`, `@testing-library/jest-dom`, `jsdom` (current registry versions checked, not assumed). `vitest.config.mts` (`.mts`, not `.ts` — avoids the same CommonJS/ESM config-loader warning the CI-typegen fix session hit and fixed by extension, not by touching `package.json`'s `"type"` field) mirrors the backend's own `vitest.config.ts`: `resolve.alias` for `@`, dummy `SUPABASE_URL`/`SUPABASE_ANON_KEY`/`BACKEND_URL` so `lib/env.ts`'s eager Zod validation doesn't need real credentials.

Two environment problems, both found and fixed before any real feature test was written:
- `server-only`'s default export throws unconditionally outside Next's own bundler (Next resolves it to a no-op via the `react-server` exports condition; Vitest doesn't set that condition). Aliased `server-only` → `test/mocks/server-only.ts` (a one-line no-op) rather than setting `react-server` globally in the Vitest config, which risked changing how React itself resolves for component tests.
- Testing-Library's auto-cleanup between tests self-registers via a global `afterEach` — this project imports `describe`/`it`/`expect` from `"vitest"` per file rather than turning on `test.globals` (matching the backend's style), so that detection silently never fires. Symptom: "multiple elements found" once a test file has more than one test that renders the same element. Found on `DocumentTypeSelect`'s first test (§ below); fixed once in `test/setup.ts` with an explicit `afterEach(() => cleanup())`.

`test/query-client-wrapper.tsx` (`createQueryWrapper()`) is the shared `renderHook`/`render` wrapper for anything touching React Query — a fresh `QueryClient` per call, `retry: false` on both queries and mutations so a mocked rejection doesn't sit through retry delays in tests.

### Services: `documents.service.ts#uploadDocument`/`getJobStatus`

`UploadDocumentParams` (new, in `types/api.ts`) pairs with the `uploadResponseSchema` that already existed from Stage 1. `uploadDocument` builds a `FormData` (`file`, and `documentType` only when provided — omitted rather than defaulted client-side, matching the backend's own default of `"invoice"`) and posts it through `backendFetch`; `getJobStatus` GETs `/api/v1/documents/jobs/:id` with the id URL-encoded. Tests mock `backendFetch` (one layer below what's under test, matching the backend's own repository-mocking style) and assert on the actual `FormData`/path/schema passed, not just that *a* call happened.

BFF routes: `POST` added to the existing `app/api/documents/route.ts` (reads `request.formData()`, 400 `VALIDATION_ERROR` locally — without ever calling `uploadDocument` — if `file` isn't a real `File` instance), and a new `app/api/documents/[jobId]/route.ts` (`GET`, async `params` per Next 16's route-handler convention — `{ params }: { params: Promise<{ jobId: string }> }`).

Writing the POST route's own test hit a real bug: `new Request(url, { method: "POST", body: formData })` followed by `request.formData()` inside the handler threw `AssertionError [ERR_ASSERTION]` deep in `node:internal/deps/undici/undici`'s `multipartFormDataParser`, specifically `webidl.is.File(value)` failing. Wrote a 5-line repro in plain Node (no Vitest) — identical code, worked fine — which pinned the cause on jsdom: jsdom ships its own `File`/`FormData` (they're DOM interfaces, not just Fetch API ones), and a jsdom-constructed `File` fails undici's internal brand check when it reaches the *real* `Request.formData()` parser Node provides. Fixed with `// @vitest-environment node` at the top of both new route test files — Route Handlers are server-side Node code regardless, so this is the more correct environment choice on its own merits, not just a workaround.

### Hooks: `useUploadDocument`/`useJobStatus`, and the backoff schedule

`features/upload/hooks.ts`. `useUploadDocument` is a plain `useMutation` wrapping `apiFetch` the same way `uploadDocument` wraps `backendFetch`. `useJobStatus(jobId: string | null)` is a `useQuery` with a dynamic `refetchInterval`; passing `null` (rather than requiring the caller to conditionally call the hook) disables it via `enabled: jobId !== null` — needed because a queue of upload items, some without a job yet, all need to call this hook unconditionally, one per item (see components, below).

The backoff schedule (2s/3s/5s/8s, capped at 10s, stopping once the job is `completed`/`failed`/`rejected_quota`) is `getNextPollInterval(status, fetchCount)` in `features/upload/poll-schedule.ts` — a pure function, deliberately pulled out of the `refetchInterval` callback itself. `fetchCount` is React Query's own `query.state.dataUpdateCount`. 12 plain unit tests (no timers, no rendering) cover every step, the cap, and all three terminal statuses.

Testing that this pure function is actually *wired in* correctly needed real fake timers, which surfaced a second real bug: `@testing-library/react`'s `waitFor` polls via a genuine `setInterval` and simply never resolves once `vi.useFakeTimers()` has frozen time — a test hung for the full default 5000ms timeout before failing with a timeout error, not a useful assertion failure, which is what made it non-obvious at first. Diagnosed by bisecting with `vi.advanceTimersByTimeAsync` steps directly instead of `waitFor`. Fixed with a small local `advanceUntil(predicate, maxMs, stepMs)` helper (advances in `stepMs` increments, flushing microtasks after each, until `predicate()` is true or `maxMs` is exhausted) — used only inside the fake-timer describe block. The test asserts *ranges* ("not within 500ms," "eventually, within a few seconds") rather than the exact scheduled millisecond, on purpose: matching React Query's precise internal tick count isn't part of this hook's actual contract.

### State management: `features/upload/queue.ts`

`UploadQueueItemStatus = "queued" | "uploading" | "upload-failed" | JobDto["status"] | "batch-submitted"` — reuses the backend's own status union directly (including keeping `rejected_quota` distinct from `failed`, matching how the rest of the app already treats them differently) rather than a parallel enum, plus the states that exist before a job does. `uploadQueueReducer` (7 action types: `add`/`remove`/`upload-started`/`upload-succeeded`/`upload-failed`/`job-status-updated`/`clear-finished`) and `createUploadQueueItem` are both pure — `createUploadQueueItem` takes its `id` as a parameter rather than calling `crypto.randomUUID()` internally, specifically so the reducer module has zero side effects and its tests need no randomness mocked. `useUploadQueue()` is a thin `useReducer` wrapper (`addFiles`/`removeItem`/`clearFinished`/raw `dispatch`) — it has no import of `useUploadDocument`/`useJobStatus` at all; composing state with the network-facing hooks happens one layer up, in the controller (next section). 19 tests across the pure reducer and the hook wrapper.

### The composition point: `features/upload/use-upload-controller.ts#useUploadController`

Combines `useUploadQueue()` + `useUploadDocument()` in a `useEffect`: finds the first `"queued"` item, dispatches `upload-started`, calls the mutation, dispatches `upload-succeeded`/`upload-failed` from its callbacks. An `isUploadingRef` (not state — a ref specifically so setting it doesn't itself trigger a re-render/re-run) guards against starting a second upload while one is in flight, which is what makes uploads process **sequentially**: after one dispatch changes `queue.items`, the effect re-runs, sees the ref still `true`, and bails, until `onSettled` flips it back after the mutation's callbacks have already dispatched the result.

The effect's dependency array is `[queue.items, queue.dispatch, uploadMutation.mutate]`, deliberately *not* `[queue, uploadMutation]` — both of those are fresh object references every render (`useUploadQueue` returns a new object literal each call; `useMutation`'s return value isn't referentially stable either), so depending on the whole objects would re-run the effect on every render regardless of whether the queue's contents actually changed, defeating the ref guard's purpose. This is a real `react-hooks/exhaustive-deps` warning, not a hypothetical one — confirmed by temporarily removing the `eslint-disable-next-line` and re-running lint before deciding to keep it, with a comment explaining why rather than a bare suppression.

Verified sequential (not concurrent) behavior with a real test, not just by reading the code: held the first mocked upload's promise open with an explicit `resolve` captured outside the mock, queued two files, confirmed the second stayed `"queued"` (not `"uploading"`) and `apiFetch` had only been called once — then resolved the first and confirmed the second started. A separate test confirms a rejected upload (`ApiError`) still lets the queue move on to the next file rather than getting stuck.

## 6. Bug fix: "Maximum update depth exceeded" on upload (2026-08-08)

The user ran both apps locally and hit a real crash uploading a document — confirmation that §5's "not verified" gap above was load-bearing, not academic. Told to diagnose root cause (not patch superficially) and specifically to determine whether it was effect dependencies, unstable callback identities, or unnecessary reducer dispatches.

**Root cause, precisely**: `PolledUploadQueueItem`'s effect (`useEffect(() => { if (data) onStatusUpdate(data); }, [data, onStatusUpdate])`) called `onStatusUpdate` on every poll. `onStatusUpdate` was a fresh closure every render at *two* levels — `UploadQueueList` rebuilt a per-item `(job) => onStatusUpdate(item.id, job)` wrapper, and `UploadWorkspace` rebuilt the dispatch call itself, both inline. Meanwhile `uploadQueueReducer`'s `job-status-updated` case unconditionally built a new array via `.map()` regardless of whether the incoming job data actually differed from what was already stored. Chain: poll resolves → effect fires → dispatch → new array (even if nothing changed) → re-render → new callback identity → effect fires again — with no reference-equality check anywhere to let `useReducer` bail out.

Confirmed this redundancy was real, not just plausible, via direct instrumentation: a throwaway `console.log` inside the reducer (removed before committing anything), counting invocations while a job sat at a constant "processing" status. Measured ~1.75x more `job-status-updated` dispatches than real polls justified with one item under plain conditions, exactly 2x under `React.StrictMode` (matching its documented double-invoke behavior, not additional evidence of a worse bug), and linear (not multiplicative) scaling with a second simultaneously-polling item.

**Honest limitation, stated rather than hidden**: attempted an integration-level reproduction of the literal "Maximum update depth exceeded" crash in `UploadWorkspace.test.tsx` — five variations (plain, `StrictMode`, freshly-varying poll responses to defeat React Query's default structural sharing, two simultaneous items) — none crossed React's actual update-depth threshold inside jsdom/Vitest, despite the underlying redundant-dispatch pattern being real and measured. Rather than force a fragile repro or quietly ship something that looked like proof but wasn't, the regression tests target the precise, deterministic property instead (below), and the integration test that remains is documented in its own comment as a sanity check, not primary proof.

**Fix**:
1. **Primary**: `job-status-updated`'s reducer case now returns the *exact same* state array reference (no new array, no new item object) when the incoming job's `status`/`errorMessage` match what's already stored for that item, or when the target id isn't in the queue at all. This is what actually lets `useReducer` stop scheduling re-renders — an equal-but-new array every time (the old behavior) never gave React the chance.
2. **Secondary**: `PolledUploadQueueItem` now accepts `onStatusUpdate: (id, job) => void` and curries `item.id` itself (already has it as a prop) instead of `UploadQueueList` pre-currying a fresh closure per item per render; `UploadWorkspace` wraps its handler in `useCallback` keyed on `queue.dispatch` (stable — `useReducer`'s own dispatch never changes identity), deliberately not on the whole `queue` object (a fresh reference every render, which would have defeated the memoization entirely — confirmed by momentarily trying it and watching `react-hooks/exhaustive-deps` flag exactly this).

**Tests**: `queue.test.ts` gained three reducer-level cases — unchanged status/errorMessage returns the same reference (`toBe`), a real change (different `errorMessage`) still returns a new one, and an unknown id also returns the same reference (tightening prior coverage from value-equality to reference-equality). `UploadWorkspace.test.tsx`'s existing polling-regression test was simplified (dropped the `StrictMode` wrapper and two-file variant added during diagnosis, since neither changed the outcome) and its docstring rewritten to say plainly what it does and doesn't prove. `PolledUploadQueueItem.test.tsx`'s one assertion on the old `onStatusUpdate(job)` signature was updated to `onStatusUpdate(id, job)`.

**Verification**: full workspace `typecheck`/`lint`/`test` green, 94 frontend tests (up from 90). Re-ran the real curl-based `/upload` check — confirms no server-rendering regression, but this specifically **cannot** verify the fix itself, since the bug has no server-rendered signature at all. This one needs the user's own browser to actually confirm.

**Confirmed fixed**: the user re-tested in a real browser and reported back directly — uploaded a document, no more "Maximum update depth exceeded," no React warnings in DevTools, upload completed and polling behaved correctly. That's the real verification for this bug; everything above was the closest available substitute until it landed.

## 7. Stage 4: Results (2026-08-08)

### Data layer: `features/results/extract-fields.ts`

`extractDocumentFields(resultJson: Record<string, unknown> | null)` walks `resultJson.documents[].fields`, returning `{name, displayValue, confidence: number | null}[]` — `displayValue` prefers a field's `content` (string) over `value` (string or number, stringified), falling back to `"—"` if neither is usable; `confidence` is `null`, never a fabricated `0`, when the field doesn't carry a numeric one (mirrors the backend's own `null`-not-`0` convention, §4 project-root decision 6). `extractRawContent(resultJson)` returns `resultJson.content` when present — the case for `generic` (Azure's `prebuilt-layout` model) results, which have no `documents[].fields` structure at all, only `{pages, tables, content}`.

Deliberately does **not** model Azure's full `DocumentField` union (bounding boxes, nested object/array fields, per-type value shapes) — every access goes through an `isRecord` guard and degrades to skipping that field/document rather than throwing on anything malformed or unexpected. This mirrors `apps/backend/src/utils/confidence.ts#computeAverageConfidence` deliberately: that's the one place in the codebase that already has to defensively parse this same genuinely-untyped field, and its own test fixtures (`{documents:[{fields:{Name:{value,confidence}}}]}` for field-shaped results, `{pages,tables}` for generic) are what this session verified the extraction logic's shape assumptions against, in the absence of a real Azure Document Intelligence response to check against directly (root `PROGRESS.md` §4 decision 26 — a real gap, not silently treated as fully closed).

16 tests: null input, non-array `documents`, real invoice/receipt-shaped extraction, multi-document flattening, `content`-over-`value` preference, the value-fallback and em-dash-fallback paths, null confidence for both missing and non-numeric values, malformed-field/malformed-document skipping without throwing, a `generic`/layout result correctly returning `[]`, plus 5 more for `extractRawContent` (null, present, missing, empty-string-treated-as-absent, non-string-treated-as-absent).

### Preview: `preview.ts`, `preview-cache.ts`, `use-document-preview.ts`

`preview.ts` implements the `DocumentPreviewSource` union locked in during Stage 3 planning (project-root `PROGRESS.md` §4 decision 2: `session-blob | remote-url | unavailable`) — `remote-url` still has no producer, since the backend still never persists uploaded files; the type exists purely so one can slot in later without touching any UI component that consumes it.

`preview-cache.ts` is a plain module-level `Map<string, File>` — deliberately not React state, not a Context, not lifted into `queue.ts`. It exists for exactly one purpose: letting `/documents/[jobId]` (a separate route from `/upload`) recover the just-uploaded `File` after a client-side navigation away from the upload queue's own component tree, where that `File` otherwise only lives in local reducer state. A plain module `Map` survives client-side route changes within the same page load (the module isn't re-evaluated) but is gone after a real page reload — matching the already-decided "session-only preview" scope exactly, since there's no cross-session story to build toward anyway. 4 tests, each using a unique `jobId` since the cache is genuinely module-level and persists across tests within the file (see §8 below for a test-authoring mistake this caused and how it was caught).

`use-document-preview.ts#useDocumentPreview(jobId)` reads the cache in a `useEffect`, creates a blob URL via `URL.createObjectURL` when a file is found, and revokes it in the effect's cleanup — on unmount and whenever `jobId` changes, so switching between two cached files doesn't leak the first one's URL. 4 tests: `unavailable` when nothing is cached, a `session-blob` result (`url` starting with `"blob:"`) when something is, `URL.revokeObjectURL` called with the right URL on unmount (`vi.spyOn`), and the previous URL revoked + a fresh one created when `jobId` changes via `rerender`.

**Wired into the upload flow**: `use-upload-controller.ts`'s `uploadMutation.mutate(...)` call now calls `cacheFileForPreview(response.job.jobId, next.file)` inside `onSuccess`, only for `response.kind === "single"` — a `.zip` batch's individual entries were never separately accessible client-side to begin with (same limitation `queue.ts` already documents for live sub-job polling), so there's no per-file `File` to cache against any of them. 2 new tests in `use-upload-controller.test.tsx`: a single upload's file is cached under its job id; a batch upload caches nothing.

### A lint rule, investigated rather than blindly suppressed or blindly obeyed

`react-hooks/set-state-in-effect` — part of the currently-installed `eslint-plugin-react-hooks@7.1.1`'s React-Compiler-oriented rule set (pulled in transitively through `eslint-config-next`; not something bumped this session) — flagged `useDocumentPreview`'s effect for calling `setSource(...)` directly in its body. Rather than either silently adding a blanket disable or restructuring around it without checking whether the rule had a real point, read the rule's own implementation (`validateNoSetStateInEffects` in the installed package's compiled source) to see exactly what it flags and what it recommends instead. It names three remedies: non-local derived data (doesn't apply — nothing here is owned by a parent), a derived-event pattern (doesn't apply — no prop transition being detected), and `useSyncExternalStore` for syncing from external mutable state (closer — `preview-cache.ts`'s `Map` genuinely is exactly that).

Worked through `useSyncExternalStore` concretely and it doesn't fully fit: it can cleanly replace the *read* half (getting the cached `File` for a `jobId`), but this hook also needs to *create a resource with paired cleanup* (the blob URL), which `useSyncExternalStore`'s `getSnapshot` contract doesn't cover — `getSnapshot` needs to be a pure, repeatable read, not something that allocates a browser resource each time it might get called (React can call it speculatively). The render-time alternatives that could compute the URL without an effect — `useMemo`, a lazy `useState` initializer — have a sharper problem: React Strict Mode's development-only double-invoke calls render-phase code (including `useMemo` callbacks and lazy initializers) twice with no paired cleanup mechanism, so either would leak one `blob:` URL per mount in development. The original `useEffect`-based pattern doesn't have this problem, because Strict Mode's double-invoke for *effects* specifically is mount→cleanup→mount — the first blob URL gets revoked before the second is created. Concluded the original pattern is not just acceptable but actually the *safer* one of the options considered, and kept it, with a single `eslint-disable-next-line react-hooks/set-state-in-effect` on the one line the rule actually flagged (the `unavailable`-reset branch — the `session-blob` branch's own `setSource` call, it turns out, isn't flagged by this rule at all; confirmed by briefly adding a disable comment there too and seeing ESLint itself report it as unused) and a comment explaining the reasoning above, not just "rule doesn't apply here."
