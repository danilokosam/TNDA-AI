# TNDA-AI Backend — Progress

## 1. Summary of Work Completed

A working, type-checked (strict TypeScript, zero `as` casts) Bun + ElysiaJS backend was built from scratch. The server boots, responds on all routes, and every request/response is validated with Zod (used directly as Elysia's Standard-Schema validators — no duplicate TypeBox/Zod schema pairs).

### Modules & endpoints

| Module | Endpoint | Auth | Purpose |
|---|---|---|---|
| health | `GET /health` | none | liveness check |
| auth | `POST /api/v1/auth/signup` | none | creates a Supabase auth user + organization + owner profile in one flow, rolls back the auth user if org/profile creation fails |
| auth | `POST /api/v1/auth/login` | none | Supabase password sign-in, returns session + profile |
| auth | `GET /api/v1/auth/me` | required | current user + organization |
| organization | `GET /api/v1/organizations/me` | required | org record + usage summary |
| organization | `GET /api/v1/organizations/me/usage` | required | pages/documents used vs. plan limits for the current billing period |
| billing | `GET /api/v1/billing/plans` | required | plan catalog (free/basic/pro) |
| billing | `GET /api/v1/billing/subscription` | required | org's effective plan + subscription row (or implicit free tier) |
| billing | `POST /api/v1/billing/checkout` | required | creates a Stripe Checkout Session (`{ planId: 'basic'\|'pro', redirectUrl? }` → `{ url }`) — see §9 |
| billing | `POST /api/v1/billing/portal` | required | creates a Stripe Customer Portal session (`{ returnUrl? }` → `{ url }`) |
| billing | `POST /api/v1/billing/webhook` | **public** — Stripe signature, not bearer auth | receives `checkout.session.completed` / `customer.subscription.created`\|`updated`\|`deleted`, syncs `subscriptions` — see §9 |
| documents | `POST /api/v1/documents` | required | multipart upload, single file **or** `.zip` batch, plus an optional `documentType` field (`invoice`\|`receipt`\|`identity_document`\|`generic`, defaults to `invoice`) that selects the processing strategy — see §6, §13 |
| documents | `GET /api/v1/documents/jobs/:id` | required | polls job status, pulling a fresh status from Azure if still in flight |

Swagger UI is mounted at `/docs`.

### Utilities & cross-cutting concerns

- **`src/utils/file-inspector.ts`** — detects true MIME type from magic bytes (`file-type`, never trusts client `Content-Type`), reads PDF page count via `pdf-lib` without rendering pages.
- **`src/utils/zip.ts`** — in-memory `.zip` extraction (`fflate`, no temp files), filters directories, `__MACOSX/`, `.DS_Store`, empty entries.
- **`src/utils/errors.ts`** — `AppError` hierarchy (`ValidationError`, `UnauthorizedError`, `QuotaExceededError`, `PayloadTooLargeError`, `UnsupportedFileTypeError`, `RateLimitedError`, `AzureServiceError`, …), each carrying an HTTP status + stable machine code.
- **`src/middlewares/error.middleware.ts`** — global `onError` normalizes every thrown error (ours and Elysia's own validation/parse/not-found errors) into `{ error: { code, message, details? } }`.
- **`src/middlewares/auth.middleware.ts`** — verifies the Supabase bearer token, loads the caller's `profiles` row, injects `auth: { userId, email, organizationId, role }` into context for every protected route.
- **`src/middlewares/rate-limit.middleware.ts`** — in-memory fixed-window limiter keyed by client IP (`RATE_LIMIT_WINDOW_MS` / `RATE_LIMIT_MAX_REQUESTS`); swap the `Map` for Redis if the app is ever scaled horizontally.
- **`src/services/azure-document-intelligence.service.ts`** — talks to Azure Document Intelligence over its **REST API directly** (not the `@azure/ai-form-recognizer` SDK — see note below), implements the 202/Operation-Location pattern by hand, and retries `429` responses with exponential backoff + jitter (honors `Retry-After`).

> **Design note on the Azure SDK vs. REST API:** the task allowed either. The SDK's `beginAnalyzeDocument` poller is designed to poll within one continuous process; this app instead persists the `Operation-Location` URL on `document_jobs` and resumes polling from a **separate, later HTTP request** to `GET /jobs/:id` (possibly hitting a different server instance). Driving the submit/poll REST calls by hand fits that architecture more directly and avoids fighting the SDK's poller-serialization model — so `@azure/ai-form-recognizer` was removed from `package.json` in favor of `fetch`.

## 2. Project Architecture Map

```
src/
  config/            env validation (Zod), Supabase client, Azure REST config, hand-written DB types
  modules/
    auth/            signup / login / me
    organization/     org profile, usage & quota computation (owns "effective plan" logic)
    billing/          plan catalog, current subscription, Stripe Checkout/Portal/webhook sync
    documents/        upload (single + zip), pre-flight quota checks, job polling
      *.routes.ts      HTTP layer (Elysia routes, Zod validation)
      *.service.ts     business logic
      *.repository.ts  Supabase access (service-role client; every query filters by organization_id itself since RLS is bypassed)
      *.schema.ts      Zod DTOs
      documents.strategy.ts  document-type -> processing-strategy registry (owns Azure model selection — see §13)
  services/          external integrations — azure-document-intelligence.service.ts
  middlewares/        auth, centralized error handling, rate limiting
  utils/             file inspection, zip extraction, AppError hierarchy
  index.ts           app wiring (cors, swagger, error/rate-limit middleware, route mounting)
supabase/migrations/  numbered SQL migrations (see §3)
```

**Backend-uses-service-role-key pattern:** all repositories query through `supabaseAdmin` (the service-role client), which bypasses RLS, and every query explicitly filters by `organization_id`/caller identity in application code. The RLS policies in the migrations are defense-in-depth for any future direct-from-client Supabase access, not the primary tenant-isolation mechanism for this API.

## 3. Database Migrations Status

**Applied and verified against the live Supabase project** (see §7). Nine SQL files in `supabase/migrations/`, applied in order:

1. `0001_extensions.sql` — `pgcrypto` for `gen_random_uuid()`
2. `0002_organizations.sql` — `organizations` table only (RLS/policies deliberately deferred — see `0004`)
3. `0003_profiles.sql` — `profiles` table (`owner`/`admin`/`member` role enum), FK to `auth.users` (RLS/policies deferred — see `0004`)
4. `0004_authorization.sql` — `current_organization_id()` helper + the RLS policies for `organizations` and `profiles` that call it. Split into its own migration, run after both tables exist, because `current_organization_id()` is a `LANGUAGE SQL` function whose body queries `profiles` — Postgres validates a SQL-language function's body against the catalog at `CREATE FUNCTION` time (unlike `plpgsql`, which defers to runtime), so defining it any earlier fails. See §7 for how this was discovered.
5. `0005_plans.sql` — `plans` catalog, seeded with `free` / `basic` / `pro` rows (idempotent `upsert`)
6. `0006_subscriptions.sql` — `subscriptions`, one active/trialing/past_due row per org enforced via partial unique index
7. `0007_document_jobs.sql` — `document_jobs` table + status enum (`pending/processing/completed/failed/rejected_quota`) + `updated_at` trigger
8. `0008_usage_functions.sql` — `get_organization_monthly_usage(org_id)` SQL function used by the pre-flight quota check
9. `0009_stripe_billing.sql` — adds `organizations.stripe_customer_id` (unique, nullable) and `subscriptions.stripe_customer_id`/`stripe_subscription_id` (the latter a **plain, non-partial** unique index, not the partial-index style used elsewhere in this schema — see §9 for why) for Stripe webhook sync

RLS is enabled on every table with `organization_id`-scoped `select` policies (and a same-org `insert` policy on `document_jobs`); writes beyond that are service-role only.

To (re-)apply against a Supabase project, two options are now available (see §7 for full detail — **do not mix the two on the same database**, they track applied migrations independently):

```bash
# Option A: this project's own migration runner (SUPABASE_DB_URL required in .env)
bun run db:migrate

# Option B: Supabase CLI
supabase link --project-ref <your-project-ref>
supabase db push
```

After applying, regenerate `src/config/database.types.ts` from the live schema if it ever drifts from the hand-written version:
```bash
supabase gen types typescript --project-id <your-project-ref> > src/config/database.types.ts
```
(the `Relationships` arrays this project's hand-written types use were shaped to match Supabase's own generator output, so a regenerated file should be a drop-in replacement.)

## 6. Pre-flight Validation & Zip Batch Logic (how the quota protection works)

`documents.service.ts`:

1. `submitUpload` checks `file.size` against `MAX_UPLOAD_SIZE_MB` (hard server cap) before reading any bytes, then sniffs the first bytes for a ZIP signature to decide single-file vs. batch.
2. **Single file** (`processSingleDocument`): `inspectDocumentFile` → real MIME type + PDF page count → `assertFileMeetsPlanConstraints` (file size vs. `max_file_size_mb`, page count vs. `max_pages_per_document`, both **hard** per-file caps, no DB row on failure) → monthly quota check (`pagesUsed + pageCount > max_pages_per_month` or `documentsUsed + 1 > max_documents_per_month`) → on quota failure, a `document_jobs` row is written with `status = 'rejected_quota'` for audit purposes and a `422` is returned → on success, a `pending` row is created, then submitted to Azure and flipped to `processing`.
3. **Zip batch** (`processZipBatch`): extracts all entries in memory, then loops with a **running in-memory quota counter** seeded from the DB — this is what stops many small files inside one archive from cumulatively blowing through the monthly quota even though each individually looked fine against the initial DB snapshot. Each file gets one of `processing / rejected / rejected_quota / failed` in the response; the archive is never rejected wholesale for one bad file inside it.
4. **Polling** (`getJobStatus`): terminal jobs (`completed/failed/rejected_quota`) are returned straight from the DB with no Azure call; in-flight jobs get one live `GET` against the stored `Operation-Location`, and the row is only written back to the DB when Azure reports a terminal state (`succeeded`/`failed`), to minimize writes.

## 7. Automated Supabase Migration Tooling (2026-08-06)

Added a real migration runner and validated it end-to-end against the live Supabase project (`.env` now has real Supabase credentials).

- **`scripts/db-migrate.ts`** reads every `.sql` file in `supabase/migrations/` (sorted ascending, numeric-aware), applies each one **inside its own transaction** against Postgres, and tracks what's already been applied in a `public._migrations(filename, applied_at)` table it creates on first run — so re-running the script is safe and idempotent; already-applied files are skipped.
- **Why it doesn't use `@supabase/supabase-js`** (as originally asked): `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` authenticate PostgREST, which only exposes specific tables/views/RPC functions — there is no generic "run arbitrary SQL" endpoint, by design. Nothing in our schema defines an `exec_sql`-style RPC either (and creating one would itself require running SQL first). So the script instead connects directly to Postgres over the wire protocol using the `postgres` package (added as a new dependency) and a new env var, **`SUPABASE_DB_URL`** (documented in `.env.example`, optional — only `db-migrate.ts` reads it via `Bun.env`, it was deliberately **not** added to `src/config/env.ts`'s Zod schema so the main app's boot-time validation and every other script/route stay unaffected by whether it's set).
- **`package.json`** gained two scripts: `db:migrate` (`bun run scripts/db-migrate.ts`) and `db:push` (`supabase db push`, the Supabase CLI's own equivalent, offered as an alternative). **These two are not interoperable** — `db:migrate` tracks state in `public._migrations`, the CLI tracks it in `supabase_migrations.schema_migrations`; mixing them against the same database means neither tool will know what the other already applied. Pick one per environment.
- **Connectivity gotcha hit and resolved during validation:** the direct Postgres hostname (`db.<ref>.supabase.co:5432`) resolves to an IPv6-only address on this Supabase project, and the sandbox this was run from has no IPv6 egress, so the first attempt failed with `ECONNREFUSED`. Fixed by switching `SUPABASE_DB_URL` to Supabase's **connection pooler** (Supavisor) endpoint instead — `aws-<n>-<region>.pooler.supabase.com:5432` with username `postgres.<project-ref>` — which is IPv4-compatible. Worth knowing if this is ever run from another IPv6-less environment (most CI runners, some sandboxes).
- **A real bug was caught and fixed by this first live run**, not by typechecking (which can't catch this — it's a Postgres catalog-validation-order issue, invisible to TypeScript): `0002_organizations.sql` originally defined `current_organization_id()` (a `LANGUAGE SQL` function whose body queries `public.profiles`) before `profiles` existed (`profiles` was created in `0003`). Postgres validates `LANGUAGE SQL` function bodies against the catalog at `CREATE FUNCTION` time — unlike `plpgsql`, which defers to first call — so this failed immediately on the real database with `relation "public.profiles" does not exist`. The transaction wrapper meant this rolled back cleanly with no partial state. **Fix:** split the migrations — `0002` and `0003` now contain only their tables (no RLS/policies), and a new `0004_authorization.sql` defines `current_organization_id()` plus the `organizations`/`profiles` RLS policies that depend on it, now correctly ordered after both tables exist. The old `0004_plans.sql` → `0007_usage_functions.sql` were renumbered up to `0005`–`0008` accordingly (renamed via `git mv` to preserve history — this happened before any commit had successfully applied them to production, so it was the right time to fix the ordering rather than patch around it).
- **Verified:** `bun run db:migrate` applied all 8 migrations successfully against the live project (`7 migration(s) applied, 1 already up to date` on the second run, after the fix); confirmed via a direct query that all six tables (`organizations`, `profiles`, `plans`, `subscriptions`, `document_jobs`, `_migrations`) exist and that the `plans` table seeded correctly (`free`: 1 page/document, 2 pages/month; `basic`; `pro`). `bun run typecheck` remains clean after all of this.

## 8. Azure Document Intelligence End-to-End Test (2026-08-06)

Added `scripts/test-e2e-azure.ts`, a self-contained live pipeline test: it spawns its own instance of the app (on a dedicated port, isolated from any `bun run dev` already running), signs up (or logs in, if the email already exists) a fresh test user via the real HTTP API, generates a mock invoice PDF **in memory with `pdf-lib`** (no fixture file on disk), uploads it through the real `POST /api/v1/documents` multipart endpoint, and polls `GET /api/v1/documents/jobs/:id` every 2 seconds until Azure reports a terminal state — printing the full extracted result payload at the end. Response shapes from the API are validated with Zod (`safeParse`/`parse`), consistent with the rest of the codebase — no `as` casts. Run it with `bun run scripts/test-e2e-azure.ts`.

**This surfaced and led to fixing a real, serious bug** — not something a fresh Azure resource alone would have caught; it required actually exercising the full request path with a real signup:

- **Symptom:** every document upload failed with `500 INTERNAL_ERROR: Cannot coerce the result to a single JSON object` — but only when going through the real running server, never when the same Supabase queries were replicated standalone.
- **Root cause:** `auth.repository.ts`'s `signInWithPassword` (called by both signup and login) was calling `.auth.signInWithPassword()` on the **shared `supabaseAdmin` singleton**. supabase-js mutates a client's own internal session on any successful sign-in, and from then on uses that session's user JWT — instead of the key the client was created with — as the Authorization header for every subsequent `.from()`/`.rpc()` call made on that *same client instance*. Since `supabaseAdmin` is a module-level singleton shared across the entire process, the **first** user to sign up or log in silently downgraded it from `service_role` to their own `authenticated` role for **every other request the server handles afterward**, until another sign-in overwrote it again.
- **Why it looked like a document-upload bug specifically:** the `document_jobs` RLS policies (0004_authorization.sql) grant `authenticated` users `select` and `insert` (scoped to their own org/user), by design, but deliberately **no `update`/`delete`** policy — those are meant to be service-role-only. So under a downgraded client, `INSERT` kept succeeding (matched the insert policy) while every subsequent `UPDATE` — marking a job `processing` or `failed` — silently matched 0 rows under RLS and threw. This is exactly why it reproduced 100% of the time through the real signup→upload flow but never in a standalone script that skipped sign-in.
- **Fix:** `src/config/supabase.ts` gained `createAuthClient()`, which constructs a **fresh, one-off** client (with the anon key) for password sign-in only, never reusing or mutating `supabaseAdmin`. `auth.repository.ts`'s `signInWithPassword` now calls `createAuthClient().auth.signInWithPassword(...)` instead of `supabaseAdmin.auth.signInWithPassword(...)`. `auth.admin.createUser()` and `auth.getUser(token)` (used by `auth.middleware.ts` on every request) were both verified empirically to **not** mutate client session state, so they were left on `supabaseAdmin`.
- **Incidentally, this also answers §7's "RLS is unverified" concern from the previous entry**: chasing this bug down *was* an end-to-end exercise of the RLS policies as a non-service-role client, and they behaved exactly as designed (insert allowed, update correctly denied) — which is what made the bug diagnosable in the first place.
- Also added lightweight `console.error` logging of the full Postgres/PostgREST error object (code, details, hint) in `documents.repository.ts`'s `createDocumentJob`/`updateDocumentJob` and in `documents.service.ts`'s `submitToAzure` catch block — previously these were fully swallowed into a bare `.message` string, which is what made this bug slow to diagnose. Kept permanently, not just for this session, since server-side visibility into DB failures is worth it and these never leak to the client response.

**Verified:** `bun run scripts/test-e2e-azure.ts` completes successfully end-to-end against the real Azure resource — job goes `processing` → `completed` after 4 polls (~8s), and the printed `resultJson` contains genuine Azure `prebuilt-invoice` extraction output (`docType: "invoice"`, confidence `1`, fields like `BillingAddressRecipient` correctly pulled from the mock PDF). `bun run typecheck` remains clean.

## 9. Stripe Billing & Subscriptions (2026-08-06)

Full checkout → webhook → subscription-sync flow, added to the `billing` module (which gained a `billing.repository.ts` and `billing.schema.ts` it didn't have before):

- **`src/config/stripe.ts`** — a single `stripe` client built from `STRIPE_SECRET_KEY`, plus `STRIPE_PRICE_ID_BY_PLAN` (`{ basic, pro }`) mapping our plan slugs to the two Stripe Price IDs from env. `env.ts` gained `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` / `STRIPE_PRICE_ID_BASIC` / `STRIPE_PRICE_ID_PRO` as required fields (`APP_URL` already existed from initial scaffolding and is reused as the default Checkout/Portal redirect base).
- **`POST /api/v1/billing/checkout`** (`{ planId: 'basic'|'pro', redirectUrl? }` → `{ url }`): resolves the organization's Stripe Customer, creating one via `stripe.customers.create()` and persisting it to `organizations.stripe_customer_id` on first use (`resolveOrCreateStripeCustomer`), then creates a `mode: "subscription"` Checkout Session with `client_reference_id`/`metadata` set to the organization id, and returns the hosted Checkout URL.
- **`POST /api/v1/billing/portal`** (`{ returnUrl? }` → `{ url }`): creates a Billing Portal session for the org's existing Stripe Customer; `422`s with a clear message if the org has never checked out (no customer yet).
- **`POST /api/v1/billing/webhook`** (public): registered **before** `.use(authMiddleware)` in `billing.routes.ts` (same pattern as `auth.routes.ts`'s public signup/login), since Stripe authenticates via the `stripe-signature` header, not a bearer token. Uses Elysia's `parse: "text"` route option (plus `body: z.string()` so the type inference matches) to get the **exact raw body string** — required because Stripe's HMAC signature check is byte-sensitive and would break on a JSON-parsed-then-re-serialized body. `verifyStripeWebhookEvent` calls `stripe.webhooks.constructEventAsync(rawBody, signature, STRIPE_WEBHOOK_SECRET)` (the async variant, Stripe's recommended one for non-Node runtimes like Bun, since it uses Web Crypto instead of Node's sync `crypto`) and throws `ValidationError` (400) on a bad/missing signature, per the task's explicit requirement.
- **Event handling** (`handleStripeWebhookEvent`): `customer.subscription.created`/`updated`/`deleted` all funnel through one `syncSubscriptionFromStripeObject` function that reads the org via `organizations.stripe_customer_id`, reads plan + billing period from `subscription.items.data[0]` (**not** top-level `subscription.current_period_start/end` — Stripe moved those fields to the item level in this API version, since a subscription can now have multiple items with independent billing cycles), maps the Stripe price id back to our `plan_id` and Stripe's richer status set (`incomplete_expired`, `unpaid`, `paused`, ...) down to our 5-value `subscription_status` enum, and **upserts by `stripe_subscription_id`** — so `created`→`updated`→`deleted` for the same subscription all converge on one row regardless of delivery order. `checkout.session.completed` retrieves the full subscription object and reuses the same sync function immediately, rather than waiting on a possibly-delayed separate `customer.subscription.created` delivery. Unrecognized customers/price-ids are logged and skipped (return `200`) rather than thrown as errors — retrying a webhook won't fix a config problem, so erroring would just cause Stripe to retry pointlessly for up to 3 days.
- **A real cast-avoidance catch during review:** an early draft of the price-id → plan-id reverse lookup used `Object.entries(...).find(...)` and cast the result back to `PaidPlanId` with `as` — caught before shipping and replaced with a properly-typed `Record<string, PaidPlanId>` reverse map instead, keeping the zero-`as` rule intact.
- **A real correctness catch during review:** the initial migration made `subscriptions.stripe_subscription_id`'s unique index **partial** (`where stripe_subscription_id is not null`), mirroring the style used for `organizations.stripe_customer_id` — but PostgREST's `.upsert(..., { onConflict: "stripe_subscription_id" })` generates a plain `ON CONFLICT (stripe_subscription_id) DO UPDATE` with no `WHERE` clause, which can't target a partial index. Fixed by making that one index non-partial before ever applying it live; Postgres already treats every `NULL` as distinct under a plain unique index, so nothing was lost by dropping the partial predicate.

**Verified live**, end-to-end, against the real Stripe API and the live Supabase project (no Stripe CLI available in this sandbox, so webhook delivery was tested by self-signing events with `stripe.webhooks.generateTestHeaderStringAsync()` using the same `STRIPE_WEBHOOK_SECRET` configured in `.env` — this exercises the exact same verification and sync code path a real Stripe-delivered webhook would, just without needing a publicly reachable endpoint):

1. Signup → `GET /billing/subscription` correctly shows the implicit free tier (no `subscriptions` row yet).
2. `POST /billing/checkout` → real `checkout.stripe.com` URL returned; `organizations.stripe_customer_id` persisted.
3. `POST /billing/portal` → real `billing.stripe.com` URL returned, reusing that same customer.
4. `POST /billing/webhook` with a bad signature → `400 VALIDATION_ERROR`, as required.
5. A self-signed `customer.subscription.updated` event → `200`, and `subscriptions` gets a new row (`plan_id: "basic"`, `status: "active"`, correct period dates, both Stripe ids set); `GET /billing/subscription` immediately reflects it.
6. A self-signed `customer.subscription.deleted` event for the *same* subscription id → `200`, and the **same row** flips to `status: "canceled"` (confirming the upsert-by-`stripe_subscription_id` convergence works); `GET /billing/subscription` correctly falls back to the free plan again, since `canceled` isn't in the "active" set the partial `subscriptions_one_active_per_org` index / `getActiveSubscription` query looks for.

`bun run typecheck` remains clean throughout (zero `as` casts).

## 13. Azure Model Selection Decoupled from Global Config — Strategy Pattern (2026-08-06)

Removed `AZURE_DOCUMENT_INTELLIGENCE_MODEL_ID` as a global setting. Previously the entire app used exactly one Azure model (`prebuilt-invoice`, read from that env var) for every upload regardless of what was actually in the file — a receipt, an ID document, anything, all analyzed as if it were an invoice. Model selection is now a per-request runtime decision owned by the domain layer, via a small strategy pattern.

- **`src/services/azure-document-intelligence.service.ts`** is now a pure infrastructure adapter: `beginDocumentAnalysis(bytes, mimeType, modelId)` takes `modelId` as a required parameter instead of reading `azureDocumentIntelligenceConfig.modelId`. It has zero opinion on which model gets used for what — `src/config/azure.ts` no longer has a `modelId` field at all, and `env.ts` no longer declares `AZURE_DOCUMENT_INTELLIGENCE_MODEL_ID`.
- **New `src/modules/documents/documents.strategy.ts`** (domain layer) owns the actual decision: `DocumentType = "invoice" | "receipt" | "identity_document" | "generic"`, a `DocumentProcessingStrategy` interface (`{ documentType, submit(bytes, mimeType) }`), and a `STRATEGIES: Record<DocumentType, DocumentProcessingStrategy>` registry mapping each type to an Azure-prebuilt-model strategy today. Adding a new document type, pointing one at a different Azure model, or swapping a strategy to a different provider entirely (or a multi-step Azure+LLM pipeline) is a change scoped to this one file — `documents.service.ts`, the routes, and the Azure REST adapter itself are all unaffected either way, which was the explicit goal of this refactor.
- **Scope boundary, stated deliberately, not an oversight**: only *submission* is abstracted by the strategy interface. Status polling (`getJobStatus`) and persistence (`document_jobs.azure_operation_id`) still assume Azure's Operation-Location model, since every strategy today is still Azure-backed. A genuinely non-Azure strategy would also need to address how *that* provider's progress gets checked — intentionally left for whenever (if ever) that's actually needed, rather than generalized speculatively now.
- **`documents.schema.ts`**'s `uploadDocumentSchema` gained `documentType: z.enum(DOCUMENT_TYPES).default("invoice")` — a new multipart form field, defaulting to `"invoice"` specifically to preserve the pre-refactor behavior (the old global default was `prebuilt-invoice`) for any existing caller that doesn't send it. For a `.zip` batch, the requested type applies to every file in the archive — there's no per-file type detection, which wasn't asked for and would be a different, larger feature.
- **`processSingleDocument`/`processZipBatch`/`submitUpload` in `documents.service.ts`** all gained a `documentType` parameter, threaded down from the route to a renamed `submitForAnalysis` (was `submitToAzure` — renamed because it no longer has any Azure-specific knowledge itself; it just resolves a strategy via `getProcessingStrategy(documentType)` and calls `.submit()`).
- **A real bug caught by live verification, not by the unit tests**: the first `generic` → model-ID mapping used `"prebuilt-document"`, which turned out to return a genuine `404 ModelNotFound` from Azure's `2024-11-30` API — that model ID has apparently been retired/renamed server-side and the unit tests (which mock the Azure adapter) had no way to catch this, since they only assert *that* the right model ID string gets passed through, not that Azure actually recognizes it. Caught by manually uploading a real file with `documentType: "generic"` against the live server and seeing the real Azure error. Fixed by switching `generic` to `prebuilt-layout` (Azure's stable general OCR/structure model) — arguably a better semantic fit for "generic" anyway, since it makes zero domain assumptions at all, unlike `prebuilt-document`'s key-value heuristics.
- **Also fixed a self-inflicted verification mistake worth recording**: a stray `bun src/index.ts` process from earlier in this session was still bound to port 3000 (from before this refactor's code changes), so the first live verification attempt actually hit stale, pre-refactor code and silently "confirmed" the wrong model was used. `EADDRINUSE` in the new process's own log was the tell. Killed the stale process before trusting any further manual verification.

**Verified**: `bun run typecheck`/`lint`/`test` (53/53, +4 new tests in `documents.strategy.test.ts` covering the registry, per-type model uniqueness, and the `operationLocation` → `operationReference` mapping) all pass. ## 14. Document List/History + Analytics Endpoints (2026-08-07)

The frontend's Dashboard and History features needed a list/filter/aggregate capability the backend never had (only single-job-by-id lookup existed). Rather than have the frontend read `document_jobs` directly via Supabase RLS to work around that — the originally-planned frontend-side workaround — the backend gained two new endpoints, keeping it the single source of truth for querying, filtering, pagination, and analytics. Designed as stable, general-purpose REST endpoints (predictable envelope shapes, opaque pagination cursors, parameterized filters), not shaped around this specific frontend.

- **`GET /api/v1/documents`** — cursor-paginated, filterable job list. Query params: `status`, `documentType`, `search` (matches `file_name`), `dateFrom`/`dateTo`, `cursor`, `limit` (1-100, default 20). Response: `{ data: JobDto[], pagination: { nextCursor, hasMore } }`. `JobDto` gained `documentType`/`averageConfidence` (previously computed/discarded at upload time, now persisted — see below).
  - **Keyset pagination on `created_at` alone**, not offset (`.range()`) and not a compound `(created_at, id)` cursor. Offset pagination drifts under concurrent inserts — a real case here, since a batch upload can add rows while someone's paging through their own history. A compound cursor would need Supabase's `.or()` raw-filter-string DSL to express `(created_at, id) < (cursor)`, which means interpolating decoded, client-supplied cursor content into a filter *expression* rather than a filter *value* — accepted the simpler, safer trade instead: two jobs created in the exact same instant could theoretically land on opposite sides of a page boundary, rare enough (each row is written by a separate awaited round trip) not to be worth the larger attack surface.
  - The pagination cursor is opaque on the wire (base64url of the encoded `created_at`) — callers pass back exactly what `nextCursor` gave them, never construct one themselves, so the encoding can change later without breaking any client's request shape. A malformed/tampered cursor is treated as "no cursor" (first page), not a request error.
- **`GET /api/v1/organizations/me/stats`** — success rate, average processing time, and a daily job-count series for charting. Query: `since` (ISO datetime, defaults to 30 days back, bounded to 400 days back and not in the future — both enforced by `organization.schema.ts`, not just documented). Backed by two new `SECURITY INVOKER` Postgres functions (`get_organization_job_stats`, `get_organization_daily_job_counts` — migration `0010_document_analytics.sql`), following the existing `get_organization_monthly_usage` precedent for aggregation in SQL rather than pulling rows into the app to sum. Deliberately **not** `security definer`/`grant`ed to `authenticated` like that earlier function is — these are only ever called by the service-role client, which already bypasses RLS regardless, so granting broader access would be unnecessary surface area.
  - `successRate` is `null`, not `0`, when there are no terminal (completed/failed) jobs in the window — `0` would misleadingly read as "100% failure" when the honest answer is "no data yet."
  - The daily-count series is **gap-filled to a complete, contiguous date range** in the service layer (`organization.service.ts#buildDailySeries`) — the Postgres function itself only returns days with actual activity (a plain `GROUP BY`), and a day missing from a sparse result is indistinguishable from "no data at all" to a client that doesn't know the query's internals. Every consumer of this API gets a complete, chart-ready series without needing to know that detail.
- **`document_jobs.document_type` and `.average_confidence` are now actually persisted**, not just computed and discarded. `document_type` was already resolved per-upload (it picks the Azure model) but never saved to the row; now written on every `createDocumentJob` call. `average_confidence` is computed at job-completion time by a new `src/utils/confidence.ts#computeAverageConfidence`, which averages every field-level confidence in Azure's `documents[].fields{name:{confidence}}` shape (the invoice/receipt/identity_document models) and returns `null` — not `0` — for `generic` (`prebuilt-layout`), which has no per-field confidence at all.

**Verified against the real database, not just typechecked**: seeded 15 synthetic `document_jobs` rows (varied statuses/types/dates/confidence, direct SQL insert — real Azure calls aren't relevant to testing list/filter/pagination logic) for a real test org, then confirmed live against the running server: default listing, `limit`-bounded pagination with a working cursor into page 2 (no overlap, no gaps), every filter (`status`, `documentType`, `search`) independently narrowing results correctly, invalid query values rejected with `400 VALIDATION_ERROR` and a clear per-field message, unauthenticated requests rejected with `401`, and the stats endpoint's default/custom `since`, gap-filled `dailyCounts`, and both out-of-range rejections (`since` too old, `since` in the future) all behaving exactly as designed. Synthetic rows deleted afterward.

**Tests**: 34 new tests across 4 new files (`documents.repository.test.ts`, `documents.routes.test.ts`, `organization.repository.test.ts`, `organization.service.test.ts`) — 94 total, up from 60, all passing. `documents.routes.test.ts`/`organization.routes.test.ts` are the first tests in this codebase to exercise an authenticated route's success path rather than only its 401 case — they mock `supabaseAdmin.auth.getUser` and the `profiles` lookup `auth.middleware.ts` itself makes, establishing the pattern for any future route test that needs auth to succeed. `organization.service.test.ts` uses `vi.useFakeTimers()` to test the gap-filling date-series logic deterministically, since it's computed relative to `new Date()`.

## 15. Wave 1 — ZIP-bomb protection, auth/upload-security test coverage, CI dependency scanning (2026-08-08)

Backend-specific detail for the Wave 1 pass described in full at the root `PROGRESS.md` §3.20 (grounding in the companion audit, cross-app scope, the six-item breakdown) — this section covers only what's specific to this app.

### `utils/zip.ts`: streaming extraction, not `unzipSync`

`extractZipEntries` previously handed the whole archive to fflate's `unzipSync` in one call — no limit on entry count, per-file size, or total decompressed size, and no way to interrupt a bad archive mid-decompression. Rewritten around fflate's incremental `Unzip` class: the archive is pushed in bounded 64KB chunks (not all at once — reading fflate's own `inflt` source confirmed its internal output buffer only grows chunk-by-chunk as input is fed, so this is what actually lets a resource check abort mid-expansion), with `UnzipInflate` registered explicitly (`Unzip`'s default constructor only auto-registers the "stored"/uncompressed decoder, not DEFLATE — confirmed by reading the source, not assumed). Three new exported constants: `MAX_ZIP_ENTRIES` (500), `MAX_ZIP_ENTRY_UNCOMPRESSED_BYTES` (100MB — 2× the `pro` plan's 50MB/file limit, the largest real case), `MAX_ZIP_TOTAL_UNCOMPRESSED_BYTES` (300MB). A declared size is checked upfront where the local file header provides one; the real, running decompressed byte count is independently tracked via the `ondata` callback and enforced as bytes actually stream out, so a header that lies (or, for a streaming-created archive, never declares a size at all) is caught the same way. A cheap End-Of-Central-Directory signature scan up front preserves the "not a valid .zip" rejection for non-zip input, since the streaming reader otherwise has no reason to notice a missing EOCD on its own (it only recognizes local file headers as it scans, unlike `unzipSync`'s central-directory-based parsing).

`zip.test.ts` (new, 10 tests) proves the real production constants, not scaled-down stand-ins — highly-compressible (all-zero) fixtures keep the *compressed* test archives at a few KB and fast to build/run, while genuinely exceeding the real limits once decompressed. One test specifically builds its fixture via fflate's streaming `Zip`/`ZipDeflate` writer (not `zipSync`) so the resulting entry has no declared size at all, proving the incremental byte-counting guard catches a bomb even when the cheap upfront check has nothing to check against.

### Auth module + rate limiter: from zero test files to full coverage

`auth.repository.ts`, `auth.service.ts`, `auth.middleware.ts`, `auth.routes.ts`, `rate-limit.middleware.ts` — 44 new tests. ### Upload-security boundary: `file-inspector.ts` + `submitUpload`

`file-inspector.test.ts` (new, 13 tests) proves classification is by real content, not filename — a file named `invoice.pdf` whose actual bytes are a PNG is correctly reported as `image/png`, the literal security property this module's own docstring already claimed but had never been tested. **Bug fixed, not previously documented anywhere**: constructing a deliberately-corrupt-but-recognizable TIFF fixture (a valid 4-byte signature followed by a bogus IFD offset) made `fileTypeFromBuffer` throw (`End-Of-Stream`, from `strtok3`'s internal tokenizer) instead of returning `undefined` — meaning a real upload shaped like this would have propagated as an unhandled exception instead of a clean `UnsupportedFileTypeError`. Now caught and treated the same as "type not detected." ## 18. Wave 3 Phase 1 — job-claiming schema and RPC (2026-08-08)

Backend-specific detail for the Wave 3 Phase 1 pass described in full at the root `PROGRESS.md` §3.22 — a full architecture design review happened first (background processing: claiming, crash recovery, retries, idempotency, the Azure lifecycle, polling, queue-vs-database, worker design, concurrency, the state model, event-log integration, failure modes, tenancy, observability, testing, deployment), approved in principle, with implementation explicitly scoped to Phase 1 only. Only what's specific to this app is repeated here.

**Azure idempotency investigation** (required before any code, per explicit instruction): fetched Microsoft's own REST API reference for API version `2024-11-30` (the exact version `config/azure.ts` targets) and confirmed no idempotency-key/dedup mechanism exists on the `:analyze` endpoint — every submission creates a fresh, server-generated operation unconditionally, with no way to discover an orphaned one afterward. The narrow "submitted to Azure, crashed before persisting the operation id" gap identified by the design review cannot be closed on Azure's side; stays an accepted, documented limitation (ADR 0012). Directly ruled out adding `submission_attempted_at`: its only value would be forensic, it changes no behavior, and this phase doesn't touch the submission code path at all.

**Schema** (`0016_document_job_claiming.sql`, the first migration since Wave 2's `0014`/`0015`): `document_jobs` gains `claimed_by`/`claimed_at`/`lease_expires_at` (the claim), `lease_epoch` (a fencing token, bumped only on a fresh claim, never a renewal), and `next_attempt_at` (backoff scheduling — the column Wave 2's ADR explicitly deferred to this wave). Two CHECK constraints (claim-field all-or-nothing consistency; `next_attempt_at` only meaningful on a retryable failure) mirror this schema's existing "app logic primary, DB constraint backs it up" pattern. One partial index (`document_jobs_claimable_idx`) covers the common pending/processing claim path. Claim state lives directly on `document_jobs`, not a new table — same orthogonal-attribute precedent as `deleted_at`/`review_status`/`retry_count`. No `document_job_events` change — claiming/leasing are worker-operational mechanics (the architecture doc's own kind-(2) taxonomy), not domain events.

**The RPC**, `claim_or_renew_document_job(p_worker_id, p_lease_seconds, p_max_retries)`: renews an existing claim the caller already holds, or atomically claims one eligible row via `SELECT ... FOR UPDATE SKIP LOCKED`, folding a failed-and-retryable row's retry transition (status back to `pending`, `retry_count` incremented, `is_retryable`/`next_attempt_at` reset) into the same statement. `documents.repository.ts` gained `claimOrRenewDocumentJob`, wrapping it exactly the way `organization.repository.ts`'s existing RPC wrappers do.

**Two real defects caught during this phase's own independent review, before the migration was applied**:
1. **A concurrency-slot naming trap.** The design implicitly assumed one `claimed_by` value per worker *process*; tracing through `WORKER_CONCURRENCY > 1` (an already-approved later-phase default) showed a worker holding several jobs at once would have every renewal call silently renew *all* of them instead of claiming new work, since the RPC's renew-vs-claim decision is purely "does a row already have `claimed_by` = this value." Fixed by documenting explicitly, everywhere the parameter appears (migration column comment, RPC comment, repository TSDoc), that it identifies one claim *slot*, not a process.
2. **A real, confirmed security gap.** The migration's first draft assumed omitting a `GRANT ... TO authenticated` was sufficient to keep the RPC service-role-only (mirroring how `document_jobs`' own UPDATE/DELETE already have no `authenticated` policy). Querying `information_schema.routine_privileges` against the real database mid-review proved this wrong twice over: PostgreSQL grants `EXECUTE` to `PUBLIC` by default on function creation, and this specific Supabase project *also* grants `EXECUTE` directly to `authenticated`/`anon`/`service_role` on every new `public`-schema function (a project-level default-privilege rule, not anything this repo's own migrations set up) — confirmed empirically, not assumed from Postgres defaults alone. Fixed with two explicit `REVOKE` statements (`PUBLIC`; then `authenticated`/`anon` by name); `service_role`'s own access was verified, empirically, to survive both.

**Tests**: 3 new unit tests (`documents.repository.test.ts`) covering `claimOrRenewDocumentJob`'s call shape, the null-on-nothing-available case, and the AppError path — mirroring `organization.repository.test.ts`'s existing RPC-mocking convention. Per explicit instruction, the real concurrency/locking/timing behaviors were **not** added as permanent CI-running integration tests (this project's CI stays unit-tests-only for now — a stated, deliberate limitation, not an oversight; revisit only if the worker architecture later makes it necessary). Instead verified via a real-database script run directly against the development Supabase project: two concurrent claims never both win; a pending job is claimable; a retryable failed job becomes claimable only once `next_attempt_at` passes, with the retry transition correct; a terminal failed job is never claimed; an active lease can't be stolen; an expired lease is reclaimable; renewal is owner-only; a stale (reclaimed-over) worker can neither renew nor have an epoch-gated write succeed; organization isolation holds; a soft-deleted job is never claimed; both CHECK constraints reject what they should; the grants themselves are correct (`authenticated`/`anon` denied, `service_role` allowed) — 36 checks, all passing.

**A real, populated dev database needed real care, not just a clean-room assumption.** This database has months of real leftover `pending`/`processing` rows from prior manual verification sessions (already documented in this file's own history — e.g. accumulated `e2e-test-*` rows). The verification script's first two iterations had real flaws surfaced by this: fixture rows lost the claim query's `ORDER BY created_at ASC` race to older real rows (fixed by pinning fixture timestamps far in the past, non-destructively — nothing pre-existing was ever read, claimed, or modified by this fix); and several assertions incorrectly expected a losing concurrent caller to get `null`, when in a live, uncontrolled-population database it legitimately claims some *other* real available job instead (fixed by asserting "didn't get *my* specific job," not "got nothing"). A handful of real historical rows were incidentally claimed by the script's early, still-buggy iterations before these fixes landed — all identified and fully restored to their untouched claim state (verified by a final query showing zero rows with any claim set anywhere in the table) before the phase was considered done.

### Live verification — two real defects found and fixed, then re-verified end to end

Running the worker as a real process against the development Supabase project and live Azure — the one gap the initial verification above left open — found two real defects no mocked test could have caught, both fixed, both re-verified live afterward. Full reasoning for both in `docs/adr/0013`'s "Two real defects found by live verification" section; summarized here.

1. **The worker process crashed entirely on a single unexpected polling exception.** A live worker claimed a pre-existing leftover fixture row (unrelated debugging data from an earlier session, since cleaned up) whose `azure_operation_id` no longer resolved. `checkClaimedJobProgress` had no try/catch around `getAnalysisOperationStatus` — it mirrored the old `getJobStatus`'s shape, safe there only because Elysia's per-request error middleware caught it; nothing equivalent exists in a worker process. The exception propagated through `runClaimSlot` into `worker/index.ts`'s unguarded `Promise.all(slots)` and killed the whole process, taking every other slot's in-flight work down with it. **Fixed**: `runClaimSlot` now wraps its per-iteration claim/submit/poll work in a try/catch — logs full context (slot id, job id, stack trace), clears in-memory job tracking, attempts no epoch-gated write from the catch block, and lets Phase 1's existing lease-expiry mechanism recover the row. `worker/index.ts` now uses a new `runSlots` helper (`claim-loop.ts`, `Promise.allSettled` + rejection logging) instead of a bare `Promise.all`, so one slot's own unanticipated failure can't cascade into killing healthy siblings.
2. **Phase 1's `claimOrRenewDocumentJob` (already committed, `275d578`) didn't actually return `null` when nothing was available to claim.** With multiple concurrent slots racing for one available row, the losing slots received `{ id: null, status: null, ... }` — PostgREST's real serialization of a SQL NULL composite return — instead of a genuine `null`. `return data ?? null;` let this truthy object through; the claim loop mistook it for a held job with `status: null`, which matches neither `"pending"` nor `"processing"`, so the slot just believed it held a phantom job forever. Since `shouldContinue()` is only re-checked while idle, an affected slot never checked it again — **graceful shutdown hung indefinitely** (confirmed: `SIGTERM` logged as received, process still alive 8+ seconds later, required `SIGKILL`). **Fixed** in `documents.repository.ts#claimOrRenewDocumentJob`: `return data?.id ? data : null;` — `id` is the primary key, never null on a real row. This is a fix to already-shipped Phase 1 code, not a Phase 2 change; Phase 1's own "nothing available" unit test previously mocked a bare `data: null`, which couldn't have caught the real shape — it now reproduces the actual object-of-nulls response, plus a new pass-through assertion for a real row.

## 23. Investigation: a document stuck at `pending` in local development — not a bug (2026-08-08)

A real user report ("uploaded a document, the frontend keeps polling `GET /api/documents/:id` every few seconds, `/documents` stays at `Waiting to process…` indefinitely") was investigated per this project's systematic-debugging discipline — root cause first, no fix without it. Zero code changes resulted; every system involved was confirmed working exactly as designed.

**Evidence gathered, in order**: (1) `ps`/`lsof` showed no `src/worker/index.ts` process running anywhere in the dev environment — only the API server, the frontend dev server, and an unrelated `stripe listen` process. (2) The specific job's row (`document_jobs`) showed `status: "pending"`, `claimed_by: null`, `lease_epoch: 0`, `retry_count: 0`, `next_attempt_at: null`, and a correctly-persisted `storage_path` — a fully healthy, fully eligible, never-claimed row, not a stuck lease or a failed claim. (3) `document_job_events` for that job contained exactly one row, `job_created` — no claim, no processing, no error, ever. (4) The claim RPC's own `WHERE` clause (`0016_document_job_claiming.sql`) filters only on `deleted_at is null and status in ('pending', 'processing')` plus retry-eligibility — no `organization_id`/role condition exists anywhere in it, ruling out the reporting user's `member` role or organization as a factor. (5) `features/upload/poll-schedule.ts#getNextPollInterval` and its existing test suite (`poll-schedule.test.ts`) already explicitly assert that `pending`/`processing` keep polling and `completed`/`failed`/`rejected_quota` stop — the "indefinite polling while pending" behavior observed is the tested, intended design, not a leak. (6) `git log -S"worker:dev"` confirmed the worker scripts were introduced in this same Wave 3 Phase 2 commit and `turbo.json`'s `dev` task has been unchanged since the monorepo's initial wiring — the worker has never been part of `bun run dev`'s fan-out, by original design (ADR 0013), not a regression.

**Root cause**: the background worker was simply never started in this development session. This is the exact, already-documented consequence of Wave 3 Phase 2's own deliberate decision not to wire the worker into the dev fan-out ("whoever operates this needs to actually run `bun run worker:start`/`worker:dev`... nothing starts it automatically"). No defect exists in job creation, claiming, the worker, Azure submission/polling, terminal-state persistence, `GET /api/documents/:id`, or frontend polling.

**Hypothesis verified live, not just asserted**: with the reported job still `pending` and the frontend actively polling it in a real browser, `bun run worker:start` was started for real — it claimed the exact reported job within 3 seconds, downloaded it from Storage, submitted it to the real Azure Document Intelligence resource, and completed it with a real extracted result (a 1-page invoice-type image, 85% average confidence). The frontend's own polling picked up the `pending → processing → completed` transition on its existing schedule with no changes, rendered the full extracted-fields view, and — confirmed by direct network-request inspection over a window longer than the polling schedule's own maximum interval — **stopped polling entirely** once `completed` was reached, exactly as `poll-schedule.ts` already guarantees. `/documents` correctly showed "Completed" immediately after. The worker was then sent a real `SIGTERM` and exited cleanly (`"all slots drained, exiting"`), no `SIGKILL` needed. This also resolves this file's own previously-open item from §23's "To resume work" list: a human has now visually confirmed the worker-driven upload flow in a real browser, end to end.

**Tests**: none added or changed. The investigation's own evidence-gathering (above) confirmed every implicated behavior — job eligibility, claim-RPC scope, polling backoff/termination — already has direct, passing test coverage (`claim-loop.test.ts`, `documents.service.test.ts`, `documents.repository.test.ts`, `poll-schedule.test.ts`); adding more here would test nothing that isn't already protected, and no regression was found to protect against.

**Verification**: full monorepo `typecheck`/`lint`/`test` clean — backend 347/347, frontend 346/346 (both unchanged, since nothing was modified). `git status` confirmed empty for the entire duration of the investigation.

**Open question, not resolved here — needs a decision, not a silent fix**: a developer manually testing uploads (as opposed to running the Phase 2 verification script, which starts and stops the worker itself) has no signal that a second, separate process is required, and gets an indefinitely-spinning "Waiting to process…" with no explanation. Smallest-to-largest options, **none implemented**, pending direction: (a) document the requirement more prominently (README "Getting Started", a note in the Upload page's own copy) — zero implementation risk; (b) add a convenience script so starting the worker doesn't require `cd apps/backend` first; (c) wire `worker:dev` into `turbo run dev`'s fan-out — reverses a decision ADR 0013 made deliberately, and needs explicit sign-off before touching, not a unilateral change during a bug investigation.
