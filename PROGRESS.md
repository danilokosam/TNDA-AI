## 1. Project Overview

TNDA-AI is a multi-tenant SaaS platform for automated document processing (invoices, receipts, identity documents, generic scans — single files or `.zip` batches) via Azure Document Intelligence, with Stripe-backed subscription billing. Two applications: a Bun + ElysiaJS REST API (`apps/backend`) and a Next.js dashboard (`apps/frontend`), in a pnpm + Turborepo monorepo. **The backend is the single source of truth** for business logic, querying, filtering, pagination, and analytics — the frontend never queries Supabase directly for application data (it does use Supabase directly for one thing only: session/cookie management via `@supabase/ssr`, which is identity plumbing, not application data — see §4, decision 1).

### 3.3 Frontend Stage 1 — Shell + Auth

Built the full authenticated app shell: `proxy.ts` (centralized session refresh via `@supabase/ssr`'s `getUser()`, route protection, reciprocal `/login`↔`/dashboard` redirect, 401-not-redirect for unauthenticated `/api/*` calls), the `services/` → `/api/*` Route Handler → BFF architecture, sidebar/topbar shell, login/signup forms, 5 stub pages for the planned routes.

**The single biggest finding of this phase**: the plan's Eden Treaty approach (type-only importing the backend's exported `App` type for zero-hand-written DTOs) **does not work** — verified by testing, not assumed. `backend/src/index.ts` transitively imports every route module via the backend's own `@/*` alias; TypeScript resolves those imports using the *importing project's* `tsconfig.json` paths, not the imported file's own, so once pulled into a frontend file the alias resolves against the wrong root and fails outright. The fallback (`openapi-typescript` against the backend's mounted Swagger) also doesn't work — `@elysiajs/swagger` serializes raw Zod-internal `_def` trees instead of real JSON Schema, confirmed by fetching `/docs/json` directly and finding every response schema is a bare `{}`. Landed on a hybrid: files with zero internal imports (`database.types.ts`, `utils/errors.ts`) resolve fine as type-only cross-project imports and are used directly (zero duplication for those); everything else is hand-written Zod in `frontend/types/api.ts`, verified field-by-field against real backend source, parsed at every API call site (runtime safety, not just compile-time), with a compile-time `AssertExact<A,B>` check wherever a schema mirrors a type-importable DB row. **Caught a real bug in that safety net itself**: the first version used `declare const` for the assertion, which type-checks successfully regardless of what it resolves to (declaring a `never`-typed variable isn't itself an error) — a deliberate-break test (`price_monthly: z.number()` → `z.string()`) confirmed `tsc` still passed. Fixed by switching to a real assignment (`export const _checkX: AssertExact<...> = true`), which actually forces the check.

Verified end-to-end via `curl` against the real backend + Supabase project: signup → real org+profile created → single non-chunked `SameSite=lax` session cookie set → dashboard renders with real data → reciprocal redirect → `/api/organization` returns real parsed data → logout actually clears the session (not just the cookie) → subsequent access correctly denied → login → wrong password → invalid signup body, all behaving correctly. ### 3.8 Stage 2 close-out review

Before committing, asked to review every uncommitted change once more rather than take the prior pass as final — this caught two real issues that a second, more skeptical read surfaces and a first implementation pass didn't:

- **`UsageMeter` used `role="progressbar"` with an unclamped `aria-valuenow`.** A progress bar is semantically "an operation running to completion" — usage-vs-quota is a scalar measurement within a known range, which is ARIA's `role="meter"` (the dataviz skill's own name for this component, too). Also, `documentsUsed`/`pagesUsed` are plain counts, not clamped to the plan limit — an org that used to be on a higher plan and downgraded (or any future edge case producing `used > limit`) would have pushed `aria-valuenow` past `aria-valuemax`, which is invalid per the ARIA spec. Fixed: `role="meter"`, `aria-valuenow` clamped to `Math.min(used, limit)`, and an explicit `aria-valuetext` so the real (possibly over-limit) numbers are still what gets announced.
- **The empty-state gate only checked `stats.totalJobs`, which counts terminal (completed/failed) jobs only.** Verified directly against `0010_document_analytics.sql`: `get_organization_daily_job_counts` and `get_organization_job_stats` share the exact same `where ... and status in ('completed', 'failed')` clause, so `dailyCounts` and `totalJobs` are always consistent with each other — that part was already correct. But an org with a job still `pending`/`processing` (uploaded, not yet resolved) would have `totalJobs === 0` and see "No documents yet," which is misleading once Stage 3 makes that a reachable real state. `usage.documentsUsed` (from `/organizations/me`, already fetched on this page) counts `pending`/`processing`/`completed` — cheap, already-available signal to add. Gate is now `stats.totalJobs === 0 && usage.documentsUsed === 0`.
- **Noted, not changed**: `apps/frontend/PROGRESS.md`'s Stage 0 section says the plan anticipated "shadcn's own chart primitives" (i.e. shadcn's `chart.tsx`, built on Recharts) specifically so charts would share the same `--chart-1..5` token system as the rest of the theme. Checked the original plan file (`~/.claude/plans/flickering-wandering-hejlsberg.md`) directly — it has zero mentions of charts at all, so this was a Stage-0-session inference, not a hard requirement from planning. The hand-rolled SVG built in §3.7 still draws from the same token system (§4 decision 13) — the "one token system" goal is met — but it's a genuinely different implementation choice (no Recharts) than what that earlier note anticipated, made without having read it at the time. Two real environment problems surfaced immediately — both would have silently produced confusing failures in every later slice if left unfixed, not just cosmetic:

- **`server-only` throws outside Next's own bundler.** The package's default export condition throws unconditionally ("This module cannot be imported from a Client Component module") — Next resolves it to a genuine no-op via the `react-server` exports condition specifically for server code, which plain Vitest never sets. Considered setting that condition globally in the Vitest config, but rejected it: React itself branches behavior on `react-server` too, so a global flip risked silently changing how component tests render, for a fix that only one package (`server-only`) actually needs. Found on the very first real component test (`DocumentTypeSelect`, written in §3.10); fixed once, centrally, in `test/setup.ts` (an explicit `afterEach(() => cleanup())`) rather than per test file.

- The document-type selector sets the type applied to the *next* upload action, not per already-queued item. A `.zip` can only carry one type anyway (a real backend constraint); for multiple separate files this keeps the UI simple rather than building per-row type editing that wasn't asked for. If a user wants two different types in one session, they change the selector between drops.
- A `.zip` batch's queue item shows the immediate accepted/rejected breakdown from the upload response as-is, but doesn't live-poll each individually-accepted sub-job — that's Results/History's job (Stage 4/5), not the upload page's, per `queue.ts`'s own doc comment on `batchResult`.
- No byte-level upload progress bar. `fetch`-based uploads (used throughout this app, including `apiFetch`) don't expose upload progress the way `XMLHttpRequest` does; the queue shows a spinner-style "Uploading…" state instead of a percentage.

### 3.11 Stage 3 bug fix — "Maximum update depth exceeded" on upload

The user manually ran both apps in a real browser (per §3.10's own plan) and hit a real crash uploading a document — the exact class of bug §3.10's own tests couldn't have caught, since it's a pure client-side render loop, invisible to every verification method available in this environment (curl included). Told explicitly to diagnose root cause, not patch superficially, and to determine whether it was effect dependencies, unstable callback identities, or unnecessary reducer dispatches.

**Diagnosis.** Traced the real data flow: `PolledUploadQueueItem`'s effect (`useEffect(() => { if (data) onStatusUpdate(data); }, [data, onStatusUpdate])`) called `onStatusUpdate` on every poll — but `onStatusUpdate` was a *fresh closure on every render*, at two compounding levels: `UploadQueueList` rebuilt a per-item wrapper (`(job) => onStatusUpdate(item.id, job)`) and `UploadWorkspace` rebuilt the dispatch call itself, both inline, both every render. Combined with `uploadQueueReducer`'s `job-status-updated` case unconditionally building a new array via `.map()` regardless of whether the incoming job data actually differed from what was already stored, this is the textbook shape of the bug: effect fires → dispatch → new array reference (even when nothing changed) → re-render → callback identity changes → effect fires again. Confirmed this is real, not just plausible, by temporarily instrumenting the reducer directly (a throwaway `console.log` inside it, removed before committing) and counting invocations during a sustained "job stuck at the same status" scenario: significantly more `job-status-updated` dispatches fired than real polls could justify (roughly 1.75x with a single item, exactly 2x under `React.StrictMode` — matching its documented double-invocation behavior, not a sign of anything additional — and scaling linearly, not multiplicatively, with a second simultaneously-polling item).

**What didn't reproduce, and why that's stated plainly rather than hidden**: tried to reproduce the literal "Maximum update depth exceeded" crash in an integration test — five variations (a bare re-render loop, `React.StrictMode`, freshly-varying poll responses to defeat React Query's default structural sharing, two simultaneously-polling items) — none crossed React's actual update-depth threshold inside this jsdom/Vitest environment, despite the underlying redundant-dispatch pattern being real and directly measured. Rather than force a fragile, environment-sensitive repro (or worse, quietly claim one that doesn't actually prove anything), the regression tests target the *precise, deterministic property* that has to hold instead — see below.

**Fix — two parts, one primary**:
1. **(Primary, directly satisfies the user's stated goal)** `uploadQueueReducer`'s `job-status-updated` case now returns the exact same state reference — no new array, no new item object — when the incoming job's `status` and `errorMessage` match what's already stored for that item (or when the target id doesn't exist in the queue at all). `useReducer` only bails out of scheduling a re-render when the *identical* reference comes back; returning an equal-but-new array every time (the previous behavior) meant a job legitimately sitting at one status across many polls never gave React a chance to stop.
2. **(Secondary, addresses the callback-identity contributing cause directly)** Stopped constructing a new `onStatusUpdate` closure on every render at two separate levels. `PolledUploadQueueItem` now takes `onStatusUpdate: (id, job) => void` and curries `item.id` itself (a prop it already has) instead of `UploadQueueList` pre-currying it into a fresh per-item closure every render; `UploadWorkspace` wraps its dispatch call in `useCallback` keyed on `queue.dispatch` (stable — `useReducer`'s dispatch never changes identity), not the whole `queue` object (a fresh reference every render, which would have defeated the memoization).

Both matter: the reducer fix is what makes the crash-driving cascade actually *stop* once started (the semantically correct, primary fix); the callback fix means the effect doesn't fire more than necessary in the first place, which was real, measured, wasted work independent of whether it happened to cross a crash threshold.

**Regression tests** (`features/upload/queue.test.ts`): dispatching `job-status-updated` with status/errorMessage unchanged returns the exact same array reference (`toBe`, not `toEqual` — reference identity is the entire point); dispatching with only `errorMessage` different still returns a new reference (confirms the fix doesn't silently swallow real changes); dispatching for an unknown id also returns the same reference (tightens existing no-op coverage to check identity, not just value equality). `components/upload/UploadWorkspace.test.tsx` keeps an integration-level sanity test (renders the real composed tree, sustained identical-status polling, asserts no throw) — explicitly documented in its own comment as a sanity check, not the primary proof, given the reproduction difficulty above.

**Verification**: full workspace `typecheck`/`lint`/`test` green (94 backend + 94 frontend — 4 new tests). Re-ran the real curl-based `/upload` check (fresh signup, real backend + Supabase) to confirm no server-rendering regression — but stated plainly that this cannot verify the actual fix, since the bug is a pure client-side render-loop with no server-rendered signature at all. Asked the user to confirm in their own browser, where they originally found it — that's the only real verification available for this specific class of bug in this environment.

**Closed the loop**: the user re-tested in a real browser afterward and confirmed it directly — uploaded a document, no more "Maximum update depth exceeded," no React warnings in DevTools, upload completed and polling behaved correctly. This is the actual, authoritative verification for this bug; everything above it (the reducer-level reference-equality tests, the curl check) was the closest available substitute until this confirmation landed.

### 3.15 Architecture redesign, Part 1 — Persistent document storage

Framed explicitly by the user as intentional architecture evolution, not a bug fix: migrate the original uploaded file from session-only browser memory to real backend-persisted storage, so Results/History/Dashboard/any future review screen can always retrieve it, not just the tab that did the upload. Planned together with two other parts (Part 2, §3.16, and a file-lifecycle design that was later absorbed into a larger redesign, §3.17) via Plan Mode; two sequencing questions were resolved via `AskUserQuestion` before implementation: plan all three parts together but implement Part 1 first, and — for the eventual delete workflow — soft-delete job rows, hard-delete only the underlying file.

**Storage & schema**: migration `0011_document_storage.sql` — a private Supabase Storage bucket (`documents`, `public: false`) created via SQL (`insert into storage.buckets`), not the dashboard, so it's reproducible and versioned like everything else in `supabase/migrations/`; `document_jobs.storage_path text`, nullable (null means no file persisted — predates the migration, or the non-fatal upload below failed); a `storage.objects` RLS `select` policy scoped by `(storage.foldername(name))[1] = current_organization_id()`, matching the object path convention (`{organizationId}/{jobId}/{fileName}`) — defense-in-depth only, since the actual access path is entirely backend service-role, same model as `document_jobs` itself (ADR 0005).

**Backend**: new `services/storage.service.ts` — `buildStoragePath`, `uploadDocumentFile`, `createSignedPreviewUrl` (1-hour expiry), `deleteDocumentFile` (implemented here, unused until Phase 2 of the review-workflow redesign, §3.17/§9) — all thin wrappers over `supabaseAdmin.storage.from(bucket)`, needing zero new credentials since the existing service-role client already covers Storage the same way it covers every other table. `documents.service.ts`'s `processSingleDocument` and `processZipBatch` both upload the original file to Storage right after creating the "pending" job row, **deliberately non-fatal**: a storage hiccup is caught, logged, and the flow proceeds straight to Azure submission regardless — `storage_path` simply stays `null`, and the preview UI already has an honest "unavailable" state for exactly that case. New route `GET /jobs/:id/preview-url` → `{url: string | null}`, deliberately a separate endpoint from the job status DTO rather than a field on it — embedding a signed URL in `JobDto` would mean generating one on every routine status *poll* while a job is still processing, when there's nothing to preview yet.

**Frontend**: `use-document-preview.ts` rewritten around a `useQuery` against the new endpoint. Decision order: a resolved signed URL always wins when present (the persisted file is the real source of truth now); the session cache (`preview-cache.ts`, otherwise unchanged) is downgraded to a fast-path/fallback only — an instant render for the tab that just uploaded, while the signed-URL fetch is in flight, or a last resort if server-side storage genuinely failed. **A real gap found and fixed proactively while implementing this, not present in the original plan**: without care, the hook would return `unavailable` both while the signed-URL query was still loading *and* once confirmed empty — meaning a reloaded or History-opened job would flash "Preview unavailable" for a moment before its real preview arrived. Fixed by adding a `loading` variant to `DocumentPreviewSource` (now `loading | session-blob | remote-url | unavailable`, up from three), using TanStack Query's `isPending` specifically to distinguish "don't know yet" from "confirmed nothing." `DocumentPreviewPanel` gained a matching skeleton state; its "unavailable" copy was updated to no longer claim the file is session-tab-only, since that's no longer true for anything uploaded after this migration.

Pre-existing jobs (uploaded before this migration) have `storage_path = null` permanently — there's no original file left to backfill — and fall back to session-cache-or-unavailable exactly as before; stated plainly rather than silently glossed over.

**Verification**: full workspace `typecheck`/`lint`/`test` green. The user manually verified in a real browser: the uploaded file actually appears in the Supabase Storage bucket; the Results-page preview loads via a real signed URL (confirmed via the `<iframe>`'s `src` in DevTools, not a `blob:` URL); the preview survives a full page reload; the preview also works when the same job is reached via the History table instead of directly after upload — the two specific cases Issue 1 (§3.14) identified as broken.

### 3.16 Architecture redesign, Part 2 — Results-page information architecture

Investigated before writing any code, per explicit instruction, rather than jumping straight to "add a Markdown renderer." Confirmed directly from source: `result_json` is Azure's entire `analyzeResult` response, stored verbatim and untyped — `paragraphs[]`, `tables[]`, and `pages[]` (word/line bounding boxes) all arrive from Azure and are all persisted in full, but the frontend has only ever read two things out of it: `documents[].fields` (feeding `DocumentFieldsTable`, for the three field-shaped types) and the flat `content` string (feeding `DocumentRawContent`, for all four types). `generic` documents have no `documents[].fields` at all.

Weighed three options for the raw-content panel's canonical representation: (a) render Azure's own Markdown `content` properly; (b) bypass `content` and reconstruct a custom viewer directly from `paragraphs[]`/`tables[]`, which — unlike the flat string — carry `role` (title/sectionHeading/etc.) and bounding regions, real future value for a positional "click a field, see it highlighted on the source" review UI; (c) something else. **Rejected (b) explicitly for this pass**: Azure's own Markdown conversion already does the reading-order paragraph/table interleaving correctly (merging by span offset) — reimplementing that by hand is exactly the work `outputContentFormat=markdown` (§3.14) was already requested to avoid; there is no live Azure response sample anywhere in this repository to validate a hand-built reconstruction against; and nothing is actually lost by deferring it, since the full untouched payload stays persisted in `result_json` regardless of which rendering approach runs today — a future structured/positional viewer remains just as buildable later. Chose (a).

**A second, real bug surfaced by this investigation, not previously noticed**: `DocumentResultsView` was unconditionally rendering `DocumentRawContent` whenever `content` was non-null, for *all four* document types — meaning invoice/receipt/identity_document jobs were showing their fields table *and* a full raw-text dump at equal visual prominence, un-collapsed. This directly contradicted `documents.strategy.ts`'s own code comment, which claimed those three types' content "isn't surfaced in the UI." The comment was simply stale; the behavior was real and needed fixing regardless of what the comment said.

**Implementation**: added `react-markdown`+`remark-gfm`+`@tailwindcss/typography` (none previously installed). `DocumentRawContent` gained a `format: "markdown" | "text"` prop — the Markdown pipeline (inside a `prose prose-sm dark:prose-invert` container) applies only when `format === "markdown"`; the `"text"` path keeps the exact prior preformatted/monospace rendering unchanged. This split matters for correctness, not just presentation: only `generic` documents actually receive Markdown from Azure (§3.14) — running the other three types' plain OCR text through a Markdown parser risks misinterpreting incidental characters (a line starting with `"- "`, a stray `#`/`_` in an address or ID number) as formatting instead of literal content. A new `extract-fields.ts#isMarkdownContent(documentType)` mirrors the backend's own per-type routing table (`documents.strategy.ts`) to decide which format applies — hand-kept-in-sync with a dated comment, the same established convention this file already uses for `DOCUMENT_TYPES` itself. `react-markdown`'s default behavior never renders raw HTML embedded in the source as live elements (no `rehype-raw` was added), confirmed with a dedicated test — relevant since Markdown content here originates from a scanned document, not a trusted author. Fixed the real bug above by collapsing `DocumentRawContent` behind a native `<details>/<summary>Show raw extracted text</summary>` whenever structured fields also exist, leaving it at full prominence only for `generic` (no fields at all) — no new dependency, consistent with this codebase's native-element-over-new-primitive precedent elsewhere.

**Verification**: full workspace `typecheck`/`lint`/`test` green. The user manually verified in a real browser: a `generic` document's raw-content panel now renders actual headings and a bordered table instead of literal `#`/`|` characters; an invoice/receipt/identity_document's raw content is now collapsed behind "Show raw extracted text," with the underlying text itself unchanged once expanded.

### 3.17 Document review workflow redesign — Phase 1 (review, corrections, confirm/reject)

After Part 2 (§3.16) was confirmed, the user reported the remaining gap wasn't a rendering problem: the Documents list only exposes a "View" action, and the Results page is read-only with no way to correct a wrong extraction or record that a human reviewed it. Requested a full architecture proposal — document review, field editing, confirmation/rejection, Storage lifecycle, future audit/history, multi-document-type support — before any code, explicitly not a quick fix.

Investigated the current architecture directly (routes, schema, repository/service functions, existing frontend patterns — `DropdownMenu` already used elsewhere, no `Dialog`/`AlertDialog` primitive existing yet, `react-hook-form` used only for the two auth forms) via Plan Mode, using a Plan subagent to draft and independently verify a proposal against real source before it was presented. Two decisions were confirmed via `AskUserQuestion` before finalizing the plan:
- **Field corrections get a full, per-edit audit-history table**, not a simpler "latest value only" column on `document_jobs` — chosen over the lighter option specifically because the user named future audit/history as a first-class requirement, not an afterthought, and the lighter option would have permanently lost any record of an intermediate edit once superseded by a later one.
- **Any organization member — not just the uploader or an owner/admin — can edit fields, save corrections, confirm, or reject.** Matches how viewing already works (org-scoped, not uploader-scoped) and supports the realistic case where the person who uploaded a batch isn't the person who reviews it. Destructive actions (remove the original file, delete the document) stay restricted to the uploader or an owner/admin — the already-agreed model from the earlier file-lifecycle design, which this larger redesign absorbed as its own later phase rather than building in parallel.

The approved plan sequences three phases: **Phase 1 — the review workflow itself (this section)**; Phase 2 — file lifecycle (remove file / delete document, absorbing the earlier design); Phase 3 — Documents-list fast-follow (a delete/remove-file action menu, a review-status badge). Only Phase 1 is built so far.

**Schema** (`0012_document_review.sql`): a new `document_review_status` enum (`unreviewed | confirmed | rejected`) and `review_status`/`reviewed_by`/`reviewed_at` columns on `document_jobs` — deliberately a completely independent lifecycle from the existing `status` column, which tracks Azure processing and directly drives the frontend's polling logic (`poll-schedule.ts`); conflating the two would mean either inert enum values that never affect polling, or breaking the polling contract outright. A two-column CHECK constraint (`review_status = 'unreviewed' or status = 'completed'`) backs the same rule the service layer already enforces, as defense-in-depth, not the primary mechanism. A new `document_field_corrections` table — one row per field-edit event (`field_name`, `previous_value`, `new_value`, `edited_by`, `edited_at`), RLS-enabled with a same-org `select` policy expressed as a subquery against `document_jobs` (this table carries no `organization_id` column of its own). `reviewed_by`/`edited_by` both use `on delete set null`, not `on delete cascade` like `document_jobs.user_id` — these columns record mere involvement ("who last touched this"), not ownership, so removing an unrelated profile must never silently delete jobs it happened to review.

**A non-obvious rule, load-bearing for the whole feature meaning anything**: saving new corrections on a job that's already `confirmed`/`rejected` automatically resets it to `unreviewed` (clearing `reviewed_by`/`reviewed_at`) — otherwise a "Confirmed" badge could keep describing data a later, unreviewed edit has already superseded. This reset only fires on the standalone "save without deciding" path (`PATCH .../corrections`); confirming or rejecting *with* an accompanying corrections payload sets the final status directly in the same write, with no separate reset-then-set round trip. Writes are ordered specifically so a partial failure never lands in a state that claims something the data doesn't actually back up — full reasoning is in the code's own comments (`documents.service.ts`), not just here.

**Backend**: `documents.repository.ts` gained `listFieldCorrections`/`insertFieldCorrections`; `documents.service.ts` gained a small field-value-lookup helper mirroring `extract-fields.ts#extractDisplayValue` on the frontend (deliberately duplicated rather than moved into `@tnda-ai/shared` — that package is scaffolded but still completely unimported and not even declared as a dependency of either app; wiring it up for real, for one ~10-line function, was judged disproportionate — the same proportionality call already made twice this session for `DOCUMENT_TYPES` and `isMarkdownContent`), plus `getFieldCorrections`/`saveFieldCorrections`/`confirmDocumentReview`/`rejectDocumentReview`. Four new routes: `GET`/`PATCH /jobs/:id/corrections`, `POST /jobs/:id/confirm`, `POST /jobs/:id/reject` — all four guard `status === 'completed'` (there's nothing to review or correct before that), throwing `ConflictError` otherwise, this codebase's first real use of that error class outside auth. `GET .../corrections` is a separate endpoint, not fields folded onto the shared `JobDto` — computing "effective value per field" needs an extra query against the new table, cheap for one job but not something every row of a 100-item `GET /documents` page should pay for (or dishonestly fake as empty); `reviewStatus`/`reviewedAt`/`reviewedBy` *do* live on the base `JobDto`, since they're plain, already-fetched columns with no such cost.

**Frontend**: `extract-fields.ts` gained `extractEffectiveFields`, merging Azure's originally-extracted fields with the corrections endpoint's effective-value map — `isCorrected` compares the *current* value against the original, not "does any correction exist for this field," so a field corrected and then manually reverted back to Azure's original value correctly reads as uncorrected again. `DocumentFieldsTable` is now always directly editable — no separate view/edit-mode toggle, since editing is this screen's actual purpose now, not an occasional action — showing "Edited" in place of a now-inapplicable Azure confidence score once a field's displayed value differs from its original. `DocumentResultsView` gained a full-width action bar above its existing two-column layout: a review-status badge, "Save corrections" (dirty-gated, absent entirely for `generic` documents with nothing to correct), "Confirm," "Reject," with inline error feedback if any action fails. `react-hook-form` was deliberately not reused here despite being the existing pattern for the two auth forms — the field set is dynamic and Azure-determined (a different, variable-length list per document), and a corrected value has no real validation rule to enforce beyond "a replacement string," so a plain `useState` draft was judged sufficient without the added surface of a form library built for schema-driven validation against a fixed field set.

**One lint-driven fix worth recording as a pattern, not just a fix**: resetting the local edit draft whenever `jobId` changes was first written as a `useEffect` calling `setState` — `react-hooks/set-state-in-effect` correctly flagged this as avoidable, unlike Stage 4's blob-URL case (§3.12, §4 decision 27), which genuinely needs an effect for its paired resource-cleanup semantics. This one doesn't: fixed using React's own documented "adjust state during render" pattern (a `draftJobId` comparison directly in the render body, resetting the draft synchronously within the same render pass) rather than another scoped disable comment — the correct fix this time was structural, not a suppression.

The user manually verified in a real browser: editing a field and saving without confirming persists correctly across a reload while the review status stays "Unreviewed"; confirming a document and then editing a field again correctly reverts its status to "Unreviewed" automatically; reject behaves the same way; `generic` documents correctly get confirm/reject with no field-editing UI; no console errors or React warnings throughout.

### 3.18 Document review workflow redesign — Phase 2 (file lifecycle)

The second of the three approved phases (§3.17) — remove the original file, or delete the whole document — absorbing the file-lifecycle design agreed before Phase 1 even started. Followed the same TDD-first workflow and wait-for-manual-verification discipline as every phase before it.

**Schema** (`0013_document_soft_delete.sql`): a single nullable `deleted_at timestamptz` on `document_jobs`. Kept as its own migration rather than folded into `0012`, even though both just add columns to the same table — this one ships alongside Phase 2's own independent piece of work, the same "migration ships with the code that uses it" reasoning already behind 0010/0011 staying separate.

**Repository layer**: `listDocumentJobsForOrganization` and `getDocumentJobForOrganization` (`documents.repository.ts`) both gained a `.is("deleted_at", null)` filter — a soft-deleted job now disappears from the Documents list and stops being reachable through the same lookup every other Phase-1 endpoint (`getJobStatus`, `getDocumentPreviewUrl`, corrections, confirm/reject) already routes through, so it goes invisible everywhere at once, not just off one list. Deliberately **not** added to `getMonthlyPagesUsed`/`getDocumentsSubmittedSince` (`organization.repository.ts`) — quota counts what was submitted in a billing period, not what's currently visible, and this was the one place the plan explicitly flagged as easy to get wrong by reflexively adding the filter everywhere `document_jobs` is queried; verified correct, not just remembered as a rule. A new `getDocumentJobForOrganizationIncludingDeleted` — same id+org-scoped lookup, deliberately skipping the `deleted_at` filter — exists specifically for the two delete-related service functions below, so a *second* `DELETE /jobs/:id` call on an already-deleted job can still find the row, re-check permissions, and cleanly no-op instead of 404ing (real idempotency, not just "doesn't blow up twice").

**Backend service functions** (`documents.service.ts`): a new private `assertCanManageFile(job, userId, role)` throws `ForbiddenError` unless the caller is the job's own uploader or an org `owner`/`admin` — the first real usage anywhere in this codebase of `ForbiddenError`, defined in `utils/errors.ts` since early in the project but never thrown until now. `removeDocumentFile(organizationId, jobId, userId, role)` hard-deletes the Storage object (`storage.service.ts#deleteDocumentFile`, implemented in Part 1, unused until now) and sets `storage_path = null`; idempotent — a job with no `storage_path` is a no-op. `deleteDocument(organizationId, jobId, userId, role)` soft-deletes the job and removes its file at the same time (leaving orphaned bytes once a job is hidden from every view serves no purpose); idempotent on an already-deleted job.

**A deliberate asymmetry in how the two functions handle a Storage failure**: inside `deleteDocument`, the file-removal step is non-fatal — caught, logged, the soft-delete proceeds regardless, same tier of caution as Part 1's original upload-time write, since the document disappearing from view is the primary effect and shouldn't be blocked by a transient Storage hiccup. `removeDocumentFile` does the opposite on purpose — a failure there propagates, and `storage_path` is left untouched, since removing the file *is* that endpoint's entire purpose; silently nulling the path while the file might still be there would create a permanently orphaned, unreferenced object with nothing left pointing to it.

**New endpoints**: `DELETE /jobs/:id/file` → the updated `JobDto` (the job stays fully visible, matching confirm/reject's existing response shape). `DELETE /jobs/:id` → just `{jobId}` — deliberately not a full `JobDto`, since once deleted the job isn't retrievable through any other endpoint, so there's nothing else meaningful left to return.

**Frontend**: added the `alert-dialog` shadcn primitive via the actual CLI (`npx shadcn@latest add alert-dialog`), not hand-written, so it matches the project's existing radix-nova conventions exactly (the same pattern `dropdown-menu.tsx` already used) — confirmed it touched only that one new file (it also tried to regenerate `button.tsx` but skipped it, content already identical). First `Dialog`/`AlertDialog`-family primitive anywhere in this frontend; previously only `sheet.tsx` existed (the sidebar's mobile drawer), and no confirm-before-destructive-action pattern existed at all. `features/documents/hooks.ts` (not `features/results/hooks.ts`) gained `useRemoveDocumentFile`/`useDeleteDocument` — placed there deliberately, since Phase 3's Documents-list actions need the exact same two hooks, not just the Results page. `useRemoveDocumentFile` invalidates `["document-preview-url", jobId]` on success (the one piece of cached data that actually changes — `JobDto` never exposed `storage_path` to begin with); `useDeleteDocument` invalidates `["job-status", jobId]` and `["documents-list"]`. `DocumentResultsView`'s action bar gained "Remove file" (`outline` variant, matching "Save corrections"'s milder treatment) and "Delete document" (`destructive` variant, matching "Reject"'s existing red treatment — both comparably serious), each behind an `AlertDialog` confirmation, visually separated from Save/Confirm/Reject by a thin vertical divider rather than a new row. Confirming "Delete document" navigates to `/documents` afterward (`next/navigation`'s `useRouter`), since the job disappears from view the moment it's deleted. Both new mutations feed into the same inline error `Alert` and combined `isMutating` disable flag Phase 1 already built, extended rather than duplicated.

**A testing-pattern gap this phase had to fill, not follow**: no prior test in this codebase exercised a Radix Dialog/AlertDialog-family component. Worked out that Radix portals dialog content into `document.body` only once opened — genuinely absent from the DOM before that, not rendered-and-hidden — so `await user.click(trigger)` then `await screen.findByRole("alertdialog")` is the correct wait-for-open sequence. A dialog's trigger button and its in-dialog confirm action can legitimately share the same accessible name (a standard, expected UX pattern, not an accident), which needs `within(dialog).getByRole(...)` scoping in tests to disambiguate rather than a bare `screen.getByRole`. Also needed this test suite's first `next/navigation` mock (`vi.mock("next/navigation", () => ({ useRouter: () => ({ push: mockPush }) }))`), since no earlier tested component called `useRouter` directly.

**Verification**: full workspace `typecheck`/`lint`/`test` green — 168 backend + 265 frontend tests (up from 146/250). ### 3.19 Document review workflow redesign — Phase 3 (Documents-list actions) — plan complete

The third and final phase of the approved plan. The Documents list (`DocumentsTable.tsx`, Stage 5) still only had a single "View" link per row, with no way to remove a file or delete a document except by navigating to that document's own Results page first, and no visibility into review status from the list at all. Skipped consciously, not forgotten — would follow the exact same reducer-entry pattern already used for `status`/`documentType` if picked up later.

**No backend changes, no new migration** — unlike every phase before this one, which each touched the backend in some way.

### 3.20 Wave 1 — security, testing, and documentation hardening (2026-08-08)

Between Phase 3 and this session: a full repository audit (delivered as a published Artifact, not reproduced here) and a proposed `docs/document-domain-architecture.md`, written and then explicitly revised against user feedback (Archive modeled as a Retention-axis attribute rather than a linear state; the lifecycle event log scoped precisely, not as a catch-all; a dedicated background-processing architecture contract added ahead of Wave 3). The user then approved **Wave 1 only** from that document's roadmap — closing the audit's already-identified gaps, explicitly *not* touching schema or introducing any Wave 2+ concept (event log, background workers, retry-state, etc.). All six named items are done, grounded in specific findings rather than reinterpreted:

**1. ZIP decompression-bomb protection (`utils/zip.ts`) — the audit's one exploitable-today finding.** `extractZipEntries` previously called `unzipSync` on the whole archive in one call, with no entry-count, per-file, or cumulative decompressed-size limit — a small, highly-compressed archive could exhaust server memory before any check ran. Rewritten to stream the archive through fflate's incremental `Unzip` API instead, feeding input in bounded 64KB chunks (not the whole archive at once — this is what makes a single wildly-compressed entry get caught *mid*-expansion, not only after a giant internal buffer has already been grown to fit it). Three explicit ceilings, chosen relative to the real plan limits (`pro`'s 50MB/file is the largest legitimate case): `MAX_ZIP_ENTRIES` (500), `MAX_ZIP_ENTRY_UNCOMPRESSED_BYTES` (100MB, 2× the largest real per-file limit), `MAX_ZIP_TOTAL_UNCOMPRESSED_BYTES` (300MB). An entry's declared size is checked upfront where the header provides one (cheap, fails fast on an honest-but-huge declaration), and the real, running decompressed byte count is independently tracked and enforced as data actually streams out — so a header that lies about size (or never declares one, the "streaming-created archive" case) is caught exactly the same way as one that's honest. A cheap upfront End-Of-Central-Directory signature check (mirroring what `unzipSync` itself did) preserves the existing "not a valid zip" rejection for garbage input, since the new streaming reader has no other reason to notice a missing EOCD on its own. `zip.test.ts` (new, 10 tests) proves this at real scale — highly-compressible (all-zero) fixtures keep the *compressed* test archives tiny and fast to build, while genuinely exceeding the real limits when decompressed, including one adversarial case (fflate's streaming `Zip` writer, not `zipSync`) specifically constructed so the entry's size is *not* known upfront, proving the incremental byte-counting guard works on its own, independent of the cheap header check.

**Consistency model, decided explicitly rather than assumed**: this backend talks to Postgres exclusively through PostgREST (`supabaseAdmin.from(...)`), which has no client-side multi-table transaction primitive; true atomicity between a `document_jobs` write and its event row would need a new write-RPC pattern this codebase has never used for a write (its four existing RPCs are read-only aggregations). A new wave, explicitly scoped by the user in two stages: first a full architecture design review (background processing — job claiming, worker crash recovery, retry semantics including revisiting §3.21's open 429 item, idempotency, the Azure operation lifecycle, polling architecture, queue-vs-database, worker design, concurrency, the state model, event-log integration, failure modes, tenancy, observability, testing strategy, deployment impact) with explicit instruction **not** to implement anything — reviewed fresh from source (`documents.service.ts`, `documents.repository.ts`, the Azure adapter, all migrations, the Dockerfile, CI, `package.json`/`turbo.json`), not from memory. Not done in this phase, by explicit instruction: no worker process, no Azure submission/polling moved, no HTTP behavior changed, no retry execution beyond the schema needed to prove claiming works.

**Azure idempotency investigation, done before writing any code, per explicit instruction**: fetched Microsoft's actual REST API reference for the exact API version this codebase targets (`2024-11-30`) and confirmed there is no idempotency key, client-request-id-for-dedup, or any other deduplication mechanism on the `:analyze` endpoint — every call creates a fresh, server-generated operation, unconditionally, with no way to later discover an orphaned one. **The RPC**: `claim_or_renew_document_job(p_worker_id, p_lease_seconds, p_max_retries)` — one function handling both renewal (of a claim the caller already holds) and fresh claiming (via `SELECT ... FOR UPDATE SKIP LOCKED`), with a failed-and-retryable row's retry transition folded into the same atomic claim statement. Full reasoning in the new **ADR 0012**.

**Two real defects found and fixed during this phase's own independent review, before the migration was ever applied — exactly what that review step exists to catch**:
1. The original `claimed_by` design implicitly assumed one id per worker *process*; tracing through what happens when `WORKER_CONCURRENCY > 1` (a later phase's own approved default) showed a worker holding several jobs at once would have its renewal call silently renew *all* of them instead of claiming a new one. Fixed by documenting explicitly (on the column, the function, and the repository wrapper) that `p_worker_id` identifies one claim *slot*, not a process — before any worker code exists to get this wrong.
2. The migration's original security comment claimed the RPC was "not granted to `authenticated`" by simply never writing a `GRANT` — which is not how PostgreSQL functions work (`EXECUTE` is granted to `PUBLIC` by default on creation) and, empirically, not how *this* Supabase project works either (a project-level default-privilege rule separately grants `EXECUTE` directly to `authenticated`/`anon`/`service_role` on new functions, independent of `PUBLIC`). Confirmed by querying `information_schema.routine_privileges` against the real database mid-review — the omission-only approach would have left the RPC callable by any signed-in end user, a real cross-tenant vulnerability given the function is `security definer` and claims across every organization by design. Fixed with two explicit `REVOKE` statements (`PUBLIC`, then `authenticated`/`anon` by name); `service_role`'s own grant was confirmed, empirically, to survive both revokes.

**Tests**: 3 new unit tests (`documents.repository.test.ts`, mirroring `organization.repository.test.ts`'s existing RPC-mocking convention exactly) covering the wrapper function's call shape, the "returns null when nothing available" case (not an error), and the AppError-on-failure path. ### 3.23 Wave 3 Phase 2 — background processing worker (2026-08-08)

A second design review, worker-specific this time (byte retrieval without the original request's in-memory bytes, worker concurrency defaults, Azure 429/`Retry-After` handling, fencing discipline for every worker-originated write, claim release on terminal transitions, the one new lifecycle event this phase needs, and the `GET /jobs/:id` behavior change), approved with **twelve explicit decisions locked in advance**. Before writing any code, a required **three-area consistency review** checked: exact `retry_count` semantics (attempts vs. retries, and whether `maxRetries=3` produces exactly the intended number of submission attempts); every point a worker can lose its lease epoch, and whether a stale worker could still write afterward; and whether an exhausted retryable failure reliably becomes terminal and unclaimable. All three checked out consistent with Phase 1's actual RPC — no schema/RPC change was needed. Full reasoning in the new **ADR 0013**; implemented in the exact 9-step order the approved plan specified (repository primitive → retry-policy pure functions → service-layer processing functions, unit-tested but unwired → migration → worker skeleton → wire the worker to the real service functions → remove the synchronous HTTP submission path → full regression pass → docs).

**The one real design gap this phase's own consistency review found, closed before implementation began**: the claim RPC's renewal call and a fresh claim are the same function — a "renewal" can silently fall through to claiming a genuinely *different* job if this worker slot's own lease was lost to a reclaim elsewhere in between. The original design implicitly assumed a renewal always either confirms the same job or returns nothing. The worker's claim loop (`src/worker/claim-loop.ts#runClaimSlot`) now routes every response from a claim call — fresh or renewal — through the identical adoption path, never assuming a "renewed" result is still the job it thinks it's tracking.

**The worker** (`apps/backend/src/worker/`): a dependency-injected claim loop (`claim`/`submit`/`poll`/`sleep`/`now`/`log` all injected, so concurrency/timing/shutdown logic is unit-testable with zero real timers or a real database) wired to two new epoch-gated service functions — `submitClaimedJobForProcessing` (downloads the file from Storage and re-inspects it, since the worker has no in-memory bytes from the original HTTP request; a missing `storage_path` is terminal and non-retryable, never retried) and `checkClaimedJobProgress` (mirrors the old polling logic, but epoch-gated and claim-releasing). Every write either function makes goes through a single new repository primitive, `updateDocumentJobIfEpochMatches` — `UPDATE ... WHERE id = $1 AND lease_epoch = $2`, returning `null` (not an error) on a zero-row match, which the caller must treat as "stop touching this job," never retried. Terminal writes clear `claimed_by`/`claimed_at`/`lease_expires_at`; `lease_epoch` itself is never reset, so it keeps serving as a fencing/history token across a job's entire retry lifetime, not just one attempt — Phase 1's ADR 0012 had explicitly left claim-release for a later phase to build; this is that phase.

**Azure `429` is now retryable, resolving Wave 2's own previously-open decision item (§3.21 decision 61)**: a 429 surviving `beginDocumentAnalysis`'s existing internal retry-with-backoff represents sustained rate-limiting, not a rejected request. `Retry-After` (when Azure sends one) is captured into `AzureServiceError.details.retryAfterSeconds` and honored verbatim by the backoff calculation; otherwise, retry delay is exponential with jitter (30s base, ×2 per retry, capped at 10 minutes), computed from the job's pre-failure `retry_count` — matching exactly what the claim RPC itself checks for eligibility.

**The one new lifecycle event Phase 1's ADR explicitly deferred**: `processing_retried` (migration `0017`, a single `ALTER TYPE ... ADD VALUE`), fired exactly once per retry attempt — on a fresh claim with `retry_count > 0`, never on a renewal. Claiming/renewing/lease-expiry stay out of the domain event log, unchanged from Phase 1's own operational-vs-domain boundary.

**`GET /jobs/:id` is now a pure database read — the one change in this phase to existing HTTP behavior.** `POST /documents` no longer submits to Azure synchronously either: the upload path persists the job as `pending` and returns immediately (still `202`, still the same response shape — `BatchFileResult.status` still reports `"processing"` for an accepted batch file, meaning "accepted into the pipeline," not the job's literal DB status, a deliberate documented distinction, not a contract change). The worker is now the sole path that ever polls Azure or writes a processing/completed/failed transition.

**A real bug found and fixed during this phase's own implementation** (not anticipated by either design review): the claim loop deliberately checks `shouldContinue()` (the shutdown signal) only while idle — checking it while a job is held would mean either abandoning in-flight work on shutdown, or a second, weaker shutdown rule just for that branch. Running the test suite written against this design reproduced a genuine out-of-memory crash: a test whose mocked `poll` never returned a terminal status meant the loop never went idle, so the shutdown check was never re-consulted and the loop ran forever. Not a flaw in the idle-only-check design itself (a real Azure operation does eventually resolve) — the test fixture's own mock needed to terminate for the test to be a meaningful, terminating test at all. Fixed by making the mock terminate, not by weakening the loop's shutdown semantics. A second, independent bug in the same pass: the graceful-shutdown test's own fake `shouldContinue` closure mutated its state *before* returning on its first call, so it could never actually return `true` — fixed by capturing the return value ahead of the mutation.

**Frontend verification, done by a fresh code trace across ten files, not assumed**: every place the frontend branches on job status (the polling-continuation logic, the upload-queue's "still working" gate, and both status-badge display maps, the latter two exhaustively typed over the full status union so a missing case would already be a compile error) already treats `pending` identically to `processing` for behavior. Zero frontend changes were needed or made.

1. **The worker crashed entirely on one unexpected polling exception.** A live worker claimed a pre-existing, unrelated leftover fixture row (from an earlier debugging session) whose `azure_operation_id` no longer resolved; `checkClaimedJobProgress` had no try/catch around the Azure call (safe in the old HTTP-request shape only because Elysia's error middleware caught it there — no equivalent exists in a worker process), so the exception killed the entire process, including every other slot's in-flight work. **Fixed**: `runClaimSlot` now catches unexpected exceptions per-iteration, logs full context, clears in-memory tracking, and attempts no write — the row simply recovers via Phase 1's existing lease-expiry mechanism. `worker/index.ts` switched from a bare `Promise.all(slots)` to a new `runSlots` helper (`Promise.allSettled` + rejection logging) so one slot's failure can't cascade into killing healthy siblings.

### 3.30 One-command local dev: `pnpm dev` now also starts the worker (2026-08-08)

Follow-up to §3.28's "left open" question — the user chose to actually wire the worker into `pnpm dev` rather than document-only, reversing ADR 0013's original "not wired into the Turbo dev fan-out" decision deliberately and explicitly this time, not silently.

**Investigated first**: Turborepo's `turbo run <task>` runs, in parallel, whatever script literally named `<task>` each package defines, skipping packages that don't have one — exactly how `pnpm dev` already ran both `apps/frontend#dev` and `apps/backend#dev` together. `apps/backend/package.json` already had `worker:dev`/`worker:start` scripts (both left completely untouched); the only piece missing was a matching `turbo.json` task entry and a second task name on the root `dev` script.

**A real blocker found live, not assumed**: the obvious choice — orchestrating `worker:dev` (the `--watch` variant, for parity with the API's own hot-reloading `dev` script) — was tested end-to-end (start `pnpm dev`, send it a real `SIGINT`) and failed the explicit "shuts down cleanly" requirement: the worker's own graceful-shutdown logic completed correctly (`"all slots drained, exiting"` printed), but the underlying `bun --watch` process never actually exited on its own — Turbo waited, logged `"1 task shutting down..."` repeatedly, and after ~50s had to forcibly kill it (`"Graceful shutdown timed out. Force killed Turborepo tasks: @tnda-ai/backend#worker:dev"`). Confirmed via web search to be a known upstream Bun bug (`oven-sh/bun#13539` and related issues — `--watch` mode's file-watcher keeps the process alive after the script's own top-level work finishes, unrelated to this codebase's own signal handling, which is correct). **Fix**: orchestrate `worker:start` (no `--watch`) instead — verified live to exit cleanly and quickly (~11s total wall time including full startup, no forced kill) on the identical `SIGINT` test. Trade-off, stated plainly: worker code changes don't hot-reload under the unified command; `bun run worker:dev` (unchanged, still available) remains the way to get that during worker-focused development.

**Changes**: `turbo.json` gained a `worker:start` task entry (identical shape to the existing `dev` task: `cache: false, persistent: true`); root `package.json`'s `dev` script changed from `"turbo run dev"` to `"turbo run dev worker:start"`. Nothing else — `apps/backend/package.json` (both worker scripts), `apps/frontend/package.json`, and every other task (`build`/`typecheck`/`lint`/`test`) are byte-for-byte unchanged; this is purely local-dev orchestration, with no effect on CI, Docker, or any production script.

**Tests**: none — this is process orchestration configuration, not application logic; nothing here is unit-testable, and the project has no existing precedent for testing `package.json`/`turbo.json` scripts directly. Verified entirely through live process-level checks instead (below).

**Verification, all live, not simulated**: `pnpm dev --dry-run` confirmed the exact intended execution plan (`@tnda-ai/backend#dev`, `@tnda-ai/backend#worker:start`, `@tnda-ai/frontend#dev` — every other package/task combination correctly `<NONEXISTENT>`, skipped). A real `pnpm dev` run from the repository root started all three processes with clearly Turbo-prefixed, readable output; a real document was uploaded via the live API and polled to `completed` with a real Azure-extracted result, proving the worker started by this one command actually processes uploads end to end, no second terminal involved. `SIGINT` to the whole process group produced a clean, fast shutdown of all three tasks, confirmed via both the log (no "Force killed" message) and direct process-list inspection. Both standalone worker commands re-confirmed unaffected: `apps/backend/package.json` diff is empty, and `bun run worker:start` run standalone still starts/stops exactly as before. Full monorepo `typecheck`/`lint`/`test` clean.

## 4. Architectural Decisions (what, and why)

1. **Backend is the single source of truth; frontend never queries Supabase directly for application data.** (User decision, §3.4.) Supersedes the original plan's resolution for backend gaps #1/#5 (frontend-side RLS reads for History/stats) — those are now real backend endpoints instead (§8). The one exception, deliberately not a violation of this rule: `@supabase/ssr` for session/cookie management is identity plumbing (the same category as the backend talking to Supabase Auth directly for token verification), not an application-data query.
2. **Session-only document preview, behind a swappable abstraction.** (User decision.) The backend never persists uploaded files; a persistent preview isn't achievable without new infrastructure, and isn't needed for the immediate upload→results flow that matters for v1. Built behind a `DocumentPreviewSource` union type (`session-blob | remote-url | unavailable`) specifically so a persistent backend-provided URL can replace it later without touching any UI component — an explicit requirement, not an implementation nicety. **Implemented in Stage 4** (§3.12): `session-blob` via a module-level `jobId -> File` cache + `URL.createObjectURL`; `remote-url` still has no producer (unchanged — the backend still doesn't persist files); `unavailable` is the real fallback for any job reached outside the immediate post-upload flow.
3. **`@supabase/ssr` hybrid auth session model.** Backend still owns signup/login orchestration (org+profile creation, with rollback) — bypassing it would leave orphaned `auth.users` rows. Immediately after, `setSession()` hydrates an `@supabase/ssr` server client, which then owns cookie/refresh lifecycle. Refresh centralized in `proxy.ts` (Server Components can't write cookies themselves). Logout calls `signOut()` for real server-side revocation, not just cookie clearing. `SameSite=Lax`, deliberately — `Strict` would drop the session cookie on the top-level GET redirect back from Stripe Checkout, silently logging the user out right after they pay.
4. **Hand-written Zod schemas + `AssertExact`, not Eden/openapi-typescript.** Both alternatives were tried and don't work (§3.3) — this isn't a fallback chosen for convenience, it's the only approach that actually functions given the two projects' independent `tsconfig`s and the backend's broken Swagger JSON output. Arguably *stronger* than either alternative would have been: real runtime validation at every call site, not just a compile-time promise.
5. **Keyset (cursor) pagination over offset, for `GET /documents`.** Offset pagination (`.range()`) drifts under concurrent inserts — a real case here, since a batch upload can add rows while someone's paging through their own history. Cursor is on `created_at` alone (no `id` tiebreaker) — a compound cursor would need Supabase's `.or()` raw-filter-string DSL, meaning decoded client-supplied cursor content would be interpolated into a filter *expression* rather than a filter *value*. Accepted trade: two jobs created in the exact same instant could theoretically land on opposite sides of a page boundary — rare enough (each row is a separate awaited round trip) not to be worth the larger attack surface. Cursor is opaque on the wire (base64url); a malformed one is treated as "first page," not an error.
6. **`successRate`/`averageConfidence`/etc. are `null`, never a fabricated `0`, when there's no data to compute them from.** A `0` success rate reads as "100% failure" when the honest state is "no data yet"; `generic` documents (Azure's `prebuilt-layout` model) have no per-field confidence at all, and forcing a `0` there would be a lie, not a default.
7. **Stats' daily-count series is gap-filled server-side, in the service layer**, not left sparse for clients to reconstruct. The Postgres function only returns days with actual activity; a day missing from that result is indistinguishable from "no data at all" to a client that doesn't know the query's internals — filling every day once, in one place, means every consumer gets a complete, chart-ready series.
8. **No history rewrite for the monorepo migration — verified, not assumed.** `git filter-repo` was the first instinct; asked to justify it against a simpler move-and-commit approach, that simpler approach was proven (in a throwaway repo, against a real bare "remote," before touching the real one) to preserve every commit hash unchanged, push as an ordinary fast-forward, and support `git log --follow`/`git blame` correctly across the move. No force-push anywhere in this migration.
9. **`packages/types`/`packages/shared` are scaffolded and workspace-wired, but deliberately left empty.** The backend's schemas are Zod v3, the frontend's are Zod v4 (an already-made, deliberate choice — not an oversight); backend code assumes Bun-only APIs in places. Moving code into a shared package now wouldn't remove the need for the hand-verification work already done, just relocate it. Real future sharing is a *deliberate* decision to make later, not a speculative one to force now.
10. **CSRF is covered by `SameSite=Lax` + all-mutations-are-POST, deliberately, not a token.** `SameSite=Lax` already withholds the cookie on cross-site subrequests; combined with every mutating route being POST, that closes the practical gap without adding a separate mechanism.
11. **No optimistic updates in the frontend, for now — considered per-feature, not a gap.** Checked against every real mutation in the app (upload-queue entries are already transient client-only state; "mark as reviewed" is explicitly local-only since there's no backend field to persist it to yet; a plan change redirects to Stripe and can't be optimistically shown; History has no mutations at all). Recorded so this reads as a considered decision if revisited later.
12. **Call paths are fixed and enforced, not just documented, in the frontend.** Server Components import `services/*.service.ts` directly (in-process); Client Components only reach the same code indirectly through this app's own `/api/*` Route Handlers. Every file under `services/` starts with `import "server-only"` so an accidental Client Component import fails the build instead of silently risking a path to tokens in a client bundle.
13. **Chart color is the `dataviz` skill's validated default (blue), not invented, and validated against this app's real surfaces.** (Stage 2, §3.7.) This theme (`shadcn init`'s neutral base) had never used a real hue before — `--chart-1..5` were unpopulated grays. Rather than eyeball a brand color, used the skill's documented default categorical slot 1 and ran `scripts/validate_palette.js` against this app's *actual* computed card-surface hex in both modes (derived from its `oklch()` tokens, not the skill's own example surfaces) before trusting it. 18. **Incremental TDD, per feature category, is the standing workflow for frontend feature work from Stage 3 onward.** (User decision, §3.9.) Types/contracts → failing tests → minimal implementation → full-workspace verify → next category. Apply this to Stage 4 (Results) and beyond unless told otherwise — it isn't scoped to Upload specifically.
19. **Test boundary is one layer below whatever's under test, never deeper.** (§3.10.) Service tests mock `backendFetch`/`apiFetch`, not `fetch` itself; route tests mock `services/*`, not the services' own internals; component tests mock `apiFetch`, not React Query. Matches the backend's own established testing philosophy (mock the repository layer, not the Supabase client) — re-verifying a lower layer's own correctness in every test above it would be redundant, not more thorough.
20. **Uploads process sequentially, one at a time, never concurrently.** (§3.10, `useUploadController`.) Consistent with the same rate-limiting caution that already drove the polling backoff schedule (§7) — a burst of simultaneous upload requests from one proxying Next.js server is the same category of risk as a burst of poll requests, even though uploads are less frequent than polls.
21. **One `useJobStatus` call per rendered list item (`PolledUploadQueueItem`), not one hook trying to poll N jobs.** (§3.10.) The standard React pattern for "a hook per item in a dynamic list" — hooks can't run inside a loop or conditionally, so each queue item with a `jobId` gets its own component instance and its own independent poll/backoff cycle.
22. **Upload queue state management has zero knowledge of the hooks that talk to the backend.** (§3.10, `features/upload/queue.ts` vs. `use-upload-controller.ts`.) The reducer only knows how to represent and transition queue items; a separate controller hook composes it with `useUploadDocument`/`useJobStatus`. Keeps the reducer trivially testable with plain objects and no network mocking at all.
23. **Document type is chosen per upload *action*, not per queued item.** (§3.10, scope decision.) A `.zip` batch can only carry one type regardless (backend constraint); building per-row type editing for the non-batch multi-file case wasn't asked for and would have meaningfully expanded this slice's scope for a need that hasn't come up yet.
24. **A `.zip` batch's queue item shows its immediate accept/reject breakdown but isn't live-polled sub-job-by-sub-job.** (§3.10.) Tracking potentially many independent per-file polls from the upload page was judged out of scope for Stage 3 — checking on an individual file's outcome after a batch upload is Results/History's job (Stage 4/5).
25. **Any reducer action driven by a reactive/polling effect (not a one-shot event) must explicitly guard against no-op updates and return the exact same state reference when nothing changed.** (§3.11, the bug-fix session.) `useReducer`'s only bail-out mechanism is reference equality — an action that fires repeatedly with frequently-identical data (polling is the paradigm case) will otherwise produce a "new" state every time regardless, which is fine in isolation but becomes a real "Maximum update depth exceeded" risk once anything downstream (an unstable callback, an effect keyed on the resulting prop) reacts to that reference change. `upload-started`/`upload-succeeded`/`upload-failed` don't need this guard — they're genuine one-shot events, not repeating ones — only `job-status-updated` does. Apply the same discipline to any future reducer action with the same "fired repeatedly by a poll/subscription" shape (Results/History, if either ends up polling anything).
26. **`resultJson`'s shape, for Stage 4's field extraction, was verified against the backend's own defensive parsing code and its test fixtures (`apps/backend/src/utils/confidence.ts`/`.test.ts`), not a live Azure Document Intelligence call.** (§3.12.) §9's own point 4 flagged this as unverified going into Stage 4 and asked for a re-check "before assuming a specific field layout" — judged this the most authoritative source actually reachable without spending real Azure credits: it's the one place in the codebase that already has to know `resultJson`'s real shape well enough to defensively compute an average confidence from it, built from real-shaped fixtures. `extract-fields.ts` mirrors its defensive style deliberately (never throws on a malformed/missing field, `isRecord` guards, no assumption the full Azure `DocumentField` union is modeled). Still not the same as a real Azure response — carried forward as a real, stated gap (§7), not silently treated as closed.
27. **Kept `useDocumentPreview`'s effect+setState pattern over the alternatives a new `react-hooks/set-state-in-effect` lint rule implied, with a justified inline disable.** (§3.12.) The rule (from `eslint-plugin-react-hooks@7.1.1`, pulled in transitively via `eslint-config-next`) suggests `useSyncExternalStore` for syncing from external mutable state, which fits reading the cached `File` but not the blob-URL creation+cleanup this hook also does; the render-time alternatives (`useMemo`, a lazy `useState` initializer) have no paired cleanup for React Strict Mode's development-only double-invoke and would leak one blob URL per mount, which the effect's own mount→cleanup→mount double-invoke pairing doesn't. Read the rule's actual source before deciding, rather than either blindly complying (and shipping a real regression) or blindly suppressing (without checking whether the rule had a point). Scope any future use of this same escape hatch narrowly — it's specific to "a resource that needs paired cleanup, derived from a synchronous external read," not a blanket exemption from the rule.
28. **`DocumentPreviewPanel` renders `session-blob`/`remote-url` uniformly through an `<iframe>`, not a type-branched `<img>`/PDF-viewer.** (§3.12.) `DocumentPreviewSource` deliberately carries no MIME type (decision 2) — branching would mean threading file type through as a new prop for a UI gain (a marginally cleaner image preview) that browsers already provide natively inside a frame regardless of file type.
29. **Results lives at `/documents/[jobId]`, not folded into a future History per-row view.** (§3.12, resolves §9's previously-open point 3.) Chosen because it's what this stage's own preview-cache/hook doc comments already assumed while being built, and because a job-detail route reached directly from the upload queue (§3.12's "View results" link) is the more natural product flow than requiring a detour through History first. `documents.service.ts#getJobStatus` (Stage 3, already tested) remains the sole data source — no new backend call was needed.
30. **`@tanstack/react-table` (installed since Stage 0) still isn't used, and Stage 5's History table confirms this wasn't a one-off Stage-4 judgment call.** (§3.13.) Its actually-installed major version (9.0) has a materially different, more complex API than the familiar v8 one the original plan assumed; with no sorting/selection/expansion actually needed for either table built so far, plain HTML `<table>` markup remains the better fit both times. Revisit only if a future table genuinely needs what the library provides.
31. **Human review status (`review_status`) is a completely independent lifecycle from Azure processing status (`status`), never folded into the same column.** (§3.17.) `status` directly drives the frontend's polling logic (`poll-schedule.ts` stops polling on a terminal value) — overloading it with review semantics would mean either new enum values that never affect polling (a status column half of whose values are inert) or breaking the polling contract outright. A job can only leave `review_status: unreviewed` once `status = 'completed'`, enforced in the service layer and backed by a defense-in-depth two-column CHECK constraint at the database level — the same "app logic is primary, a DB constraint backs it up" layering already established for job creation/quota checks elsewhere in this codebase.
32. **Saving a correction on an already-confirmed/rejected job resets it to `unreviewed`, automatically, as part of the same write.** (§3.17.) Without this, a "Confirmed" badge could keep describing data a later, unreviewed edit has already superseded — which is what would make the confirm/reject signal untrustworthy, not just stale-looking. Only the standalone save-without-deciding path resets; confirming/rejecting with an attached corrections payload sets the final status directly, no separate reset-then-set step.
33. **Field corrections are stored as a full, append-only, per-edit audit-history table (`document_field_corrections`), not a simpler "latest value" column on `document_jobs`.** (§3.17, confirmed via `AskUserQuestion` over the lighter, faster-to-ship alternative.) The user explicitly named future audit/history as a first-class requirement, not a nice-to-have; a single "current value" column would have made that structurally impossible to add later without losing everything corrected before the richer table existed, while the richer table costs only slightly more query complexity (a small reduction step to compute "current effective value" from the ordered history) for real, permanent audit capability from day one.
34. **Corrections-endpoint writes are ordered so a partial failure can never leave the system claiming something the data doesn't back up — the write that could make a false claim always goes last.** (§3.17.) Concretely: saving a correction on a confirmed/rejected job resets `review_status` to `unreviewed` *before* inserting the new correction rows (so a failed insert leaves an honestly-unreviewed job, not a stale "confirmed" claim over silently-unsaved edits); confirming/rejecting inserts any accompanying corrections *before* setting the final `review_status` (so a failed status-set leaves the corrections safely saved but the document simply not yet confirmed, never a "confirmed" claim the corrections behind it don't support). Same principle applied twice, in the direction each specific case actually needs it — not a single fixed ordering rule.
35. **Editing/saving/confirming/rejecting is open to any organization member; only the destructive file/document-deletion actions (Phase 2, not yet built) are restricted to the uploader or an org owner/admin.** (§3.17, confirmed via `AskUserQuestion`.) Matches how viewing already works — org-scoped, not uploader-scoped, via the existing `document_jobs_select_same_org` RLS policy and `getDocumentJobForOrganization`'s own lookup — and supports the realistic case where the person reviewing a document isn't the person who uploaded it. Reversible, non-destructive actions don't need the stricter gate destructive ones do.
36. **`GET .../corrections` is a separate endpoint, not fields on the shared `JobDto`.** (§3.17.) Computing "effective value per field" needs an extra query against `document_field_corrections` — cheap for one job, but `toJobDto` is also used by `GET /documents` (list, up to 100 rows/page); folding it into the shared DTO would mean either an N+1 query on every list load or a dishonest always-empty placeholder for list items. `reviewStatus`/`reviewedAt`/`reviewedBy` stay on the base DTO regardless, since they're plain already-fetched columns with no such cost — only the derived, per-correction data gets its own endpoint, mirroring the same reasoning that already kept the Part-1 preview-url endpoint separate from the job DTO (decision 2's Stage-4/Part-1 evolution).
37. **`@tnda-ai/shared` stays unpopulated even though Phase 1 needed the exact kind of small cross-cutting utility (an Azure-field-value lookup) it was scaffolded for.** (§3.17.) The package is still completely unimported and not declared as a dependency of either app — wiring it up for real (adding it to both `package.json`s, confirming both Bun and Next.js/Turbopack resolve a TS-source workspace package without extra config) is a genuine first-time integration step, disproportionate for one ~10-line function. Duplicated it instead, with a dated comment pointing at the original — the same proportionality call already made for `DOCUMENT_TYPES` (decision 9's original reasoning still holds) and `isMarkdownContent` (decision 39, below). Revisit `@tnda-ai/shared` if a third consumer, or a genuinely larger shared need, shows up.
38. **Storage upload (Part 1) is deliberately non-fatal, same tier of caution as this codebase's existing quota/plan checks.** (§3.15.) A storage hiccup during upload is caught, logged, and the flow proceeds straight to Azure submission regardless — `storage_path` simply stays `null`. A user getting their extracted data is judged more important than the original file also being retrievable later; the preview UI already has an honest `unavailable` state for exactly this case, so nothing is silently hidden.
39. **`DocumentPreviewSource` gained a fourth variant, `loading`, distinguishing "don't know yet" from "confirmed nothing exists."** (§3.15, extends decision 2.) Found and fixed proactively while implementing Part 1, not present in the original plan: without it, a reloaded or History-opened job would flash "Preview unavailable" for a moment before its real signed-URL preview arrived, since both "still fetching" and "confirmed empty" collapsed onto the same `unavailable` state. TanStack Query's `isPending` is what distinguishes the two now.
40. **Markdown rendering (Part 2) is scoped by document type, not applied universally to `content`.** (§3.16.) Only `generic` documents actually receive Markdown from Azure (`documents.strategy.ts` requests `outputContentFormat=markdown` for that type alone) — running the other three types' plain OCR text through a Markdown parser risks misinterpreting incidental characters (a line starting with `"- "`, a stray `#`/`_` in an address or ID number) as formatting instead of literal content. `extract-fields.ts#isMarkdownContent(documentType)` makes the split explicit and hand-mirrors the backend's own per-type routing table, the same established convention as `DOCUMENT_TYPES`.
41. **Raw content collapses behind a native `<details>/<summary>` whenever structured fields also exist, full prominence only when they don't.** (§3.16.) Fixes a real, previously-unnoticed bug (`DocumentResultsView` was showing both at equal prominence for all four document types, contradicting a stale code comment that claimed otherwise) and matches the Results page's stated direction as a review screen: structured fields are the primary editable surface for field-shaped types; raw content is a secondary "compare against the source" reference, and is the *only* extracted content there is for `generic`, where it stays prominent. No new dependency — a native disclosure element, consistent with this codebase's precedent of reaching for a plain HTML primitive before a new one.
42. **`DocumentFieldsTable` is always directly editable — no separate view/edit-mode toggle.** (§3.17.) The Results page's stated purpose is now a document *review* workspace, where correcting a value is the core action, not an occasional one; requiring an extra click to "enter edit mode" first would be pure friction with no corresponding benefit, unlike a form where accidental edits are a real risk (they aren't here — nothing saves until "Save corrections"/"Confirm"/"Reject" is explicitly clicked).
43. **`react-hook-form` was not reused for the field-corrections form, despite being the established pattern for this app's two other forms (login/signup).** (§3.17.) RHF earns its keep there through schema-driven validation (`zodResolver`) against a fixed, known-ahead-of-time field set. Neither holds for corrections: the field set is dynamic and Azure-determined (a different, variable-length list per document), and a corrected value has no real validation rule to enforce beyond "an arbitrary replacement string." A plain `useState` draft, diffed for a dirty check, covers what's actually needed without the added surface area.
44. **Storage-deletion failure is handled asymmetrically between the two Phase-2 file-lifecycle functions, deliberately, not inconsistently.** (§3.18.) `deleteDocument`'s Storage-removal step is non-fatal (caught, logged, the soft-delete proceeds regardless) — same tier of caution as Part 1's original upload-time write, since the document disappearing from view is the primary user-facing effect and shouldn't be blocked by a transient Storage hiccup. `removeDocumentFile` does the opposite — a Storage failure there propagates and `storage_path` is left untouched, since removing the file is that endpoint's entire purpose; silently nulling the path while the file might still exist would create a permanently orphaned, unreferenced object. Same category of risk, two different correct answers depending on what each endpoint is actually for.
45. **A second, deliberately unfiltered repository lookup (`getDocumentJobForOrganizationIncludingDeleted`) makes the two delete endpoints genuinely idempotent, not just error-tolerant.** (§3.18.) `getDocumentJobForOrganization` (used by every other endpoint) now excludes soft-deleted jobs — correct, since a deleted job should be invisible/unactionable everywhere else. But that same filter would make a *repeated* `DELETE /jobs/:id` call 404 instead of cleanly no-op, since the row it needs to find is exactly the one the filter hides. The delete-related service functions use the unfiltered lookup instead, specifically so a second call finds the row, re-verifies permissions, and no-ops.
46. **`ForbiddenError` and the uploader-or-owner/admin permission model got their first real implementation in Phase 2**, via a single `assertCanManageFile(job, userId, role)` helper shared by both delete-related service functions. (§3.18.) `ForbiddenError` had been defined in `utils/errors.ts` since early in the project but never actually thrown until now; the permission model itself was already agreed before Phase 1 started (decision 35) — this is just where it was finally built.
47. **`DELETE /jobs/:id/file` returns the updated `JobDto`; `DELETE /jobs/:id` returns only `{jobId}`.** (§3.18.) The first leaves the job fully visible, so returning it matches confirm/reject's existing shape; the second doesn't — once deleted, the job isn't retrievable through any other endpoint, so there's nothing else meaningful left to hand back.
48. **`useRemoveDocumentFile`/`useDeleteDocument` live in `features/documents/hooks.ts`, not `features/results/hooks.ts`** (where Phase 1's review-workflow hooks live). (§3.18.) Anticipates Phase 3's Documents-list actions, which need the exact same two hooks from a different page, not a Results-page-scoped module.
49. **The `alert-dialog` primitive was added via the actual `shadcn` CLI, not hand-written**, so it matches this project's existing radix-nova conventions exactly rather than risking a subtly-inconsistent hand-rolled version — the same verification discipline already applied to every other cross-checked choice in this document. (§3.18.)
50. **`DocumentRowActions` uses `AlertDialog`'s controlled `open`/`onOpenChange` form, not the trigger-wraps-a-button pattern `DocumentResultsView` uses for the same two actions.** (§3.19.) The trigger here is a `DropdownMenuItem`, and nesting an `AlertDialogTrigger` inside one is a known-fragile Radix composition — the dropdown's own close/focus-return behavior on item-select can race the dialog opening. A `DropdownMenuItem`'s `onSelect` (with `event.preventDefault()`) sets local state instead, and a sibling, controlled `AlertDialog` opens from that state. Two legitimate Radix compositions for the same underlying UI pattern, chosen per how each one's trigger is actually structured — not an inconsistency to reconcile.
51. **One `useRemoveDocumentFile`/`useDeleteDocument` hook instance per rendered Documents-list row, not one shared instance for the whole table.** (§3.19.) Same "hook per item in a dynamic list" pattern as `PolledUploadQueueItem` (decision 21) — a single shared mutation instance would mean every row's pending/error state collapsing onto one object, so row A's in-flight delete would incorrectly disable row B's buttons too.
52. **`REVIEW_STATUS_DISPLAY` was exported from `DocumentResultsView.tsx` for `DocumentsTable.tsx` to reuse, not duplicated a third time.** (§3.19.) Both components live in the same app, so — unlike the cross-*package* `@tnda-ai/shared` case (decision 37), which has a real first-time integration cost — sharing a small in-app display map costs nothing. Matches the same cross-file convention `DocumentsTable.tsx` already used for `DOCUMENT_TYPE_LABELS`.
53. **ZIP-bomb protection streams the archive through fflate's incremental `Unzip`, feeding input in bounded chunks, rather than checking sizes after `unzipSync` already decompressed everything.** (§3.20.) A single `unzipSync`-style call can't be interrupted mid-decompression; feeding the *outer* archive bytes to the streaming reader in small pieces is what makes an internal per-entry buffer only ever grow chunk-by-chunk, so a resource check can actually abort *during* expansion instead of only after. Verified by reading fflate's own source (`inflt`'s buffer-doubling behavior), not assumed.
54. **CI's new dependency-vulnerability scan is pinned to `--audit-level=high`, not `pnpm audit`'s `moderate` default.** (§3.20.) Checked first, not guessed: this repo currently has one pre-existing moderate advisory (`file-type`, an irrelevant-to-this-app ASF-parser bug) that `moderate` would fail CI on immediately. `high` stays green today while still gating on anything that actually warrants blocking a merge — the policy and the reasoning are both documented inline in `ci.yml`.
55. **Two bugs were fixed opportunistically while writing Wave 1's tests, not left as "found but not fixed."** (§3.20.) `auth.service.ts`'s rollback-error-masking was audit-named and bundled with the auth-testing item; `file-inspector.ts`'s uncaught-throw-on-corrupt-input was not audit-named, discovered only while constructing a test fixture. Both were small, contained, and directly reproducible by a test — fixed and disclosed explicitly in each case, rather than either silently expanding scope or silently leaving a newly-discovered gap unfixed.
56. **`DocumentRowActions`'s confirm handlers call `event.preventDefault()` on `AlertDialogAction`'s click, discovered to be necessary by reading Radix's source rather than assumed.** (§3.20.) `AlertDialogAction` is `DialogPrimitive.Close` internally and closes the dialog on any click by default, before an async mutation resolves — confirmed via `composeEventHandlers`' actual implementation (runs the passed `onClick` first, skips its own close-handler only if `event.defaultPrevented`). Without this, a pending/failed remove-file or delete couldn't show its error or pending state inside the dialog, since the dialog would already be gone.
57. **`archived_at` was explicitly deferred out of Wave 2, despite being a named line item in the architecture doc's own Wave 2 roadmap.** (§3.21, user decision.) Nothing else in this wave's actual scope (the event log, retry tracking) required the column, and no Archive operation/API/UI exists anywhere to set it — adding it now would have been exactly the "speculative column, just in case" pattern this project avoids elsewhere. Ships alongside Archive itself, whenever that's actually built, not ahead of it.
58. **The lifecycle event log's write-order consistency model (state write, then event write, event-insert failure caught and non-fatal) was chosen over introducing a new database write-RPC pattern.** (§3.21, ADR 0011.) This codebase's four existing RPCs are all read-only aggregations; a generic write-RPC flexible enough for nine structurally different transitions would mean either one SQL function per event type (real, ongoing maintenance surface) or a dynamic-column-patch function (a dynamic-SQL risk surface this schema has otherwise avoided everywhere). Reuses the exact discipline decision 34 already established for corrections/review-status ordering, extended one step further. Accepted limitation: a crash/network partition in the narrow window between the two writes can leave a real transition with no event row — cannot happen in reverse (a false event for a transition that didn't occur), which is the invariant that actually matters for an audit log.
59. **Retry-state classification (`is_retryable`) uses the real signal already available (an `AzureServiceError`'s attached HTTP status) rather than inventing a new Azure error taxonomy.** (§3.21, ADR 0011.) A submission-time 4xx means Azure explicitly rejected the request (terminal — retrying the identical request fails the same way); a 5xx, timeout, or malformed-response error with no status attached is transient. An Azure-*reported* operation failure (as opposed to a transport-level error) is always classified terminal, since Azure fully processed the document and judged its content unprocessable. Not consumed by anything yet — safe and cheap to refine once Wave 3 has real failure data to refine it against.
60. **No backoff/"not before" scheduling timestamp was added alongside `retry_count`/`is_retryable`.** (§3.21, ADR 0011.) Computing one needs a real backoff formula, which the architecture doc's own Wave 3 contract (§5) explicitly reserves for whoever builds the worker, with real queue-depth/latency data this session has none of. An unpopulated scheduling column for a formula that doesn't exist yet would itself have been a speculative addition.
61. **HTTP 429's classification under the approved 4xx-is-terminal rule was identified as a real edge case and deliberately left unfixed, recorded as an explicit Wave 3 decision item instead.** (§3.21's follow-up verification.) `beginDocumentAnalysis` already retries `429` internally (5 attempts, backoff) before ever throwing, so a persistent 429 that survives that already reflects sustained rate-limiting — arguably the canonical *retryable* case, not "Azure rejected this request." The exact classification rule was reviewed and approved verbatim in the prior turn; changing it unilaterally during a verification pass would have violated that approval. Zero functional impact today (`is_retryable` is inert). Decide explicitly, with real data, before Wave 3 ever consumes this field to drive an actual retry — don't silently special-case it later without that decision being made first.
62. **Job-claim state (`claimed_by`/`claimed_at`/`lease_expires_at`/`lease_epoch`/`next_attempt_at`) lives directly on `document_jobs`, not a separate claims/leases table.** (§3.22, ADR 0012.) The same orthogonal-attribute pattern already used repeatedly for `deleted_at`, `review_status`/`reviewed_by`, and `retry_count`/`is_retryable` — a new, independently-nullable attribute set on the existing row, not a new state machine or a second table to keep transactionally consistent with the first.
63. **`p_worker_id` identifies one claim slot, not a worker process — caught during Phase 1's own independent review before any code shipped, not discovered later as a live bug.** (§3.22, ADR 0012.) The claim RPC's renew-vs-claim-new decision is purely "does a row already have `claimed_by` = this value" — tracing through what a worker holding several concurrent jobs (`WORKER_CONCURRENCY > 1`, already an approved Wave 3 default) would actually do with one shared process id showed its renewal calls would silently renew every job it holds instead of ever claiming a new one. Documented explicitly (column comment, function comment, repository wrapper TSDoc) so the phase that builds the real worker doesn't have to rediscover this.
64. **The claim RPC's `authenticated`/`anon` access is closed with two explicit `REVOKE` statements, not by omitting a `GRANT` — confirmed empirically, not assumed.** (§3.22, ADR 0012.) PostgreSQL grants `EXECUTE` to `PUBLIC` on function creation by default, and this specific Supabase project separately grants `EXECUTE` directly to `authenticated`/`anon`/`service_role` on every new function in `public` (a project-level default-privilege rule, confirmed by querying `information_schema.routine_privileges` against the real database, not something any migration in this repo sets up). The original draft's "just don't grant it" approach — which works for a normal table's RLS — left the RPC fully callable by any signed-in end user, a real cross-tenant risk given it's `security definer` and claims across every organization. `service_role`'s own access was confirmed, empirically, to survive both revokes.
65. **Byte retrieval for the worker re-downloads from Storage and re-inspects, rather than switching Azure submission to `urlSource`.** (§3.23, ADR 0013.) The worker runs in a separate process from the original upload request, with no in-memory bytes — re-downloading and re-running `inspectDocumentFile` reuses the exact magic-byte detection every other submission path already trusts, instead of trusting Storage's stored content-type metadata or taking on `urlSource`'s different network/trust model (a publicly-reachable or signed URL Azure itself fetches) for no immediate need.
66. **A claimed job with no `storage_path` is terminal and non-retryable, never attempted.** (§3.23, ADR 0013.) If the file was never persisted, or was independently removed while queued, no future attempt could ever succeed either — there's nothing to retry towards. Distinct from the existing, unchanged decision that a Storage *upload* failure at request time is non-fatal (decision 38) — this is what happens later, when the worker actually needs the bytes that were never (or no longer) there.
67. **Every worker-originated write is fenced by `lease_epoch` through one shared primitive, `updateDocumentJobIfEpochMatches`, and a `null` return is a hard "stop touching this job" contract, not a retryable failure.** (§3.23, ADR 0013.) This is Phase 1's fencing primitive (ADR 0012) getting its first real consumer — exactly the discipline requirement ADR 0012's own "Consequences" section named as future work for whoever built the phase that adds real writes.
68. **Terminal writes clear `claimed_by`/`claimed_at`/`lease_expires_at`; `lease_epoch` itself is never reset.** (§3.23, ADR 0013.) Closes the "no release mechanism yet" gap ADR 0012 explicitly deferred. Leaving `lease_epoch` untouched on release (it only ever increments on a *fresh* claim, unchanged from Phase 1) is what lets it keep serving as a fencing/history token across a job's entire retry lifetime, not reset to a value a stale in-flight write from a *previous* attempt could still coincidentally match.
69. **The claim loop routes every response from a claim call — fresh or renewal — through the identical job-adoption path, never assuming a "renewed" result is still the job it was tracking.** (§3.23, ADR 0013 — the one real gap this phase's own consistency review found before implementation.) `claim_or_renew_document_job` is one RPC; a renewal call can legitimately fall through to claiming a different job if this slot's lease was lost to a reclaim elsewhere in between. The original worker design implicitly assumed a renewal always either confirms the same job or returns nothing — tracing the RPC's actual behavior showed a third case the design hadn't accounted for.
70. **HTTP 429 is reclassified as retryable, resolving the previously-recorded open item at decision 61.** (§3.23, ADR 0013.) A 429 that survives `beginDocumentAnalysis`'s own existing internal retry-with-backoff represents sustained rate-limiting, not Azure rejecting the request — the canonical retryable case, not a terminal 4xx. `Retry-After` (when present) is captured into `AzureServiceError.details.retryAfterSeconds`, the smallest additive change to the existing error shape, and honored verbatim by the backoff calculation ahead of the computed exponential formula.
71. **Retry backoff is exponential-with-jitter (30s base, ×2 per retry, capped at 10 minutes), computed from the job's pre-failure `retry_count`, with exhaustion compared against `maxRetries` using the exact same value the claim RPC itself checks for eligibility.** (§3.23, ADR 0013 — the first of the three pre-implementation consistency-review questions.) Getting this comparison one attempt off in either direction would mean the worker and the RPC disagree about whether a job is still eligible to be reclaimed — verified consistent before any code was written, not discovered as a mismatch afterward.
72. **`processing_retried` fires exactly once per retry attempt, only on a fresh claim with `retry_count > 0`, never on a renewal — the one new event Phase 1's ADR explicitly deferred.** (§3.23, ADR 0013, migration `0017`.) Claiming/renewing/lease-expiry stay out of the domain event log, unchanged from Phase 1's own operational-vs-domain boundary (ADR 0012). Retry exhaustion stays a `processing_failed` event with an `exhausted: true` metadata flag, not a new event type — the same domain fact, with extra detail about why no further retry will happen.
73. **`GET /jobs/:id` became a pure database read, and `POST /documents` no longer submits to Azure synchronously — the one HTTP-behavior change in this phase, with the response contract otherwise deliberately unchanged.** (§3.23, ADR 0013.) `BatchFileResult.status` still reports `"processing"` for an accepted batch file (accepted into the pipeline, not the job's literal DB status, which is `pending` until the worker picks it up) specifically to avoid any response-schema change. Verified, by a fresh frontend code trace across ten files (not assumed), that the frontend already treats `pending` identically to `processing` everywhere it branches on job status — no frontend change was needed.
74. **Worker defaults, and where each one lives**: `WORKER_CONCURRENCY=5`, `WORKER_LEASE_SECONDS=180`, `WORKER_MAX_RETRIES=3`, `WORKER_POLL_INTERVAL_MS=5000` as Zod-validated env vars; lease renewal at 50% of the lease duration is computed in `worker/index.ts` as a ratio of an already-configurable value, not given its own separate env var, since it isn't an independent tuning knob. (§3.23, ADR 0013.)
75. **No Dockerfile change, no Turbo-dev-fan-out wiring, and no live-Postgres/live-Azure test added to CI in this phase — all deliberate, not deferred by oversight.** (§3.23, ADR 0013.) The worker runs via new `worker:dev`/`worker:start` scripts, matching the existing `dev`/`start` convention; no concrete existing constraint required bundling it into the dev fan-out, and real-database/Azure verification stays manual, consistent with Phase 1's own stance (decision 62's era) rather than becoming permanent CI infrastructure.
76. **An unexpected claim/submit/poll exception inside the worker's claim loop is now caught per-iteration, logged, and never propagated — recovery relies entirely on Phase 1's existing lease-expiry mechanism, not a new write path.** (§3.23, ADR 0013 — found by live verification, not either design review.) A real, live worker process crashed entirely the first time it hit an unexpected Azure error on a stale row, taking every concurrently-held job down with it; the fix deliberately does *not* attempt an epoch-gated write from the catch block, since doing so under an unknown/possibly-already-lost claim state would risk exactly the kind of unguarded write the fencing discipline (decision 67) exists to prevent. The row simply keeps its claim until the lease naturally expires — no new recovery mechanism, reusing what Phase 1 already built.
77. **`claimOrRenewDocumentJob`'s "nothing to claim" case is now discriminated by the primary key (`data?.id`), not the truthiness of the returned object — a fix to already-committed Phase 1 code (`275d578`), not a Phase 2 change.** (§3.23, ADR 0013 — found by live verification.) PostgREST serializes a SQL NULL of the RPC's composite return type as an object with every field `null`, confirmed empirically against the real database; `data ?? null` never caught this, since the object itself is truthy. Undetected until something actually ran the RPC unattended, in a loop, against a real empty-queue state — Phase 1's own unit test mocked a bare `data: null`, which structurally cannot exercise this shape. `id` is safe as the discriminator because it's the primary key and can never be null on a genuine row.
78. **A centralized, static role/permission matrix in `packages/shared/src/authorization.ts` replaces the two ad hoc `role === "owner" || role === "admin"` checks that used to live independently in `billing.service.ts` and `documents.service.ts`.** (§3.33, ADR 0016.) `can(role, permission)` is pure, synchronous, and does no I/O; both apps import it unmodified. This is deliberately the first real population of `packages/shared` since ADR 0008 scaffolded it empty — the matrix is exactly the "concrete, specific piece of code that needs to exist in both applications, unmodified" that decision was waiting for, not a reversal of it.
79. **Ownership is a separate, generic primitive (`assertPermissionOrOwner`) rather than a per-resource ACL table.** (§3.33, ADR 0016.) Currently has exactly one caller — document deletion, where an uploader can always delete their own document without needing `documents.delete`, and an admin/owner can delete anyone's — deliberately shaped so a future resource-level rule reuses the same primitive with a different `isOwner` predicate instead of new machinery.
80. **No ACL/policy engine was introduced — an explicit non-goal, not an oversight.** (§3.33, ADR 0016.) A static, code-level role→permission map is the smallest design satisfying "centralized, not scattered" and "cheap to change a role's permissions later" without over-building for a scale (per-org custom roles) the product isn't at.
81. **`billing.manage` is owner-only, a deliberate behavior change from the pre-RBAC model where `admin` and `owner` had identical billing access.** (§3.33, ADR 0016.) `owner` represents organization ownership/financial responsibility; `admin` represents operational administration without billing authority.
82. **The `profiles_update_self` RLS gap is fixed with a self-referential subquery in the policy's `with check`, not a trigger.** (§3.33, migration `0018`, ADR 0016 — found independently, not by live verification like decisions 76-77, but confirmed correct by live verification afterward, §3.33.) Within one `UPDATE` statement, an RLS `with check` subquery on the same table sees the pre-update snapshot, so comparing the proposed `role` against `(select p.role from public.profiles p where p.id = auth.uid())` makes `role` immutable through this specific policy. Matters specifically because RBAC reads `profiles.role` as its sole source of truth for every authorization decision on both backend and frontend — any way to set it outside the trusted service-role path would have undermined the whole model.
83. **`apps/backend/src/config/database.types.ts` was hand-edited to add the `reviewer` role rather than regenerated via `supabase gen types`.** (§3.33.) The Supabase CLI isn't installed in this environment. The hand-edit was checked by hand against the real `profile_role` enum (confirmed via live query, §3.33/Task 2) rather than assumed, but it is still a stand-in, not authoritative — regenerate for real the next time the CLI is available, per §7/§9.

| `DELETE /api/v1/documents/jobs/:id` **(new, Phase 2, §3.18)** | — | `{jobId}` — soft-deletes the job and removes its file; idempotent if already deleted |

`JobDto` (three fields added in Phase 1, for the review workflow — `reviewStatus`, `reviewedBy`, `reviewedAt`): `{jobId, status, fileName, fileSizeBytes, pageCount, documentType, averageConfidence, resultJson, errorMessage, reviewStatus, reviewedBy, reviewedAt, createdAt, updatedAt}`. All four Phase-1 review/correction endpoints guard `status === "completed"` — `ConflictError`/409 otherwise, since there's nothing to review or correct before that. Both Phase-2 delete endpoints guard the caller is the job's uploader or an org `owner`/`admin` — `ForbiddenError`/403 otherwise (§4 decision 46).

**Frontend BFF routes that exist** (`apps/frontend/app/api/`): `auth/{login,signup,logout}`, `organization` (proxies `GET /organizations/me`), `organization/stats` (proxies `GET /organizations/me/stats`, Stage 2), `documents` (proxies `GET /documents`, Stage 2, **and now `POST /documents`, Stage 3** — multipart passthrough, 400 `VALIDATION_ERROR` locally if no file is present before ever calling the backend), `documents/[jobId]` (Stage 3 — proxies `GET /documents/jobs/:id`, for polling; also Stage 4's Results page, §3.12; **and now `DELETE`, Phase 2, §3.18** — added to this same existing route file, not a new one), `documents/[jobId]/file` (`DELETE`, new file, Phase 2, §3.18), `documents/[jobId]/preview-url` (Part 1, §3.15), `documents/[jobId]/corrections` (`GET`+`PATCH`, review-workflow Phase 1, §3.17), `documents/[jobId]/confirm`, `documents/[jobId]/reject` (both `POST`, §3.17), `billing/subscription` (proxies `GET /billing/subscription`, Stage 2 — minimal, §4 decision 17). **Still missing**, needed starting Stage 6: `billing/{plans,checkout,portal}`. Note (§4 decision 14): Stage 2's own Dashboard page doesn't call `organization/stats`/`billing/subscription` itself — it's a Server Component using `services/*` directly; those two BFF routes exist for client-side callers. `documents`/`documents/[jobId]` and its sub-routes *are* actively used client-side, by the upload hooks (§3.10), the Results page's review-workflow hooks (§3.17), its file-lifecycle hooks (`features/documents/hooks.ts`, §3.18), and now the Documents-list row actions too (§3.19, reusing those same file-lifecycle hooks rather than adding new ones).
