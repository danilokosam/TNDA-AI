## 1. Project Overview

TNDA-AI is a multi-tenant SaaS platform for automated document processing (invoices, receipts, identity documents, generic scans — single files or `.zip` batches) via Azure Document Intelligence, with Stripe-backed subscription billing. Two applications: a Bun + ElysiaJS REST API (`apps/backend`) and a Next.js dashboard (`apps/frontend`), in a pnpm + Turborepo monorepo. **The backend is the single source of truth** for business logic, querying, filtering, pagination, and analytics — the frontend never queries Supabase directly for application data (it does use Supabase directly for one thing only: session/cookie management via `@supabase/ssr`, which is identity plumbing, not application data — see §4, decision 1).

### 3.8 Stage 2 close-out review

Before committing, asked to review every uncommitted change once more rather than take the prior pass as final — this caught two real issues that a second, more skeptical read surfaces and a first implementation pass didn't:

- **`UsageMeter` used `role="progressbar"` with an unclamped `aria-valuenow`.** A progress bar is semantically "an operation running to completion" — usage-vs-quota is a scalar measurement within a known range, which is ARIA's `role="meter"` (the dataviz skill's own name for this component, too). Also, `documentsUsed`/`pagesUsed` are plain counts, not clamped to the plan limit — an org that used to be on a higher plan and downgraded (or any future edge case producing `used > limit`) would have pushed `aria-valuenow` past `aria-valuemax`, which is invalid per the ARIA spec. Fixed: `role="meter"`, `aria-valuenow` clamped to `Math.min(used, limit)`, and an explicit `aria-valuetext` so the real (possibly over-limit) numbers are still what gets announced.
- **The empty-state gate only checked `stats.totalJobs`, which counts terminal (completed/failed) jobs only.** Verified directly against `0010_document_analytics.sql`: `get_organization_daily_job_counts` and `get_organization_job_stats` share the exact same `where ... and status in ('completed', 'failed')` clause, so `dailyCounts` and `totalJobs` are always consistent with each other — that part was already correct. But an org with a job still `pending`/`processing` (uploaded, not yet resolved) would have `totalJobs === 0` and see "No documents yet," which is misleading once Stage 3 makes that a reachable real state. `usage.documentsUsed` (from `/organizations/me`, already fetched on this page) counts `pending`/`processing`/`completed` — cheap, already-available signal to add. Gate is now `stats.totalJobs === 0 && usage.documentsUsed === 0`.
- **Noted, not changed**: `apps/frontend/PROGRESS.md`'s Stage 0 section says the plan anticipated "shadcn's own chart primitives" (i.e. shadcn's `chart.tsx`, built on Recharts) specifically so charts would share the same `--chart-1..5` token system as the rest of the theme. ### 3.11 Stage 3 bug fix — "Maximum update depth exceeded" on upload

The user manually ran both apps in a real browser (per §3.10's own plan) and hit a real crash uploading a document — the exact class of bug §3.10's own tests couldn't have caught, since it's a pure client-side render loop, invisible to every verification method available in this environment (curl included). Told explicitly to diagnose root cause, not patch superficially, and to determine whether it was effect dependencies, unstable callback identities, or unnecessary reducer dispatches.

**Diagnosis.** Traced the real data flow: `PolledUploadQueueItem`'s effect (`useEffect(() => { if (data) onStatusUpdate(data); }, [data, onStatusUpdate])`) called `onStatusUpdate` on every poll — but `onStatusUpdate` was a *fresh closure on every render*, at two compounding levels: `UploadQueueList` rebuilt a per-item wrapper (`(job) => onStatusUpdate(item.id, job)`) and `UploadWorkspace` rebuilt the dispatch call itself, both inline, both every render. Combined with `uploadQueueReducer`'s `job-status-updated` case unconditionally building a new array via `.map()` regardless of whether the incoming job data actually differed from what was already stored, this is the textbook shape of the bug: effect fires → dispatch → new array reference (even when nothing changed) → re-render → callback identity changes → effect fires again. Confirmed this is real, not just plausible, by temporarily instrumenting the reducer directly (a throwaway `console.log` inside it, removed before committing) and counting invocations during a sustained "job stuck at the same status" scenario: significantly more `job-status-updated` dispatches fired than real polls could justify (roughly 1.75x with a single item, exactly 2x under `React.StrictMode` — matching its documented double-invocation behavior, not a sign of anything additional — and scaling linearly, not multiplicatively, with a second simultaneously-polling item).

**What didn't reproduce, and why that's stated plainly rather than hidden**: tried to reproduce the literal "Maximum update depth exceeded" crash in an integration test — five variations (a bare re-render loop, `React.StrictMode`, freshly-varying poll responses to defeat React Query's default structural sharing, two simultaneously-polling items) — none crossed React's actual update-depth threshold inside this jsdom/Vitest environment, despite the underlying redundant-dispatch pattern being real and directly measured. Rather than force a fragile, environment-sensitive repro (or worse, quietly claim one that doesn't actually prove anything), the regression tests target the *precise, deterministic property* that has to hold instead — see below.

**Fix — two parts, one primary**:
1. **(Primary, directly satisfies the user's stated goal)** `uploadQueueReducer`'s `job-status-updated` case now returns the exact same state reference — no new array, no new item object — when the incoming job's `status` and `errorMessage` match what's already stored for that item (or when the target id doesn't exist in the queue at all). `useReducer` only bails out of scheduling a re-render when the *identical* reference comes back; returning an equal-but-new array every time (the previous behavior) meant a job legitimately sitting at one status across many polls never gave React a chance to stop.
2. **(Secondary, addresses the callback-identity contributing cause directly)** Stopped constructing a new `onStatusUpdate` closure on every render at two separate levels. `PolledUploadQueueItem` now takes `onStatusUpdate: (id, job) => void` and curries `item.id` itself (a prop it already has) instead of `UploadQueueList` pre-currying it into a fresh per-item closure every render; `UploadWorkspace` wraps its dispatch call in `useCallback` keyed on `queue.dispatch` (stable — `useReducer`'s dispatch never changes identity), not the whole `queue` object (a fresh reference every render, which would have defeated the memoization).

Both matter: the reducer fix is what makes the crash-driving cascade actually *stop* once started (the semantically correct, primary fix); the callback fix means the effect doesn't fire more than necessary in the first place, which was real, measured, wasted work independent of whether it happened to cross a crash threshold.

**Regression tests** (`features/upload/queue.test.ts`): dispatching `job-status-updated` with status/errorMessage unchanged returns the exact same array reference (`toBe`, not `toEqual` — reference identity is the entire point); dispatching with only `errorMessage` different still returns a new reference (confirms the fix doesn't silently swallow real changes); dispatching for an unknown id also returns the same reference (tightens existing no-op coverage to check identity, not just value equality). `components/upload/UploadWorkspace.test.tsx` keeps an integration-level sanity test (renders the real composed tree, sustained identical-status polling, asserts no throw) — explicitly documented in its own comment as a sanity check, not the primary proof, given the reproduction difficulty above.

**Verification**: full workspace `typecheck`/`lint`/`test` green (94 backend + 94 frontend — 4 new tests). Re-ran the real curl-based `/upload` check (fresh signup, real backend + Supabase) to confirm no server-rendering regression — but stated plainly that this cannot verify the actual fix, since the bug is a pure client-side render-loop with no server-rendered signature at all. Asked the user to confirm in their own browser, where they originally found it — that's the only real verification available for this specific class of bug in this environment.

**Closed the loop**: the user re-tested in a real browser afterward and confirmed it directly — uploaded a document, no more "Maximum update depth exceeded," no React warnings in DevTools, upload completed and polling behaved correctly. This is the actual, authoritative verification for this bug; everything above it (the reducer-level reference-equality tests, the curl check) was the closest available substitute until this confirmation landed.

### 3.14 Two bugs from Stage 5's manual verification

Investigated with an explicit instruction to find root cause, not patch symptoms, before touching PROGRESS.md or committing anything — same discipline as §3.11.

**Issue 1 — "Preview unavailable" on a document reached via History or a page reload.** Investigated the entire preview pipeline: the upload flow's `cacheFileForPreview` call, `preview-cache.ts`'s module-level `Map`, the `DocumentPreviewSource` union, `useDocumentPreview`'s blob-URL lifecycle. Both issues, together, are what prompted the user to explicitly pause new feature work and ask for an architecture redesign rather than incremental patches — see §3.15-§3.17.

### 3.15 Architecture redesign, Part 1 — Persistent document storage

Framed explicitly by the user as intentional architecture evolution, not a bug fix: migrate the original uploaded file from session-only browser memory to real backend-persisted storage, so Results/History/Dashboard/any future review screen can always retrieve it, not just the tab that did the upload. Planned together with two other parts (Part 2, §3.16, and a file-lifecycle design that was later absorbed into a larger redesign, §3.17) via Plan Mode; two sequencing questions were resolved via `AskUserQuestion` before implementation: plan all three parts together but implement Part 1 first, and — for the eventual delete workflow — soft-delete job rows, hard-delete only the underlying file.

**Storage & schema**: migration `0011_document_storage.sql` — a private Supabase Storage bucket (`documents`, `public: false`) created via SQL (`insert into storage.buckets`), not the dashboard, so it's reproducible and versioned like everything else in `supabase/migrations/`; `document_jobs.storage_path text`, nullable (null means no file persisted — predates the migration, or the non-fatal upload below failed); a `storage.objects` RLS `select` policy scoped by `(storage.foldername(name))[1] = current_organization_id()`, matching the object path convention (`{organizationId}/{jobId}/{fileName}`) — defense-in-depth only, since the actual access path is entirely backend service-role, same model as `document_jobs` itself (ADR 0005).

**Backend**: new `services/storage.service.ts` — `buildStoragePath`, `uploadDocumentFile`, `createSignedPreviewUrl` (1-hour expiry), `deleteDocumentFile` (implemented here, unused until Phase 2 of the review-workflow redesign, §3.17/§9) — all thin wrappers over `supabaseAdmin.storage.from(bucket)`, needing zero new credentials since the existing service-role client already covers Storage the same way it covers every other table. `documents.service.ts`'s `processSingleDocument` and `processZipBatch` both upload the original file to Storage right after creating the "pending" job row, **deliberately non-fatal**: a storage hiccup is caught, logged, and the flow proceeds straight to Azure submission regardless — `storage_path` simply stays `null`, and the preview UI already has an honest "unavailable" state for exactly that case. New route `GET /jobs/:id/preview-url` → `{url: string | null}`, deliberately a separate endpoint from the job status DTO rather than a field on it — embedding a signed URL in `JobDto` would mean generating one on every routine status *poll* while a job is still processing, when there's nothing to preview yet.

**Frontend**: `use-document-preview.ts` rewritten around a `useQuery` against the new endpoint. Decision order: a resolved signed URL always wins when present (the persisted file is the real source of truth now); the session cache (`preview-cache.ts`, otherwise unchanged) is downgraded to a fast-path/fallback only — an instant render for the tab that just uploaded, while the signed-URL fetch is in flight, or a last resort if server-side storage genuinely failed. **A real gap found and fixed proactively while implementing this, not present in the original plan**: without care, the hook would return `unavailable` both while the signed-URL query was still loading *and* once confirmed empty — meaning a reloaded or History-opened job would flash "Preview unavailable" for a moment before its real preview arrived. Fixed by adding a `loading` variant to `DocumentPreviewSource` (now `loading | session-blob | remote-url | unavailable`, up from three), using TanStack Query's `isPending` specifically to distinguish "don't know yet" from "confirmed nothing." `DocumentPreviewPanel` gained a matching skeleton state; its "unavailable" copy was updated to no longer claim the file is session-tab-only, since that's no longer true for anything uploaded after this migration.

Pre-existing jobs (uploaded before this migration) have `storage_path = null` permanently — there's no original file left to backfill — and fall back to session-cache-or-unavailable exactly as before; stated plainly rather than silently glossed over.

**Verification**: full workspace `typecheck`/`lint`/`test` green. The user manually verified in a real browser: the uploaded file actually appears in the Supabase Storage bucket; the Results-page preview loads via a real signed URL (confirmed via the `<iframe>`'s `src` in DevTools, not a `blob:` URL); the preview survives a full page reload; the preview also works when the same job is reached via the History table instead of directly after upload — the two specific cases Issue 1 (§3.14) identified as broken.

### 3.16 Architecture redesign, Part 2 — Results-page information architecture

Investigated before writing any code, per explicit instruction, rather than jumping straight to "add a Markdown renderer." Confirmed directly from source: `result_json` is Azure's entire `analyzeResult` response, stored verbatim and untyped — `paragraphs[]`, `tables[]`, and `pages[]` (word/line bounding boxes) all arrive from Azure and are all persisted in full, but the frontend has only ever read two things out of it: `documents[].fields` (feeding `DocumentFieldsTable`, for the three field-shaped types) and the flat `content` string (feeding `DocumentRawContent`, for all four types). `generic` documents have no `documents[].fields` at all.

Weighed three options for the raw-content panel's canonical representation: (a) render Azure's own Markdown `content` properly; (b) bypass `content` and reconstruct a custom viewer directly from `paragraphs[]`/`tables[]`, which — unlike the flat string — carry `role` (title/sectionHeading/etc.) and bounding regions, real future value for a positional "click a field, see it highlighted on the source" review UI; (c) something else. **Rejected (b) explicitly for this pass**: Azure's own Markdown conversion already does the reading-order paragraph/table interleaving correctly (merging by span offset) — reimplementing that by hand is exactly the work `outputContentFormat=markdown` (§3.14) was already requested to avoid; there is no live Azure response sample anywhere in this repository to validate a hand-built reconstruction against; and nothing is actually lost by deferring it, since the full untouched payload stays persisted in `result_json` regardless of which rendering approach runs today — a future structured/positional viewer remains just as buildable later. Chose (a).

**A second, real bug surfaced by this investigation, not previously noticed**: `DocumentResultsView` was unconditionally rendering `DocumentRawContent` whenever `content` was non-null, for *all four* document types — meaning invoice/receipt/identity_document jobs were showing their fields table *and* a full raw-text dump at equal visual prominence, un-collapsed. This directly contradicted `documents.strategy.ts`'s own code comment, which claimed those three types' content "isn't surfaced in the UI." The comment was simply stale; the behavior was real and needed fixing regardless of what the comment said.

**Implementation**: added `react-markdown`+`remark-gfm`+`@tailwindcss/typography` (none previously installed). `DocumentRawContent` gained a `format: "markdown" | "text"` prop — the Markdown pipeline (inside a `prose prose-sm dark:prose-invert` container) applies only when `format === "markdown"`; the `"text"` path keeps the exact prior preformatted/monospace rendering unchanged. This split matters for correctness, not just presentation: only `generic` documents actually receive Markdown from Azure (§3.14) — running the other three types' plain OCR text through a Markdown parser risks misinterpreting incidental characters (a line starting with `"- "`, a stray `#`/`_` in an address or ID number) as formatting instead of literal content. A new `extract-fields.ts#isMarkdownContent(documentType)` mirrors the backend's own per-type routing table (`documents.strategy.ts`) to decide which format applies — hand-kept-in-sync with a dated comment, the same established convention this file already uses for `DOCUMENT_TYPES` itself. `react-markdown`'s default behavior never renders raw HTML embedded in the source as live elements (no `rehype-raw` was added), confirmed with a dedicated test — relevant since Markdown content here originates from a scanned document, not a trusted author. Fixed the real bug above by collapsing `DocumentRawContent` behind a native `<details>/<summary>Show raw extracted text</summary>` whenever structured fields also exist, leaving it at full prominence only for `generic` (no fields at all) — no new dependency, consistent with this codebase's native-element-over-new-primitive precedent elsewhere.

**Verification**: full workspace `typecheck`/`lint`/`test` green. The user manually verified in a real browser: a `generic` document's raw-content panel now renders actual headings and a bordered table instead of literal `#`/`|` characters; an invoice/receipt/identity_document's raw content is now collapsed behind "Show raw extracted text," with the underlying text itself unchanged once expanded.

### 3.17 Document review workflow redesign — Phase 1 (review, corrections, confirm/reject)

After Part 2 (§3.16) was confirmed, the user reported the remaining gap wasn't a rendering problem: the Documents list only exposes a "View" action, and the Results page is read-only with no way to correct a wrong extraction or record that a human reviewed it. Requested a full architecture proposal — document review, field editing, confirmation/rejection, Storage lifecycle, future audit/history, multi-document-type support — before any code, explicitly not a quick fix.

Investigated the current architecture directly (routes, schema, repository/service functions, existing frontend patterns — `DropdownMenu` already used elsewhere, no `Dialog`/`AlertDialog` primitive existing yet, `react-hook-form` used only for the two auth forms) via Plan Mode, using a Plan subagent to draft and independently verify a proposal against real source before it was presented. Two decisions were confirmed via `AskUserQuestion` before finalizing the plan:
- **Field corrections get a full, per-edit audit-history table**, not a simpler "latest value only" column on `document_jobs` — chosen over the lighter option specifically because the user named future audit/history as a first-class requirement, not an afterthought, and the lighter option would have permanently lost any record of an intermediate edit once superseded by a later one.
- **Any organization member — not just the uploader or an owner/admin — can edit fields, save corrections, confirm, or reject.** Matches how viewing already works (org-scoped, not uploader-scoped) and supports the realistic case where the person who uploaded a batch isn't the person who reviews it. Destructive actions (remove the original file, delete the document) stay restricted to the uploader or an owner/admin — the already-agreed model from the earlier file-lifecycle design, which this larger redesign absorbed as its own later phase rather than building in parallel.

The approved plan sequences three phases: **Phase 1 — the review workflow itself (this section)**; Phase 2 — file lifecycle (remove file / delete document, absorbing the earlier design); Phase 3 — Documents-list fast-follow (a delete/remove-file action menu, a review-status badge). Only Phase 1 is built so far.

**Schema** (`0012_document_review.sql`): a new `document_review_status` enum (`unreviewed | confirmed | rejected`) and `review_status`/`reviewed_by`/`reviewed_at` columns on `document_jobs` — deliberately a completely independent lifecycle from the existing `status` column, which tracks Azure processing and directly drives the frontend's polling logic (`poll-schedule.ts`); conflating the two would mean either inert enum values that never affect polling, or breaking the polling contract outright. A two-column CHECK constraint (`review_status = 'unreviewed' or status = 'completed'`) backs the same rule the service layer already enforces, as defense-in-depth, not the primary mechanism. A new `document_field_corrections` table — one row per field-edit event (`field_name`, `previous_value`, `new_value`, `edited_by`, `edited_at`), RLS-enabled with a same-org `select` policy expressed as a subquery against `document_jobs` (this table carries no `organization_id` column of its own). `reviewed_by`/`edited_by` both use `on delete set null`, not `on delete cascade` like `document_jobs.user_id` — these columns record mere involvement ("who last touched this"), not ownership, so removing an unrelated profile must never silently delete jobs it happened to review.

**A non-obvious rule, load-bearing for the whole feature meaning anything**: saving new corrections on a job that's already `confirmed`/`rejected` automatically resets it to `unreviewed` (clearing `reviewed_by`/`reviewed_at`) — otherwise a "Confirmed" badge could keep describing data a later, unreviewed edit has already superseded. This reset only fires on the standalone "save without deciding" path (`PATCH .../corrections`); confirming or rejecting *with* an accompanying corrections payload sets the final status directly in the same write, with no separate reset-then-set round trip. Writes are ordered specifically so a partial failure never lands in a state that claims something the data doesn't actually back up — full reasoning is in the code's own comments (`documents.service.ts`), not just here.

**Backend**: `documents.repository.ts` gained `listFieldCorrections`/`insertFieldCorrections`; `documents.service.ts` gained a small field-value-lookup helper mirroring `extract-fields.ts#extractDisplayValue` on the frontend (deliberately duplicated rather than moved into `@tnda-ai/shared` — that package is scaffolded but still completely unimported and not even declared as a dependency of either app; wiring it up for real, for one ~10-line function, was judged disproportionate — the same proportionality call already made twice this session for `DOCUMENT_TYPES` and `isMarkdownContent`), plus `getFieldCorrections`/`saveFieldCorrections`/`confirmDocumentReview`/`rejectDocumentReview`. Four new routes: `GET`/`PATCH /jobs/:id/corrections`, `POST /jobs/:id/confirm`, `POST /jobs/:id/reject` — all four guard `status === 'completed'` (there's nothing to review or correct before that), throwing `ConflictError` otherwise, this codebase's first real use of that error class outside auth. `GET .../corrections` is a separate endpoint, not fields folded onto the shared `JobDto` — computing "effective value per field" needs an extra query against the new table, cheap for one job but not something every row of a 100-item `GET /documents` page should pay for (or dishonestly fake as empty); `reviewStatus`/`reviewedAt`/`reviewedBy` *do* live on the base `JobDto`, since they're plain, already-fetched columns with no such cost.

**Frontend**: `extract-fields.ts` gained `extractEffectiveFields`, merging Azure's originally-extracted fields with the corrections endpoint's effective-value map — `isCorrected` compares the *current* value against the original, not "does any correction exist for this field," so a field corrected and then manually reverted back to Azure's original value correctly reads as uncorrected again. `DocumentFieldsTable` is now always directly editable — no separate view/edit-mode toggle, since editing is this screen's actual purpose now, not an occasional action — showing "Edited" in place of a now-inapplicable Azure confidence score once a field's displayed value differs from its original. `DocumentResultsView` gained a full-width action bar above its existing two-column layout: a review-status badge, "Save corrections" (dirty-gated, absent entirely for `generic` documents with nothing to correct), "Confirm," "Reject," with inline error feedback if any action fails. `react-hook-form` was deliberately not reused here despite being the existing pattern for the two auth forms — the field set is dynamic and Azure-determined (a different, variable-length list per document), and a corrected value has no real validation rule to enforce beyond "a replacement string," so a plain `useState` draft was judged sufficient without the added surface of a form library built for schema-driven validation against a fixed field set.

**One lint-driven fix worth recording as a pattern, not just a fix**: resetting the local edit draft whenever `jobId` changes was first written as a `useEffect` calling `setState` — `react-hooks/set-state-in-effect` correctly flagged this as avoidable, unlike Stage 4's blob-URL case (§3.12, §4 decision 27), which genuinely needs an effect for its paired resource-cleanup semantics. This one doesn't: fixed using React's own documented "adjust state during render" pattern (a `draftJobId` comparison directly in the render body, resetting the draft synchronously within the same render pass) rather than another scoped disable comment — the correct fix this time was structural, not a suppression.

**Verification**: full workspace `typecheck`/`lint`/`test` green — 146 backend + 250 frontend tests (up from 94/197). The user manually verified in a real browser: editing a field and saving without confirming persists correctly across a reload while the review status stays "Unreviewed"; confirming a document and then editing a field again correctly reverts its status to "Unreviewed" automatically; reject behaves the same way; `generic` documents correctly get confirm/reject with no field-editing UI; no console errors or React warnings throughout.

## 4. Architectural Decisions (what, and why)

1. **Backend is the single source of truth; frontend never queries Supabase directly for application data.** (User decision, §3.4.) Supersedes the original plan's resolution for backend gaps #1/#5 (frontend-side RLS reads for History/stats) — those are now real backend endpoints instead (§8). The one exception, deliberately not a violation of this rule: `@supabase/ssr` for session/cookie management is identity plumbing (the same category as the backend talking to Supabase Auth directly for token verification), not an application-data query.
2. **Session-only document preview, behind a swappable abstraction.** (User decision.) The backend never persists uploaded files; a persistent preview isn't achievable without new infrastructure, and isn't needed for the immediate upload→results flow that matters for v1. Built behind a `DocumentPreviewSource` union type (`session-blob | remote-url | unavailable`) specifically so a persistent backend-provided URL can replace it later without touching any UI component — an explicit requirement, not an implementation nicety. **Implemented in Stage 4** (§3.12): `session-blob` via a module-level `jobId -> File` cache + `URL.createObjectURL`; `remote-url` still has no producer (unchanged — the backend still doesn't persist files); `unavailable` is the real fallback for any job reached outside the immediate post-upload flow.
3. **`@supabase/ssr` hybrid auth session model.** Backend still owns signup/login orchestration (org+profile creation, with rollback) — bypassing it would leave orphaned `auth.users` rows. Immediately after, `setSession()` hydrates an `@supabase/ssr` server client, which then owns cookie/refresh lifecycle. Refresh centralized in `proxy.ts` (Server Components can't write cookies themselves). Logout calls `signOut()` for real server-side revocation, not just cookie clearing. `SameSite=Lax`, deliberately — `Strict` would drop the session cookie on the top-level GET redirect back from Stripe Checkout, silently logging the user out right after they pay.
4. **Hand-written Zod schemas + `AssertExact`, not Eden/openapi-typescript.** Both alternatives were tried and don't work (§3.3) — this isn't a fallback chosen for convenience, it's the only approach that actually functions given the two projects' independent `tsconfig`s and the backend's broken Swagger JSON output. Arguably *stronger* than either alternative would have been: real runtime validation at every call site, not just a compile-time promise.
5. **Keyset (cursor) pagination over offset, for `GET /documents`.** Offset pagination (`.range()`) drifts under concurrent inserts — a real case here, since a batch upload can add rows while someone's paging through their own history. Cursor is on `created_at` alone (no `id` tiebreaker) — a compound cursor would need Supabase's `.or()` raw-filter-string DSL, meaning decoded client-supplied cursor content would be interpolated into a filter *expression* rather than a filter *value*. Accepted trade: two jobs created in the exact same instant could theoretically land on opposite sides of a page boundary — rare enough (each row is a separate awaited round trip) not to be worth the larger attack surface. Cursor is opaque on the wire (base64url); a malformed one is treated as "first page," not an error.
6. **`successRate`/`averageConfidence`/etc. are `null`, never a fabricated `0`, when there's no data to compute them from.** A `0` success rate reads as "100% failure" when the honest state is "no data yet"; `generic` documents (Azure's `prebuilt-layout` model) have no per-field confidence at all, and forcing a `0` there would be a lie, not a default.
7. **Stats' daily-count series is gap-filled server-side, in the service layer**, not left sparse for clients to reconstruct. The Postgres function only returns days with actual activity; a day missing from that result is indistinguishable from "no data at all" to a client that doesn't know the query's internals — filling every day once, in one place, means every consumer gets a complete, chart-ready series.
8. **No history rewrite for the monorepo migration — verified, not assumed.** `git filter-repo` was the first instinct; asked to justify it against a simpler move-and-commit approach, that simpler approach was proven (in a throwaway repo, against a real bare "remote," before touching the real one) to preserve every commit hash unchanged, push as an ordinary fast-forward, and support `git log --follow`/`git blame` correctly across the move. No force-push anywhere in this migration.
9. **`packages/types`/`packages/shared` are scaffolded and workspace-wired, but deliberately left empty.** The backend's schemas are Zod v3, the frontend's are Zod v4 (an already-made, deliberate choice — not an oversight); backend code assumes Bun-only APIs in places. Moving code into a shared package now wouldn't remove the need for the hand-verification work already done, just relocate it. Real future sharing is a *deliberate* decision to make later, not a speculative one to force now.
10. **CSRF is covered by `SameSite=Lax` + all-mutations-are-POST, deliberately, not a token.** `SameSite=Lax` already withholds the cookie on cross-site subrequests; combined with every mutating route being POST, that closes the practical gap without adding a separate mechanism.
11. **No optimistic updates in the frontend, for now — considered per-feature, not a gap.** Checked against every real mutation in the app (upload-queue entries are already transient client-only state; "mark as reviewed" is explicitly local-only since there's no backend field to persist it to yet; a plan change redirects to Stripe and can't be optimistically shown; History has no mutations at all). Recorded so this reads as a considered decision if revisited later.
12. **Call paths are fixed and enforced, not just documented, in the frontend.** Server Components import `services/*.service.ts` directly (in-process); Client Components only reach the same code indirectly through this app's own `/api/*` Route Handlers. Every file under `services/` starts with `import "server-only"` so an accidental Client Component import fails the build instead of silently risking a path to tokens in a client bundle.
13. **Chart color is the `dataviz` skill's validated default (blue), not invented, and validated against this app's real surfaces.** (Stage 2, §3.7.) This theme (`shadcn init`'s neutral base) had never used a real hue before — `--chart-1..5` were unpopulated grays. Rather than eyeball a brand color, used the skill's documented default categorical slot 1 and ran `scripts/validate_palette.js` against this app's *actual* computed card-surface hex in both modes (derived from its `oklch()` tokens, not the skill's own example surfaces) before trusting it. Only `--chart-1` was repopulated — `chart-2..5` stay gray placeholders until a chart actually needs a second series.
14. **Dashboard fetches directly via `services/*`, not its own BFF routes, even though the BFF routes exist.** Same precedent as `DashboardLayout` (decision 12): nothing on this page needs client-side refetching yet. The `organization/stats`/`documents`/`billing/subscription` BFF routes were still built this session, per the plan already recorded in this document — they're for Stage 5/6 and any future client-side interaction on this specific page, not currently exercised by it.
15. **No charting library added — the documents-per-day trend chart is hand-rolled inline SVG.** None was installed yet, and a single-series line chart doesn't need one; the `dataviz` skill's own reference components are plain HTML/SVG by design. Revisit if a later stage needs genuinely complex multi-series charting.
16. **Usage meters use a simplified two-step severity (normal / at-quota), not the `dataviz` skill's literal three-step accent/warning/danger ramp.** This app has no "warning" design token yet (only `--destructive`, for errors) — inventing a whole new token tier for one meter component was out of scope for Stage 2. The meter fill switches to `--destructive` at ≥90% of the plan limit; revisit with a real three-step ramp if a genuine warning-tier need shows up elsewhere.
17. **`billing.service.ts` ships minimal (subscription read only) in Stage 2.** `plans`/`checkout`/`portal` were deliberately left for Stage 6's full Checkout/Portal flow — this session only needed enough to show the current plan + status on the Dashboard.
18. **Incremental TDD, per feature category, is the standing workflow for frontend feature work from Stage 3 onward.** (User decision, §3.9.) Types/contracts → failing tests → minimal implementation → full-workspace verify → next category. Apply this to Stage 4 (Results) and beyond unless told otherwise — it isn't scoped to Upload specifically.
19. **Test boundary is one layer below whatever's under test, never deeper.** (§3.10.) Service tests mock `backendFetch`/`apiFetch`, not `fetch` itself; route tests mock `services/*`, not the services' own internals; component tests mock `apiFetch`, not React Query. Matches the backend's own established testing philosophy (mock the repository layer, not the Supabase client) — re-verifying a lower layer's own correctness in every test above it would be redundant, not more thorough.
20. **Uploads process sequentially, one at a time, never concurrently.** (§3.10, `useUploadController`.) Consistent with the same rate-limiting caution that already drove the polling backoff schedule (§7) — a burst of simultaneous upload requests from one proxying Next.js server is the same category of risk as a burst of poll requests, even though uploads are less frequent than polls.
21. **One `useJobStatus` call per rendered list item (`PolledUploadQueueItem`), not one hook trying to poll N jobs.** (§3.10.) The standard React pattern for "a hook per item in a dynamic list" — hooks can't run inside a loop or conditionally, so each queue item with a `jobId` gets its own component instance and its own independent poll/backoff cycle.
22. **Upload queue state management has zero knowledge of the hooks that talk to the backend.** (§3.10, `features/upload/queue.ts` vs. `use-upload-controller.ts`.) The reducer only knows how to represent and transition queue items; a separate controller hook composes it with `useUploadDocument`/`useJobStatus`. Keeps the reducer trivially testable with plain objects and no network mocking at all.
23. **Document type is chosen per upload *action*, not per queued item.** (§3.10, scope decision.) A `.zip` batch can only carry one type regardless (backend constraint); building per-row type editing for the non-batch multi-file case wasn't asked for and would have meaningfully expanded this slice's scope for a need that hasn't come up yet.
24. **A `.zip` batch's queue item shows its immediate accept/reject breakdown but isn't live-polled sub-job-by-sub-job.** (§3.10.) Tracking potentially many independent per-file polls from the upload page was judged out of scope for Stage 3 — checking on an individual file's outcome after a batch upload is Results/History's job (Stage 4/5).
25. **Any reducer action driven by a reactive/polling effect (not a one-shot event) must explicitly guard against no-op updates and return the exact same state reference when nothing changed.** (§3.11, the bug-fix session.) `useReducer`'s only bail-out mechanism is reference equality — an action that fires repeatedly with frequently-identical data (polling is the paradigm case) will otherwise produce a "new" state every time regardless, which is fine in isolation but becomes a real "Maximum update depth exceeded" risk once anything downstream (an unstable callback, an effect keyed on the resulting prop) reacts to that reference change. `upload-started`/`upload-succeeded`/`upload-failed` don't need this guard — they're genuine one-shot events, not repeating ones — only `job-status-updated` does. Apply the same discipline to any future reducer action with the same "fired repeatedly by a poll/subscription" shape (Results/History, if either ends up polling anything).
26. **`resultJson`'s shape, for Stage 4's field extraction, was verified against the backend's own defensive parsing code and its test fixtures (`apps/backend/src/utils/confidence.ts`/`.test.ts`), not a live Azure Document Intelligence call.** (§3.12.) §9's own point 4 flagged this as unverified going into Stage 4 and asked for a re-check "before assuming a specific field layout" — judged this the most authoritative source actually reachable without spending real Azure credits: it's the one place in the codebase that already has to know `resultJson`'s real shape well enough to defensively compute an average confidence from it, built from real-shaped fixtures. `extract-fields.ts` mirrors its defensive style deliberately (never throws on a malformed/missing field, `isRecord` guards, no assumption the full Azure `DocumentField` union is modeled). Still not the same as a real Azure response — carried forward as a real, stated gap (§7), not silently treated as closed.
27. **Kept `useDocumentPreview`'s effect+setState pattern over the alternatives a new `react-hooks/set-state-in-effect` lint rule implied, with a justified inline disable.** (§3.12.) The rule (from `eslint-plugin-react-hooks@7.1.1`, pulled in transitively via `eslint-config-next`) suggests `useSyncExternalStore` for syncing from external mutable state, which fits reading the cached `File` but not the blob-URL creation+cleanup this hook also does; the render-time alternatives (`useMemo`, a lazy `useState` initializer) have no paired cleanup for React Strict Mode's development-only double-invoke and would leak one blob URL per mount, which the effect's own mount→cleanup→mount double-invoke pairing doesn't. Read the rule's actual source before deciding, rather than either blindly complying (and shipping a real regression) or blindly suppressing (without checking whether the rule had a point). Scope any future use of this same escape hatch narrowly — it's specific to "a resource that needs paired cleanup, derived from a synchronous external read," not a blanket exemption from the rule.
28. **`DocumentPreviewPanel` renders `session-blob`/`remote-url` uniformly through an `<iframe>`, not a type-branched `<img>`/PDF-viewer.** (§3.12.) `DocumentPreviewSource` deliberately carries no MIME type (decision 2) — branching would mean threading file type through as a new prop for a UI gain (a marginally cleaner image preview) that browsers already provide natively inside a frame regardless of file type.
29. **Results lives at `/documents/[jobId]`, not folded into a future History per-row view.** (§3.12, resolves §9's previously-open point 3.) Chosen because it's what this stage's own preview-cache/hook doc comments already assumed while being built, and because a job-detail route reached directly from the upload queue (§3.12's "View results" link) is the more natural product flow than requiring a detour through History first. `documents.service.ts#getJobStatus` (Stage 3, already tested) remains the sole data source — no new backend call was needed.
30. **`@tanstack/react-table` (installed since Stage 0) still isn't used, and Stage 5's History table confirms this wasn't a one-off Stage-4 judgment call.** (§3.13.) Its actually-installed major version (9.0) has a materially different, more complex API than the familiar v8 one the original plan assumed; with no sorting/selection/expansion actually needed for either table built so far, plain HTML `<table>` markup remains the better fit both times. Revisit only if a future table genuinely needs what the library provides.
31. **Human review status (`review_status`) is a completely independent lifecycle from Azure processing status (`status`), never folded into the same column.** (§3.17.) `status` directly drives the frontend's polling logic (`poll-schedule.ts` stops polling on a terminal value) — overloading it with review semantics would mean either new enum values that never affect polling (a status column half of whose values are inert) or breaking the polling contract outright. A job can only leave `review_status: unreviewed` once `status = 'completed'`, enforced in the service layer and backed by a defense-in-depth two-column CHECK constraint at the database level — the same "app logic is primary, a DB constraint backs it up" layering already established for job creation/quota checks elsewhere in this codebase.
32. **Saving a correction on an already-confirmed/rejected job resets it to `unreviewed`, automatically, as part of the same write.** (§3.17.) Without this, a "Confirmed" badge could keep describing data a later, unreviewed edit has already superseded — which is what would make the confirm/reject signal untrustworthy, not just stale-looking. Only the standalone save-without-deciding path resets; confirming/rejecting with an attached corrections payload sets the final status directly, no separate reset-then-set step.
33. **Field corrections are stored as a full, append-only, per-edit audit-history table (`document_field_corrections`), not a simpler "latest value" column on `document_jobs`.** (§3.17, confirmed via `AskUserQuestion` over the lighter, faster-to-ship alternative.) The user explicitly named future audit/history as a first-class requirement, not a nice-to-have; a single "current value" column would have made that structurally impossible to add later without losing everything corrected before the richer table existed, while the richer table costs only slightly more query complexity (a small reduction step to compute "current effective value" from the ordered history) for real, permanent audit capability from day one.
34. **Corrections-endpoint writes are ordered so a partial failure can never leave the system claiming something the data doesn't back up — the write that could make a false claim always goes last.** (§3.17.) Concretely: saving a correction on a confirmed/rejected job resets `review_status` to `unreviewed` *before* inserting the new correction rows (so a failed insert leaves an honestly-unreviewed job, not a stale "confirmed" claim over silently-unsaved edits); confirming/rejecting inserts any accompanying corrections *before* setting the final `review_status` (so a failed status-set leaves the corrections safely saved but the document simply not yet confirmed, never a "confirmed" claim the corrections behind it don't support). Same principle applied twice, in the direction each specific case actually needs it — not a single fixed ordering rule.
35. **Editing/saving/confirming/rejecting is open to any organization member; only the destructive file/document-deletion actions (Phase 2, not yet built) are restricted to the uploader or an org owner/admin.** (§3.17, confirmed via `AskUserQuestion`.) Matches how viewing already works — org-scoped, not uploader-scoped, via the existing `document_jobs_select_same_org` RLS policy and `getDocumentJobForOrganization`'s own lookup — and supports the realistic case where the person reviewing a document isn't the person who uploaded it. Reversible, non-destructive actions don't need the stricter gate destructive ones do.
36. **`GET .../corrections` is a separate endpoint, not fields on the shared `JobDto`.** (§3.17.) Computing "effective value per field" needs an extra query against `document_field_corrections` — cheap for one job, but `toJobDto` is also used by `GET /documents` (list, up to 100 rows/page); folding it into the shared DTO would mean either an N+1 query on every list load or a dishonest always-empty placeholder for list items. `reviewStatus`/`reviewedAt`/`reviewedBy` stay on the base DTO regardless, since they're plain already-fetched columns with no such cost — only the derived, per-correction data gets its own endpoint, mirroring the same reasoning that already kept the Part-1 preview-url endpoint separate from the job DTO (decision 2's Stage-4/Part-1 evolution).
37. **`@tnda-ai/shared` stays unpopulated even though Phase 1 needed the exact kind of small cross-cutting utility (an Azure-field-value lookup) it was scaffolded for.** (§3.17.) The package is still completely unimported and not declared as a dependency of either app — wiring it up for real (adding it to both `package.json`s, confirming both Bun and Next.js/Turbopack resolve a TS-source workspace package without extra config) is a genuine first-time integration step, disproportionate for one ~10-line function. Duplicated it instead, with a dated comment pointing at the original — the same proportionality call already made for `DOCUMENT_TYPES` (decision 9's original reasoning still holds) and `isMarkdownContent` (decision 39, below). Revisit `@tnda-ai/shared` if a third consumer, or a genuinely larger shared need, shows up.
38. **Storage upload (Part 1) is deliberately non-fatal, same tier of caution as this codebase's existing quota/plan checks.** (§3.15.) A storage hiccup during upload is caught, logged, and the flow proceeds straight to Azure submission regardless — `storage_path` simply stays `null`. A user getting their extracted data is judged more important than the original file also being retrievable later; the preview UI already has an honest `unavailable` state for exactly this case, so nothing is silently hidden.
39. **`DocumentPreviewSource` gained a fourth variant, `loading`, distinguishing "don't know yet" from "confirmed nothing exists."** (§3.15, extends decision 2.) Found and fixed proactively while implementing Part 1, not present in the original plan: without it, a reloaded or History-opened job would flash "Preview unavailable" for a moment before its real signed-URL preview arrived, since both "still fetching" and "confirmed empty" collapsed onto the same `unavailable` state. TanStack Query's `isPending` is what distinguishes the two now.
40. **Markdown rendering (Part 2) is scoped by document type, not applied universally to `content`.** (§3.16.) Only `generic` documents actually receive Markdown from Azure (`documents.strategy.ts` requests `outputContentFormat=markdown` for that type alone) — running the other three types' plain OCR text through a Markdown parser risks misinterpreting incidental characters (a line starting with `"- "`, a stray `#`/`_` in an address or ID number) as formatting instead of literal content. `extract-fields.ts#isMarkdownContent(documentType)` makes the split explicit and hand-mirrors the backend's own per-type routing table, the same established convention as `DOCUMENT_TYPES`.
41. **Raw content collapses behind a native `<details>/<summary>` whenever structured fields also exist, full prominence only when they don't.** (§3.16.) Fixes a real, previously-unnoticed bug (`DocumentResultsView` was showing both at equal prominence for all four document types, contradicting a stale code comment that claimed otherwise) and matches the Results page's stated direction as a review screen: structured fields are the primary editable surface for field-shaped types; raw content is a secondary "compare against the source" reference, and is the *only* extracted content there is for `generic`, where it stays prominent. No new dependency — a native disclosure element, consistent with this codebase's precedent of reaching for a plain HTML primitive before a new one.
42. **`DocumentFieldsTable` is always directly editable — no separate view/edit-mode toggle.** (§3.17.) The Results page's stated purpose is now a document *review* workspace, where correcting a value is the core action, not an occasional one; requiring an extra click to "enter edit mode" first would be pure friction with no corresponding benefit, unlike a form where accidental edits are a real risk (they aren't here — nothing saves until "Save corrections"/"Confirm"/"Reject" is explicitly clicked).
43. **`react-hook-form` was not reused for the field-corrections form, despite being the established pattern for this app's two other forms (login/signup).** (§3.17.) RHF earns its keep there through schema-driven validation (`zodResolver`) against a fixed, known-ahead-of-time field set. Neither holds for corrections: the field set is dynamic and Azure-determined (a different, variable-length list per document), and a corrected value has no real validation rule to enforce beyond "an arbitrary replacement string." A plain `useState` draft, diffed for a dirty check, covers what's actually needed without the added surface area.

## 7. Technical Debt & Known Limitations

Inherited from the backend's own build (see `apps/backend/PROGRESS.md` §15 for the full list) — the ones most relevant to frontend work:
- **No team/role-management endpoints** (`profiles.role` exists, no invite/change-role route) — Settings (Stage 7) should not build non-functional UI for this.
- **No background job worker** — `GET /documents/jobs/:id` polls Azure synchronously, on-demand. The frontend's polling-with-backoff design (built in Stage 3, §3.10 — `getNextPollInterval`) is load-bearing here, not just nice-to-have UX: the backend's rate limiter is IP-keyed and becomes a bucket shared across all users once every call is proxied through one Next.js server. This can be managed (backoff) but not fixed from the frontend — see the original plan file's Auth section for the full reasoning.
- **Rate limiting is single-instance/in-memory** on the backend — fine for now, would need a shared store before horizontal scaling.
- **`.zip` batches have one `documentType` for the whole archive**, not per-file.
- New from this session:
  - `packages/types`/`packages/shared` are empty scaffolds (§4, decision 9) — don't be surprised they're unpopulated; that's intentional.
  - ~~Frontend has no test suite yet~~ — no longer true as of Stage 3 (§3.9-3.10): `vitest` + Testing Library, 90 tests. Stages 1-2's own work is still untested by unit tests (verified via `curl` only, at the time) — retrofitting those isn't planned, only called out here so it's not mistaken for an oversight if noticed.
  - Multi-tab logout is eventually-, not immediately, consistent (a second open tab discovers logout on its next request, not instantly) — accepted default, documented in the frontend's original plan.
  - Dashboard's trend chart has no date-range control yet — always the backend's default 30-day window. The `organization/stats` BFF route already accepts `?since=` (it just passes the query param through), so this is a UI-only gap, not blocked on backend work, if a later stage wants it.
  - Usage meters' two-step severity, and `billing.service.ts`'s minimal scope, are deliberate Stage 2 simplifications, not oversights — see §4 decisions 16-17.
  - **New from Stage 3** (§3.10, §4 decisions 20/23/24 for the reasoning behind each):
    - No retry UI for a failed upload yet — the item just sits `upload-failed`/`failed` with its error message; the user can remove it and re-drop the same file, but there's no one-click "try again."
    - Document type is chosen per upload action, not per queued item — see §4 decision 23 if per-file type editing is ever wanted for a multi-file (non-`.zip`) drop.
    - A `.zip` batch's individual accepted sub-jobs aren't live-polled from the upload page — see §4 decision 24. Checking on one after the fact means Results/History (Stage 4/5), not this page.
    - No byte-level upload progress bar — `fetch` doesn't expose upload progress the way `XMLHttpRequest` does; would need switching the upload call to `XMLHttpRequest` (or a library wrapping it) specifically to get a real percentage, which wasn't judged worth the complexity for Stage 3.
  - **New from Stage 4** (§3.12, §4 decisions 26-29 for the reasoning behind each):
    - `resultJson`'s field shape is verified against the backend's own defensive-parsing code and its test fixtures, not a real Azure Document Intelligence response (§4 decision 26) — a real call could still reveal a shape `extract-fields.ts` doesn't handle as gracefully as intended. `extract-fields.ts` is defensive/non-throwing by design either way, so the worst case is silently showing fewer fields than exist, not a crash — but worth re-checking against a real response once one exists.
    - `DocumentPreviewPanel` renders every file type through a uniform `<iframe>` (§4 decision 28) — no dedicated image viewer, zoom, or PDF-specific controls (page navigation, etc.); relies entirely on the browser's own built-in handling of whatever's inside the frame.
    - The "View results" link on a completed upload-queue item only appears for a single-file upload — a `.zip` batch has no per-sub-job `jobId` on the client to link to (same limitation as live sub-job polling, §4 decision 24). Checking an individual batch sub-job's results after the fact is still Results/History's unbuilt job, not this link's.
  - **New from Stage 5 / Part 1 / Part 2 / review-workflow Phase 1** (§3.13-§3.17):
    - Jobs uploaded before migration `0011` have `storage_path = null` permanently — there's no original file to backfill, and their preview falls back to session-cache-or-unavailable exactly as it did before Part 1 (§3.15). Stated plainly, not a silent gap.
    - `@tnda-ai/shared` remains unpopulated (§4 decision 37) even though Phase 1 hit a real case it was scaffolded for — a small field-value-lookup helper is duplicated between backend and frontend instead, hand-kept-in-sync with a dated comment. Revisit if a third consumer or a larger shared need shows up.
    - The document review workflow's edit/confirm/reject actions have **no rejection reason field** and **no per-field "who corrected this" surfaced in the UI** (the data exists — `edited_by`/`edited_at` on every `document_field_corrections` row, `reviewed_by`/`reviewed_at` on the job — but nothing renders it yet; there's also no org-members-list endpoint anywhere in this backend to resolve a uuid to a display name against, a pre-existing gap, not new this session). Both are cheap, additive future work, not architectural blockers.
    - **Phase 2 (remove file / delete document) and Phase 3 (Documents-list actions) of the review-workflow redesign are designed but not built** — see §9. The Documents list still only has a "View" action; there is still no way to delete a document or remove just its original file from the UI.
    - No `Dialog`/`AlertDialog` primitive exists anywhere in the frontend yet (only `sheet.tsx`, used for the sidebar's mobile drawer) — a real, identified prerequisite for Phase 2's destructive-action confirmation, not something Phase 2 can skip past.

### Exact next milestone: Phase 2 of the review-workflow redesign — file lifecycle

The approved plan (still on disk if a fresh read is ever needed) sequences: Phase 1 (done, §3.17) → **Phase 2 — remove original file / delete document** → Phase 3 — Documents-list actions (a delete/remove-file menu, a review-status badge). Phase 2's design is already settled, from the plan the user approved before Phase 1 started:

- **Two independent actions**: "remove original file" (hard-deletes the Storage object via the already-implemented-but-unused `storage.service.ts#deleteDocumentFile`, sets `storage_path = null`, leaves everything else on the row untouched, idempotent if already null) and "delete document" (soft-deletes the job row — a new `deleted_at timestamptz` column, migration `0013` — **and** removes the file at the same time; the row and all its data, including `result_json` and the full correction history, are always preserved).
- **New migration `0013_document_soft_delete.sql`**: `deleted_at` only. `.is("deleted_at", null)` needs to be added to `listDocumentJobsForOrganization` and `getDocumentJobForOrganization` (`documents.repository.ts`) — but **must never** be added to `getMonthlyPagesUsed`/`getDocumentsSubmittedSince` (`organization.repository.ts`, the quota pre-flight check): quota counts what was submitted in a billing period, not what's currently visible, and deleting a job must never retroactively free up quota. This is the one place a reflexive "add the filter everywhere `document_jobs` is queried" instinct would be wrong.
- **New endpoints**: `DELETE /jobs/:id/file`, `DELETE /jobs/:id` — both restricted to the job's uploader or an org owner/admin (`ForbiddenError`, defined in `utils/errors.ts` since early in this project but still completely unused anywhere — Phase 2 is its first real usage), unlike Phase 1's any-org-member model for edit/confirm/reject (§4 decision 35).
- **A real, identified prerequisite, not optional polish**: no `Dialog`/`AlertDialog` primitive exists in this frontend yet (§7) — `radix-ui` (already a dependency, already used this same way for `DropdownMenu` in `UserMenu.tsx`) has one; a small `components/ui/alert-dialog.tsx` wrapper needs to exist before a real "are you sure?" confirmation can gate either delete action.
- Follow the same TDD-first workflow as Phase 1 (§4 decision 18) — types/schema, failing tests, minimal implementation, full-workspace verify — and the same wait-for-manual-browser-verification-before-PROGRESS.md/commit pattern this entire project has used consistently.
