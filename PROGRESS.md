### 3.8 Stage 2 close-out review

Before committing, asked to review every uncommitted change once more rather than take the prior pass as final — this caught two real issues that a second, more skeptical read surfaces and a first implementation pass didn't:

- **`UsageMeter` used `role="progressbar"` with an unclamped `aria-valuenow`.** A progress bar is semantically "an operation running to completion" — usage-vs-quota is a scalar measurement within a known range, which is ARIA's `role="meter"` (the dataviz skill's own name for this component, too). Also, `documentsUsed`/`pagesUsed` are plain counts, not clamped to the plan limit — an org that used to be on a higher plan and downgraded (or any future edge case producing `used > limit`) would have pushed `aria-valuenow` past `aria-valuemax`, which is invalid per the ARIA spec. Fixed: `role="meter"`, `aria-valuenow` clamped to `Math.min(used, limit)`, and an explicit `aria-valuetext` so the real (possibly over-limit) numbers are still what gets announced.
- **The empty-state gate only checked `stats.totalJobs`, which counts terminal (completed/failed) jobs only.** Verified directly against `0010_document_analytics.sql`: `get_organization_daily_job_counts` and `get_organization_job_stats` share the exact same `where ... and status in ('completed', 'failed')` clause, so `dailyCounts` and `totalJobs` are always consistent with each other — that part was already correct. But an org with a job still `pending`/`processing` (uploaded, not yet resolved) would have `totalJobs === 0` and see "No documents yet," which is misleading once Stage 3 makes that a reachable real state. `usage.documentsUsed` (from `/organizations/me`, already fetched on this page) counts `pending`/`processing`/`completed` — cheap, already-available signal to add. Gate is now `stats.totalJobs === 0 && usage.documentsUsed === 0`.
- **Noted, not changed**: `apps/frontend/PROGRESS.md`'s Stage 0 section says the plan anticipated "shadcn's own chart primitives" (i.e. shadcn's `chart.tsx`, built on Recharts) specifically so charts would share the same `--chart-1..5` token system as the rest of the theme. ### 3.11 Stage 3 bug fix — "Maximum update depth exceeded" on upload

The user manually ran both apps in a real browser (per §3.10's own plan) and hit a real crash uploading a document — the exact class of bug §3.10's own tests couldn't have caught, since it's a pure client-side render loop, invisible to every verification method available in this environment (curl included). Told explicitly to diagnose root cause, not patch superficially, and to determine whether it was effect dependencies, unstable callback identities, or unnecessary reducer dispatches.

**Diagnosis.** Traced the real data flow: `PolledUploadQueueItem`'s effect (`useEffect(() => { if (data) onStatusUpdate(data); }, [data, onStatusUpdate])`) called `onStatusUpdate` on every poll — but `onStatusUpdate` was a *fresh closure on every render*, at two compounding levels: `UploadQueueList` rebuilt a per-item wrapper (`(job) => onStatusUpdate(item.id, job)`) and `UploadWorkspace` rebuilt the dispatch call itself, both inline, both every render. Combined with `uploadQueueReducer`'s `job-status-updated` case unconditionally building a new array via `.map()` regardless of whether the incoming job data actually differed from what was already stored, this is the textbook shape of the bug: effect fires → dispatch → new array reference (even when nothing changed) → re-render → callback identity changes → effect fires again. Confirmed this is real, not just plausible, by temporarily instrumenting the reducer directly (a throwaway `console.log` inside it, removed before committing) and counting invocations during a sustained "job stuck at the same status" scenario: significantly more `job-status-updated` dispatches fired than real polls could justify (roughly 1.75x with a single item, exactly 2x under `React.StrictMode` — matching its documented double-invocation behavior, not a sign of anything additional — and scaling linearly, not multiplicatively, with a second simultaneously-polling item).

**What didn't reproduce, and why that's stated plainly rather than hidden**: tried to reproduce the literal "Maximum update depth exceeded" crash in an integration test — five variations (a bare re-render loop, `React.StrictMode`, freshly-varying poll responses to defeat React Query's default structural sharing, two simultaneously-polling items) — none crossed React's actual update-depth threshold inside this jsdom/Vitest environment, despite the underlying redundant-dispatch pattern being real and directly measured. Rather than force a fragile, environment-sensitive repro (or worse, quietly claim one that doesn't actually prove anything), the regression tests target the *precise, deterministic property* that has to hold instead — see below.

**Fix — two parts, one primary**:
1. **(Primary, directly satisfies the user's stated goal)** `uploadQueueReducer`'s `job-status-updated` case now returns the exact same state reference — no new array, no new item object — when the incoming job's `status` and `errorMessage` match what's already stored for that item (or when the target id doesn't exist in the queue at all). `useReducer` only bails out of scheduling a re-render when the *identical* reference comes back; returning an equal-but-new array every time (the previous behavior) meant a job legitimately sitting at one status across many polls never gave React a chance to stop.
2. **(Secondary, addresses the callback-identity contributing cause directly)** Stopped constructing a new `onStatusUpdate` closure on every render at two separate levels. `PolledUploadQueueItem` now takes `onStatusUpdate: (id, job) => void` and curries `item.id` itself (a prop it already has) instead of `UploadQueueList` pre-currying it into a fresh per-item closure every render; `UploadWorkspace` wraps its dispatch call in `useCallback` keyed on `queue.dispatch` (stable — `useReducer`'s dispatch never changes identity), not the whole `queue` object (a fresh reference every render, which would have defeated the memoization).

Both matter: the reducer fix is what makes the crash-driving cascade actually *stop* once started (the semantically correct, primary fix); the callback fix means the effect doesn't fire more than necessary in the first place, which was real, measured, wasted work independent of whether it happened to cross a crash threshold.

**Regression tests** (`features/upload/queue.test.ts`): dispatching `job-status-updated` with status/errorMessage unchanged returns the exact same array reference (`toBe`, not `toEqual` — reference identity is the entire point); dispatching with only `errorMessage` different still returns a new reference (confirms the fix doesn't silently swallow real changes); dispatching for an unknown id also returns the same reference (tightens existing no-op coverage to check identity, not just value equality). `components/upload/UploadWorkspace.test.tsx` keeps an integration-level sanity test (renders the real composed tree, sustained identical-status polling, asserts no throw) — explicitly documented in its own comment as a sanity check, not the primary proof, given the reproduction difficulty above.

**Verification**: full workspace `typecheck`/`lint`/`test` green (94 backend + 94 frontend — 4 new tests). Re-ran the real curl-based `/upload` check (fresh signup, real backend + Supabase) to confirm no server-rendering regression — but stated plainly that this cannot verify the actual fix, since the bug is a pure client-side render-loop with no server-rendered signature at all. Asked the user to confirm in their own browser, where they originally found it — that's the only real verification available for this specific class of bug in this environment.

**Closed the loop**: the user re-tested in a real browser afterward and confirmed it directly — uploaded a document, no more "Maximum update depth exceeded," no React warnings in DevTools, upload completed and polling behaved correctly. This is the actual, authoritative verification for this bug; everything above it (the reducer-level reference-equality tests, the curl check) was the closest available substitute until this confirmation landed.

## 4. Architectural Decisions (what, and why)

1. **Backend is the single source of truth; frontend never queries Supabase directly for application data.** (User decision, §3.4.) Supersedes the original plan's resolution for backend gaps #1/#5 (frontend-side RLS reads for History/stats) — those are now real backend endpoints instead (§8). The one exception, deliberately not a violation of this rule: `@supabase/ssr` for session/cookie management is identity plumbing (the same category as the backend talking to Supabase Auth directly for token verification), not an application-data query.
2. **Session-only document preview, behind a swappable abstraction.** (User decision.) The backend never persists uploaded files; a persistent preview isn't achievable without new infrastructure, and isn't needed for the immediate upload→results flow that matters for v1. Built behind a `DocumentPreviewSource` union type (`session-blob | remote-url | unavailable`) specifically so a persistent backend-provided URL can replace it later without touching any UI component — an explicit requirement, not an implementation nicety. **Implemented in Stage 4** (§3.12): `session-blob` via a module-level `jobId -> File` cache + `URL.createObjectURL`; `remote-url` still has no producer (unchanged — the backend still doesn't persist files); `unavailable` is the real fallback for any job reached outside the immediate post-upload flow.
3. **`@supabase/ssr` hybrid auth session model.** Backend still owns signup/login orchestration (org+profile creation, with rollback) — bypassing it would leave orphaned `auth.users` rows. Immediately after, `setSession()` hydrates an `@supabase/ssr` server client, which then owns cookie/refresh lifecycle. Refresh centralized in `proxy.ts` (Server Components can't write cookies themselves). Logout calls `signOut()` for real server-side revocation, not just cookie clearing. `SameSite=Lax`, deliberately — `Strict` would drop the session cookie on the top-level GET redirect back from Stripe Checkout, silently logging the user out right after they pay.
4. **Hand-written Zod schemas + `AssertExact`, not Eden/openapi-typescript.** Both alternatives were tried and don't work (§3.3) — this isn't a fallback chosen for convenience, it's the only approach that actually functions given the two projects' independent `tsconfig`s and the backend's broken Swagger JSON output. Arguably *stronger* than either alternative would have been: real runtime validation at every call site, not just a compile-time promise.
5. **Keyset (cursor) pagination over offset, for `GET /documents`.** Offset pagination (`.range()`) drifts under concurrent inserts — a real case here, since a batch upload can add rows while someone's paging through their own history. Cursor is on `created_at` alone (no `id` tiebreaker) — a compound cursor would need Supabase's `.or()` raw-filter-string DSL, meaning decoded client-supplied cursor content would be interpolated into a filter *expression* rather than a filter *value*. Accepted trade: two jobs created in the exact same instant could theoretically land on opposite sides of a page boundary — rare enough (each row is a separate awaited round trip) not to be worth the larger attack surface. Cursor is opaque on the wire (base64url); a malformed one is treated as "first page," not an error.
6. **`successRate`/`averageConfidence`/etc. are `null`, never a fabricated `0`, when there's no data to compute them from.** A `0` success rate reads as "100% failure" when the honest state is "no data yet"; `generic` documents (Azure's `prebuilt-layout` model) have no per-field confidence at all, and forcing a `0` there would be a lie, not a default.
7. **Stats' daily-count series is gap-filled server-side, in the service layer**, not left sparse for clients to reconstruct. The Postgres function only returns days with actual activity; a day missing from that result is indistinguishable from "no data at all" to a client that doesn't know the query's internals — filling every day once, in one place, means every consumer gets a complete, chart-ready series.
8. **No history rewrite for the monorepo migration — verified, not assumed.** `git filter-repo` was the first instinct; asked to justify it against a simpler move-and-commit approach, that simpler approach was proven (in a throwaway repo, against a real bare "remote," before touching the real one) to preserve every commit hash unchanged, push as an ordinary fast-forward, and support `git log --follow`/`git blame` correctly across the move. No force-push anywhere in this migration.
9. **`packages/types`/`packages/shared` are scaffolded and workspace-wired, but deliberately left empty.** The backend's schemas are Zod v3, the frontend's are Zod v4 (an already-made, deliberate choice — not an oversight); backend code assumes Bun-only APIs in places. Moving code into a shared package now wouldn't remove the need for the hand-verification work already done, just relocate it. Real future sharing is a *deliberate* decision to make later, not a speculative one to force now.
10. **CSRF is covered by `SameSite=Lax` + all-mutations-are-POST, deliberately, not a token.** `SameSite=Lax` already withholds the cookie on cross-site subrequests; combined with every mutating route being POST, that closes the practical gap without adding a separate mechanism.
11. **No optimistic updates in the frontend, for now — considered per-feature, not a gap.** Checked against every real mutation in the app (upload-queue entries are already transient client-only state; "mark as reviewed" is explicitly local-only since there's no backend field to persist it to yet; a plan change redirects to Stripe and can't be optimistically shown; History has no mutations at all). Recorded so this reads as a considered decision if revisited later.
12. **Call paths are fixed and enforced, not just documented, in the frontend.** Server Components import `services/*.service.ts` directly (in-process); Client Components only reach the same code indirectly through this app's own `/api/*` Route Handlers. Every file under `services/` starts with `import "server-only"` so an accidental Client Component import fails the build instead of silently risking a path to tokens in a client bundle.
13. **Chart color is the `dataviz` skill's validated default (blue), not invented, and validated against this app's real surfaces.** (Stage 2, §3.7.) This theme (`shadcn init`'s neutral base) had never used a real hue before — `--chart-1..5` were unpopulated grays. Rather than eyeball a brand color, used the skill's documented default categorical slot 1 and ran `scripts/validate_palette.js` against this app's *actual* computed card-surface hex in both modes (derived from its `oklch()` tokens, not the skill's own example surfaces) before trusting it. Only `--chart-1` was repopulated — `chart-2..5` stay gray placeholders until a chart actually needs a second series.
14. **Dashboard fetches directly via `services/*`, not its own BFF routes, even though the BFF routes exist.** Same precedent as `DashboardLayout` (decision 12): nothing on this page needs client-side refetching yet. The `organization/stats`/`documents`/`billing/subscription` BFF routes were still built this session, per the plan already recorded in this document — they're for Stage 5/6 and any future client-side interaction on this specific page, not currently exercised by it.
15. **No charting library added — the documents-per-day trend chart is hand-rolled inline SVG.** None was installed yet, and a single-series line chart doesn't need one; the `dataviz` skill's own reference components are plain HTML/SVG by design. Revisit if a later stage needs genuinely complex multi-series charting.
16. **Usage meters use a simplified two-step severity (normal / at-quota), not the `dataviz` skill's literal three-step accent/warning/danger ramp.** This app has no "warning" design token yet (only `--destructive`, for errors) — inventing a whole new token tier for one meter component was out of scope for Stage 2. The meter fill switches to `--destructive` at ≥90% of the plan limit; revisit with a real three-step ramp if a genuine warning-tier need shows up elsewhere.
17. **`billing.service.ts` ships minimal (subscription read only) in Stage 2.** `plans`/`checkout`/`portal` were deliberately left for Stage 6's full Checkout/Portal flow — this session only needed enough to show the current plan + status on the Dashboard.
18. **Incremental TDD, per feature category, is the standing workflow for frontend feature work from Stage 3 onward.** (User decision, §3.9.) Types/contracts → failing tests → minimal implementation → full-workspace verify → next category. Apply this to Stage 4 (Results) and beyond unless told otherwise — it isn't scoped to Upload specifically.
19. **Test boundary is one layer below whatever's under test, never deeper.** (§3.10.) Service tests mock `backendFetch`/`apiFetch`, not `fetch` itself; route tests mock `services/*`, not the services' own internals; component tests mock `apiFetch`, not React Query. Matches the backend's own established testing philosophy (mock the repository layer, not the Supabase client) — re-verifying a lower layer's own correctness in every test above it would be redundant, not more thorough.
20. **Uploads process sequentially, one at a time, never concurrently.** (§3.10, `useUploadController`.) Consistent with the same rate-limiting caution that already drove the polling backoff schedule (§7) — a burst of simultaneous upload requests from one proxying Next.js server is the same category of risk as a burst of poll requests, even though uploads are less frequent than polls.
21. **One `useJobStatus` call per rendered list item (`PolledUploadQueueItem`), not one hook trying to poll N jobs.** (§3.10.) The standard React pattern for "a hook per item in a dynamic list" — hooks can't run inside a loop or conditionally, so each queue item with a `jobId` gets its own component instance and its own independent poll/backoff cycle.
22. **Upload queue state management has zero knowledge of the hooks that talk to the backend.** (§3.10, `features/upload/queue.ts` vs. `use-upload-controller.ts`.) The reducer only knows how to represent and transition queue items; a separate controller hook composes it with `useUploadDocument`/`useJobStatus`. Keeps the reducer trivially testable with plain objects and no network mocking at all.
23. **Document type is chosen per upload *action*, not per queued item.** (§3.10, scope decision.) A `.zip` batch can only carry one type regardless (backend constraint); building per-row type editing for the non-batch multi-file case wasn't asked for and would have meaningfully expanded this slice's scope for a need that hasn't come up yet.
24. **A `.zip` batch's queue item shows its immediate accept/reject breakdown but isn't live-polled sub-job-by-sub-job.** (§3.10.) Tracking potentially many independent per-file polls from the upload page was judged out of scope for Stage 3 — checking on an individual file's outcome after a batch upload is Results/History's job (Stage 4/5).
25. **Any reducer action driven by a reactive/polling effect (not a one-shot event) must explicitly guard against no-op updates and return the exact same state reference when nothing changed.** (§3.11, the bug-fix session.) `useReducer`'s only bail-out mechanism is reference equality — an action that fires repeatedly with frequently-identical data (polling is the paradigm case) will otherwise produce a "new" state every time regardless, which is fine in isolation but becomes a real "Maximum update depth exceeded" risk once anything downstream (an unstable callback, an effect keyed on the resulting prop) reacts to that reference change. `upload-started`/`upload-succeeded`/`upload-failed` don't need this guard — they're genuine one-shot events, not repeating ones — only `job-status-updated` does. Apply the same discipline to any future reducer action with the same "fired repeatedly by a poll/subscription" shape (Results/History, if either ends up polling anything).
26. **`resultJson`'s shape, for Stage 4's field extraction, was verified against the backend's own defensive parsing code and its test fixtures (`apps/backend/src/utils/confidence.ts`/`.test.ts`), not a live Azure Document Intelligence call.** (§3.12.) §9's own point 4 flagged this as unverified going into Stage 4 and asked for a re-check "before assuming a specific field layout" — judged this the most authoritative source actually reachable without spending real Azure credits: it's the one place in the codebase that already has to know `resultJson`'s real shape well enough to defensively compute an average confidence from it, built from real-shaped fixtures. `extract-fields.ts` mirrors its defensive style deliberately (never throws on a malformed/missing field, `isRecord` guards, no assumption the full Azure `DocumentField` union is modeled). Still not the same as a real Azure response — carried forward as a real, stated gap (§7), not silently treated as closed.
27. **Kept `useDocumentPreview`'s effect+setState pattern over the alternatives a new `react-hooks/set-state-in-effect` lint rule implied, with a justified inline disable.** (§3.12.) The rule (from `eslint-plugin-react-hooks@7.1.1`, pulled in transitively via `eslint-config-next`) suggests `useSyncExternalStore` for syncing from external mutable state, which fits reading the cached `File` but not the blob-URL creation+cleanup this hook also does; the render-time alternatives (`useMemo`, a lazy `useState` initializer) have no paired cleanup for React Strict Mode's development-only double-invoke and would leak one blob URL per mount, which the effect's own mount→cleanup→mount double-invoke pairing doesn't. Read the rule's actual source before deciding, rather than either blindly complying (and shipping a real regression) or blindly suppressing (without checking whether the rule had a point). Scope any future use of this same escape hatch narrowly — it's specific to "a resource that needs paired cleanup, derived from a synchronous external read," not a blanket exemption from the rule.
28. **`DocumentPreviewPanel` renders `session-blob`/`remote-url` uniformly through an `<iframe>`, not a type-branched `<img>`/PDF-viewer.** (§3.12.) `DocumentPreviewSource` deliberately carries no MIME type (decision 2) — branching would mean threading file type through as a new prop for a UI gain (a marginally cleaner image preview) that browsers already provide natively inside a frame regardless of file type.
29. **Results lives at `/documents/[jobId]`, not folded into a future History per-row view.** (§3.12, resolves §9's previously-open point 3.) Chosen because it's what this stage's own preview-cache/hook doc comments already assumed while being built, and because a job-detail route reached directly from the upload queue (§3.12's "View results" link) is the more natural product flow than requiring a detour through History first. `documents.service.ts#getJobStatus` (Stage 3, already tested) remains the sole data source — no new backend call was needed.

## 7. Technical Debt & Known Limitations

Inherited from the backend's own build (see `apps/backend/PROGRESS.md` §15 for the full list) — the ones most relevant to frontend work:
- **No team/role-management endpoints** (`profiles.role` exists, no invite/change-role route) — Settings (Stage 7) should not build non-functional UI for this.
- **No background job worker** — `GET /documents/jobs/:id` polls Azure synchronously, on-demand. The frontend's polling-with-backoff design (built in Stage 3, §3.10 — `getNextPollInterval`) is load-bearing here, not just nice-to-have UX: the backend's rate limiter is IP-keyed and becomes a bucket shared across all users once every call is proxied through one Next.js server. This can be managed (backoff) but not fixed from the frontend — see the original plan file's Auth section for the full reasoning.
- **Rate limiting is single-instance/in-memory** on the backend — fine for now, would need a shared store before horizontal scaling.
- **`.zip` batches have one `documentType` for the whole archive**, not per-file.
- New from this session:
  - `packages/types`/`packages/shared` are empty scaffolds (§4, decision 9) — don't be surprised they're unpopulated; that's intentional.
  - ~~Frontend has no test suite yet~~ — no longer true as of Stage 3 (§3.9-3.10): `vitest` + Testing Library, 90 tests. Stages 1-2's own work is still untested by unit tests (verified via `curl` only, at the time) — retrofitting those isn't planned, only called out here so it's not mistaken for an oversight if noticed.
  - Multi-tab logout is eventually-, not immediately, consistent (a second open tab discovers logout on its next request, not instantly) — accepted default, documented in the frontend's original plan.
  - Dashboard's trend chart has no date-range control yet — always the backend's default 30-day window. The `organization/stats` BFF route already accepts `?since=` (it just passes the query param through), so this is a UI-only gap, not blocked on backend work, if a later stage wants it.
  - Usage meters' two-step severity, and `billing.service.ts`'s minimal scope, are deliberate Stage 2 simplifications, not oversights — see §4 decisions 16-17.
  - **New from Stage 3** (§3.10, §4 decisions 20/23/24 for the reasoning behind each):
    - No retry UI for a failed upload yet — the item just sits `upload-failed`/`failed` with its error message; the user can remove it and re-drop the same file, but there's no one-click "try again."
    - Document type is chosen per upload action, not per queued item — see §4 decision 23 if per-file type editing is ever wanted for a multi-file (non-`.zip`) drop.
