# Background Job Claiming: Postgres Row-Locking via RPC, Not a Message Queue

## Status

Accepted

## Context

Wave 3's stated goal (`docs/document-domain-architecture.md`) is to move document processing out of the HTTP request lifecycle into a durable background-processing mechanism, without depending on a browser tab staying open. That requires a safe way for one or more worker processes to claim a `document_jobs` row for exclusive processing, survive a worker crash without a job getting stuck forever, and eventually support retrying a job that failed transiently — all while never letting two workers process the same job concurrently, and never letting a worker touch another organization's job by mistake.

A full architecture review (a separate design-review pass, not implementation) considered the realistic options for this specifically:

- **A dedicated message broker** (Redis, BullMQ, SQS, Kafka) — new infrastructure, new credentials, a new failure mode to operate, no local-dev story this project already has. Nothing about this system's actual current scale (a single-tenant-scale dev project with no measured production load) demonstrates a concrete requirement a Postgres-based queue can't satisfy.
- **Postgres-backed claiming via `SELECT ... FOR UPDATE SKIP LOCKED`** — a standard, well-documented pattern for exactly this problem, using infrastructure this project already depends on hard (Supabase/Postgres), and extending a pattern this codebase already has real precedent for: four existing Postgres functions (`get_organization_monthly_usage`, `get_organization_job_stats`, `get_organization_daily_job_counts`, `current_organization_id`), all called via `supabaseAdmin.rpc(...)` from the repository layer, for exactly the same underlying reason — a query shape PostgREST's REST interface can't express directly.

Postgres was chosen. This ADR records the concrete shape that decision took in Phase 1's actual implementation.

## Decision

**Claim state lives directly on `document_jobs`** (`claimed_by`, `claimed_at`, `lease_expires_at`, `lease_epoch`, `next_attempt_at`), not a separate claims/leases table — the same orthogonal-attribute pattern this schema already uses repeatedly (`deleted_at`, `review_status`/`reviewed_by`, `retry_count`/`is_retryable`): a new, independently-nullable attribute set on the existing row, not a new state machine or a new table to keep in sync.

**A single Postgres function, `claim_or_renew_document_job(p_worker_id, p_lease_seconds, p_max_retries)`, handles both claiming and renewal.** It first attempts to renew an existing claim held by the caller (keyed on `claimed_by = p_worker_id` with a live lease); only if that finds nothing does it attempt to claim a new row, via `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1` inside an `UPDATE ... WHERE id = (subquery)`. This is what makes two concurrent claim calls structurally unable to pick the same row — not a probabilistic guarantee, a transactional one.

**`p_worker_id` identifies one claim slot, not a worker process.** The renew-vs-claim-new decision is purely "does a row already have `claimed_by = p_worker_id`" — a worker holding more than one job at once (`WORKER_CONCURRENCY > 1`, per the approved design) must mint a distinct id per concurrently-held job, not reuse its own process id for all of them, or a renewal call would silently renew every job that process holds instead of claiming a new one. This was caught during this phase's own independent review, before anything was applied, and is documented directly on the `claimed_by` column and the function itself so a later phase implementing the actual worker doesn't rediscover it as a live bug.

**`lease_epoch` is a fencing token**, incremented only when a job is claimed fresh (including a former holder reclaiming after losing its lease), never on a plain renewal. A worker's own claimed_by no longer matching (because someone else reclaimed the row) is what makes a stale worker's renewal attempt correctly fail — proven empirically during this phase's verification, not just reasoned about. The epoch exists for a different, not-yet-exercised purpose: a later phase's writes based on a held claim (persisting an Azure operation id, marking a result) should condition themselves on the epoch matching what the worker was given at claim time, so a worker that silently lost its lease mid-processing fails to write instead of clobbering the new holder's work — verified in this phase by simulating exactly that write pattern (an epoch-gated `UPDATE`) and confirming it affects zero rows once the epoch has moved on.

**Claiming a `failed`, retryable row performs its retry transition atomically in the same statement**: `status` moves back to `pending`, `retry_count` increments, `is_retryable`/`next_attempt_at` reset to null — not a separate write, so there is never a moment where a job is "about to retry" in some intermediate, inconsistent state.

**The RPC is not callable by `authenticated` or `anon` — and getting that right took two explicit `REVOKE` statements, not zero, discovered empirically, not assumed.** The initial draft relied on simply not writing a `GRANT` (matching how this schema's other four RPCs are *positively* granted to `authenticated`, so omitting a grant looked sufficient). Verifying directly against the real database during this phase found that was wrong twice over: PostgreSQL grants `EXECUTE` to `PUBLIC` on function creation by default, and — specific to this Supabase project — `authenticated`/`anon`/`service_role` each separately receive a direct `EXECUTE` grant on new functions in `public`, independent of `PUBLIC` (a project-level default-privilege rule, not anything any migration in this repository sets up). Revoking only from `PUBLIC` left the function fully callable by any signed-in end user. The migration now explicitly revokes from `PUBLIC`, `authenticated`, and `anon`; `service_role`'s own grant is left untouched and was confirmed, empirically, to still work after the revokes. This function is `security definer` and claims across every organization by design (a background worker has no per-tenant scope) — if it were reachable by `authenticated`, any signed-in user could claim and mutate another organization's `document_jobs` row directly, bypassing RLS entirely. Reachable only via the service-role client, the same trust boundary every other write path in this backend already uses (ADR 0005).

**No `document_job_events` change in Phase 1.** Claiming, renewing, and reclaiming are operational worker mechanics — exactly kind (2) in `docs/document-domain-architecture.md` §4.1's own taxonomy ("a worker claimed a job, a retry fired, a heartbeat, a claim timing out... not the domain lifecycle log"), not domain events. The one genuinely new domain fact Wave 3 will eventually need to represent — "an existing job began attempt N" — has no meaning yet with no worker to trigger it, and is deferred to the phase that actually builds retry-triggering logic.

## Consequences

- Every future write a worker makes while holding a claim should be conditioned on `lease_epoch` matching what it was given, or the fencing guarantee this ADR describes doesn't actually protect that write. This is a discipline requirement for whoever builds the phases that add real writes (persisting `azure_operation_id`, marking a result), not automatically enforced by the schema alone.
- `p_worker_id` must be minted per concurrently-held claim slot, not per process, by whichever phase builds the actual worker — documented in three places (the migration's column comment, the RPC's own comment, the repository wrapper's TSDoc) specifically so this isn't rediscovered as a bug later.
- There is no "release claim" mechanism yet — a job that finishes (successfully or not) still needs a later phase to clear `claimed_by`/`claimed_at`/`lease_expires_at` explicitly; until then, a completed job's claim fields simply age out via the same lease-expiry mechanism as a crashed worker's, which is harmless (nothing re-claims a `completed` job) but not yet a deliberate "done, release now" signal.
- `document_jobs_claimable_idx` only covers the common pending/processing case; the rarer retry-eligible branch has no dedicated index yet — deferred until real retry volume shows it's needed, consistent with this project's standing "don't guess at a shape before there's real data" discipline.
- This decision is specific to this project's current scale and stack. If a genuinely different requirement emerges later (cross-service fan-out, throughput a single Postgres table can't sustain), that would be a new decision, made explicitly when the requirement is real — not something this ADR tries to anticipate.
