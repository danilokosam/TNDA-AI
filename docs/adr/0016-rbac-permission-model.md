# Centralized RBAC: A Static Role/Permission Matrix in `packages/shared`

## Status

Accepted

## Context

Before this work, authorization in this codebase was not a system, it was two independent functions that happened to look alike. `billing.service.ts` had `assertCanManageBilling`, and `documents.service.ts` had `assertCanManageFile`, and each one, on its own, compared `role === "owner" || role === "admin"`. Neither function knew the other existed. There was no shared type, no shared constant, no single place that answered "what can an admin do" — just two copies of the same string comparison, kept in sync only by whoever happened to touch both files in the same sitting. The two roles that existed at the time, `admin` and `owner`, were in practice functionally identical everywhere this comparison appeared: nothing distinguished operational administration from organization ownership.

This was already showing strain. Document review needed a role that could edit and approve extracted fields without also being able to delete documents, manage organization settings, or touch billing — a capability set neither `member` nor `admin` fit. Adding that role the way authorization already worked would have meant a third bespoke `role === "..." || role === "..."` comparison, hand-written at whatever call site needed it, with no guarantee the next one would even remember the first two existed. Every future authorization rule was on track to be its own one-off, and there was no way to answer "does a reviewer have this permission" by reading one file — the answer would have been scattered across however many places had, by then, grown their own copy of the check.

Separately, `packages/shared` (see `0008-shared-packages-strategy.md`) had been deliberately scaffolded and left empty — `export {}` — specifically until "a concrete, specific piece of code actually needs to exist in both applications, unmodified." That decision was explicit that emptiness was not a gap to apologize for, just a placeholder waiting for a real case. A role/permission matrix is exactly that case: both the backend (which must enforce every rule) and the frontend (which must render UI consistent with what the backend will actually allow, e.g. disabling a billing button for non-owners) need the identical answer to "can this role do this thing," and any daylight between two independently maintained copies of that answer is a real bug waiting to happen — a button that looks enabled but 403s, or a button that's hidden when the backend would have allowed it.

## Decision

TNDA-AI now has four system roles — `member`, `reviewer`, `admin`, `owner` — and twelve permissions, defined once in `packages/shared/src/authorization.ts` and imported, unmodified, by both applications:

| Permission | member | reviewer | admin | owner |
|---|---|---|---|---|
| `documents.read` | ✓ | ✓ | ✓ | ✓ |
| `documents.upload` | ✓ | ✓ | ✓ | ✓ |
| `reports.read` | ✓ | ✓ | ✓ | ✓ |
| `documents.review` | | ✓ | ✓ | ✓ |
| `documents.edit` | | ✓ | ✓ | ✓ |
| `documents.approve` | | ✓ | ✓ | ✓ |
| `documents.delete` | | | ✓ | ✓ |
| `documents.export` | | | ✓ | ✓ |
| `organization.members.read` | | | ✓ | ✓ |
| `organization.members.manage` | | | ✓ | ✓ |
| `organization.settings.manage` | | | ✓ | ✓ |
| `billing.manage` | | | | ✓ |

Each role's permission set is additive over the one before it — `reviewer` is `member` plus review/edit/approve, `admin` is `reviewer` plus delete/export/organization management, `owner` is `admin` plus billing — which is what the matrix's staircase shape above shows directly, and what `ROLE_PERMISSIONS` in `authorization.ts` builds by literally spreading one role's array into the next's rather than repeating members. `can(role, permission)` is the one function that answers the question; it is pure, synchronous, and does no I/O, so there is no reason not to call it on every request that needs an answer.

This is exactly the concrete, specific need ADR 0008 was waiting for. `packages/shared` stops being an empty scaffold for this one purpose: the role/permission matrix is genuinely identical logic needed unmodified by both apps, not two independently-maintained schemas describing the same wire shape (the case ADR 0008 explicitly left alone). The backend consumes it through `apps/backend/src/utils/authorization.ts`'s `assertPermission(auth, permission)`, which throws `ForbiddenError` if `can()` says no — this is now the only call-site pattern for "does this role have this permission" anywhere in the backend; no service is expected to write `role === "..."` again. The frontend consumes the same `can()` directly to gate UI, for example disabling the billing-management button for anyone but an owner.

Ownership is kept deliberately separate from the role/permission matrix. `assertPermissionOrOwner(auth, permission, resource, isOwner)` is a second, generic primitive: it allows an action either because the role has the permission, or because `isOwner(resource, auth)` says the caller owns the specific resource in question, even without that permission. Today it has exactly one caller — document deletion — where an uploader can always delete their own document even as a plain `member` with no `documents.delete` permission, while an `admin` or `owner` can delete anyone's. This was deliberately not built as a per-resource ACL table (a `resource_id -> user_id -> permission` mapping) — that's a materially bigger, more general mechanism than this product currently has any second case for. Instead, `assertPermissionOrOwner` is shaped so that a future resource-level rule (say, a reviewer editing only the documents they were assigned) reuses the exact same primitive with a different `isOwner` predicate, rather than inventing new machinery each time ownership needs to interact with a permission check.

No ACL or policy engine was introduced, and that absence is an explicit non-goal, not an oversight. A dynamic, database-backed permission system, or a rules engine capable of per-organization custom roles, would be solving for a scale and flexibility this product doesn't need yet — every organization today uses the same four system roles with the same twelve permissions, and nothing in the product roadmap currently calls for per-org customization of who can do what. A static, code-level role→permission map is the smallest design that satisfies the two real requirements in front of it: a single centralized source of truth (not scattered comparisons), and the ability to change what a role can do by editing one table, without restructuring anything. Building further than that now would be speculative complexity with no consumer.

Extending this model later is meant to stay cheap. Adding a new permission means adding one string to the `Permission` union in `packages/shared/src/authorization.ts` and adding it to whichever roles' arrays should carry it — no route, service, or call-site structure changes, since every call site already asks `can(role, permission)` generically. Adding a new system role is only slightly more involved because roles are backed by a Postgres enum (`public.profile_role`): a new value needs its own migration (`ALTER TYPE ... ADD VALUE` must commit before the new value can be referenced in the same transaction, which is why `0019` and `0020` below are separate files, and why any future role addition should follow the same two-step shape), plus one new entry in `ROLE_PERMISSIONS`. Nothing else has to change, because nothing else anywhere in this codebase compares role strings directly anymore — every authorization decision routes through `can()`, `assertPermission`, or `assertPermissionOrOwner`.

Billing management (`billing.manage`) is owner-only, which is a deliberate behavior change from the pre-RBAC model, where `admin` and `owner` were functionally identical for this check. The reasoning is that `owner` represents organization ownership and financial responsibility — the entity actually accountable for the subscription and its cost — while `admin` represents operational administration (managing members, organization settings, document lifecycle) without carrying that financial authority. Conflating the two, as the old `role === "owner" || role === "admin"` check did, meant any operational admin could change the plan or open the billing portal; splitting them means only the role meant to hold financial responsibility can.

Finally, this work closes a real, independently-discovered gap in `profiles_update_self`, the RLS policy governing a user updating their own `profiles` row. Because RBAC reads `profiles.role` as its single source of truth for every authorization decision on both the backend and the frontend, any way a caller could set their own `role` outside that trusted path would undermine the whole model — and the old policy had exactly that hole. Its `with check` clause pinned `id` and `organization_id` to the caller's own identity, but never constrained `role` at all, so a user could, in principle, issue a direct PostgREST `PATCH` against their own profile row with `{"role": "owner"}` and have Postgres accept it — a straightforward self-service privilege escalation that had nothing to do with any application code, since the backend's own service-role client bypasses RLS and was never the vector. Migration `0018_profiles_role_immutable.sql` fixes this by adding `role = (select p.role from public.profiles p where p.id = auth.uid())` to the `with check` clause — a self-referential subquery that, within a single `UPDATE` statement, sees the pre-update snapshot of the row, so it compares the proposed new `role` against the row's own current stored value and rejects any attempt to change it. This makes `role` immutable through this specific policy, without a trigger. Migration `0019_profile_role_add_reviewer.sql` adds the `reviewer` enum value (additive only, in its own migration for the `ALTER TYPE` ordering reason above), and `0020_backfill_member_to_reviewer.sql` promotes every pre-existing `member`-role row to `reviewer`, since those accounts historically had review/edit/approve/export access under the old two-role model and would otherwise have silently lost it under the new, more restrictive `member` definition.

## Consequences

- Every new authorization rule, anywhere in the backend, is now expected to be expressed as a permission check against the shared matrix (`assertPermission`) or, for a resource-ownership exception, `assertPermissionOrOwner` — a direct `role === "..."` comparison anywhere in a service is a regression to the pattern this decision replaces, not a legitimate shortcut.
- Changing what a role can do is a one-line edit to `ROLE_PERMISSIONS` in `packages/shared/src/authorization.ts`, reviewable and testable in isolation, rather than a hunt across every file that independently encoded a role check.
- `packages/shared` is no longer an empty scaffold. ADR 0008's reasoning for leaving it empty — no concrete, unmodified-in-both-apps need yet — still correctly describes why it stayed empty until now; this decision is the record of the first real case arriving, not a reversal of that earlier one.
- Ownership-based exceptions stay deliberately narrow and explicit per call site (`assertPermissionOrOwner`'s `isOwner` predicate), rather than growing into an implicit, harder-to-audit general ACL layer — the tradeoff is that each new ownership rule needs its own predicate written at its own call site, which is intentional friction, not an oversight.
- Because no code compares role strings directly anymore, adding a role is now a two-step, mechanical process (an enum-value migration plus a `ROLE_PERMISSIONS` entry) instead of an audit of every file that might contain a stale comparison — but it does mean a reviewer needs to know to look at `authorization.ts` specifically, since the change is no longer visible by grepping for the new role name across service files.
- The `profiles_update_self` fix means `role` can now only ever change through the backend's service-role client, which bypasses RLS entirely — there is currently no application code path that updates a profile's `role` at all (it is set once at signup), so this fix closes a theoretical-but-real hole ahead of any feature that will eventually need a real role-change endpoint, rather than being discovered only once that endpoint existed and was already shipping.
- The `member` → `reviewer` backfill (migration `0020`) is a one-time, data-mutating migration, not a reversible schema change — any account that was `member` before this rollout is now `reviewer` permanently, by design. Signup (`auth.repository.ts`) always creates a brand-new organization with the signer-upper as its `owner`; no current code path creates a `member`- or `reviewer`-role profile row at all. The restricted `member` role only becomes reachable once a real invite/role-assignment endpoint is built.
