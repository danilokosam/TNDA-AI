# Wave 3 Phase 2: The Processing Worker — Byte Retrieval, Fencing Discipline, Retry Policy, and the `GET /jobs/:id` Behavior Change

## Status

Accepted

## Context

Phase 1 (ADR 0012) built the claiming/leasing/fencing primitive — a Postgres RPC and the schema behind it — but explicitly built no consumer of it. Azure submission and status polling still ran exactly as before: synchronously, inside the HTTP request, with no worker process anywhere. Phase 2's job was to actually move that work into a background worker, using Phase 1's primitive to make it safe under concurrency and crashes.

A second full architecture design review (background-processing-worker specific: byte retrieval without the original request's in-memory bytes, worker concurrency/defaults, Azure 429 handling, fencing discipline for every worker-originated write, claim release on terminal transitions, the one new lifecycle event this phase needs, and the `GET /jobs/:id` behavior change) was done before writing any code, and approved with twelve explicit decisions locked in advance. A required pre-implementation consistency review then checked three things specifically against Phase 1's actual RPC and ADR 0012, before any implementation began:

1. **Exact `retry_count` semantics** — attempts vs. retries, and whether `maxRetries=3` produces exactly the intended number of submission attempts.
2. **Lease-loss behavior** — every point where a worker can lose its epoch, and whether a stale worker can still perform a state/event write afterward.
3. **Terminal/retryable state transitions** — whether an exhausted retryable failure reliably becomes terminal and unclaimable.

All three checked out consistent with Phase 1 as designed; no schema or RPC change was needed. The review did surface one real design gap, described below (Decision, fencing discipline), closed before implementation began.

## Decision

**Byte retrieval: re-download from Storage, not `urlSource`.** The worker runs in a separate process from the original upload request, so it has no in-memory bytes. `submitClaimedJobForProcessing` downloads the original file from Storage (`storage.service.ts#downloadDocumentFile`) and re-runs `inspectDocumentFile` on the downloaded bytes — reusing the same magic-byte MIME detection every other submission path already trusts, rather than trusting Storage's stored content-type metadata or switching to Azure's `urlSource` submission style (which would need a publicly-reachable or signed URL Azure can fetch, a materially different trust/network model this phase didn't need to take on).

**A claimed job with no `storage_path` is terminal, not retryable.** If the file was never persisted (a non-fatal Storage failure at upload time — an existing, deliberate behavior, ADR/decision predates this phase) or was independently removed while the job sat in queue, no future attempt could ever succeed either — there is nothing to retry towards. `submitClaimedJobForProcessing` marks this `status: "failed"`, `is_retryable: false`, with a dedicated error message, and never attempts a download.

**Every worker-originated database write is fenced by `lease_epoch`.** `documents.repository.ts#updateDocumentJobIfEpochMatches(id, expectedEpoch, patch)` is the one write primitive both `submitClaimedJobForProcessing` and `checkClaimedJobProgress` use for every state transition — `UPDATE ... WHERE id = $1 AND lease_epoch = $2`, returning `null` (not an error) on a zero-row match. A `null` return is a hard contract: the caller must stop touching that job entirely for the rest of that attempt, never retry the write or fall through to any further mutation. This is Phase 1's fencing primitive (ADR 0012) getting its first real consumer, exactly as that ADR's own "Consequences" section anticipated.

**Terminal writes release the claim; `lease_epoch` itself is never reset.** Every write that lands a job in a terminal state, or a retryable failure with a scheduled `next_attempt_at`, clears `claimed_by`/`claimed_at`/`lease_expires_at` in the same statement — Phase 1 deliberately left this undone (its own "Consequences" section named it as future work). `lease_epoch` stays untouched on release; it only ever increments on a *fresh* claim (Phase 1's RPC behavior, unchanged), so it continues to serve as a monotonic fencing/history token across a job's entire retry lifetime, not just within one attempt.

**The claim loop's renewal call is routed through the exact same adoption path as a fresh claim — the one real gap the pre-implementation consistency review found.** `claim_or_renew_document_job` is a single RPC; a "renewal" call can fall through to claiming a genuinely *different* job if this slot's own lease was lost to a reclaim elsewhere in between. The original design implicitly assumed a renewal call always either confirms the same job or returns nothing — tracing the RPC's actual behavior showed a third case: it can silently hand back an unrelated job. `src/worker/claim-loop.ts#runClaimSlot` treats every response from `deps.claim(...)` uniformly: if a "renewal" comes back with a different job id than the one currently held, that's logged as lost ownership and the *new* job is adopted through the identical `pending → submit` / `processing → poll` branch a fresh claim would use — never assumed to already be in whatever state the old job was in.

**Azure `429` is retryable, and `Retry-After` is honored when Azure sends one.** This resolves Wave 2's own previously-recorded open item (ADR 0011, decision 61 in the root `PROGRESS.md`): a 429 that survives `beginDocumentAnalysis`'s existing internal retry-with-backoff (`fetchWithRetry`, unchanged by this phase) represents sustained rate-limiting, not a rejected request — the canonical retryable case, not Azure-said-no. `isRetryableSubmissionFailure` now carves 429 out of the `[400,500)` terminal range explicitly. The 429 response's `Retry-After` header (when present) is captured into `AzureServiceError.details.retryAfterSeconds` — the smallest additive change to the existing error shape, not a new error type — and `computeNextAttemptDelayMs` uses it verbatim (converted to ms, capped at the same maximum as the computed formula) instead of the exponential-backoff calculation whenever it's available.

**Retry backoff is exponential with jitter, computed from the pre-failure `retry_count`.** Base delay 30s, ×2 per retry, jitter up to +10s, capped at 10 minutes. Exhaustion (`isRetryExhausted`) compares that same pre-failure `retry_count` against `maxRetries` — matching exactly what Phase 1's RPC checks at the next claim attempt (`retry_count < p_max_retries`), which is why the consistency review's first question mattered: getting this comparison one attempt off in either direction would mean the worker and the RPC disagree about whether a job is still eligible.

**`processing_retried` fires exactly once per retry attempt — on a fresh claim with `retry_count > 0`, never on a renewal.** This is Wave 2's own deferred "no meaning yet with no worker to trigger it" event (ADR 0011), added via migration `0017` (a pure `ALTER TYPE ... ADD VALUE`, the tenth value on `document_job_event_type`). Claiming, renewing, and lease expiry stay out of the domain event log entirely — Phase 1's own "operational mechanics, not domain events" boundary (ADR 0012) is unchanged by this phase; `processing_retried` is a genuinely new domain fact ("an existing job began attempt N"), not an operational one. `processing_started`'s existing metadata gained `retryNumber` (the exact `retry_count` value, named for what it actually is rather than an ambiguous "attempt number"). Retry exhaustion stays a `processing_failed` event with `metadata.exhausted: true`, not a new event type — it's the same domain fact ("processing failed"), the exhaustion flag is just additional detail about why no further retry will happen.

**`GET /jobs/:id` is now a pure database read.** `documents.service.ts#getJobStatus` no longer polls Azure, writes any state, or records any event — it is `return getDocumentJobForOrganization(jobId, organizationId);` and nothing else. The worker (`checkClaimedJobProgress`, called from the worker's own claim loop) is the sole remaining path that ever polls Azure or writes a `processing`/`completed`/`failed` transition. This is the one change in this phase that alters existing HTTP behavior — every other change is either new code (the worker) or code newly *not* called (the old synchronous submission path).

**`POST /documents` no longer submits to Azure synchronously.** `processSingleDocument`/`processZipBatch` persist the job as `pending` and return immediately — the worker claims and submits it asynchronously. The response contract is unchanged: `POST /documents` still returns `202`, `BatchFileResult.status` still reports `"processing"` for an accepted file (meaning "accepted into the pipeline," not the job's literal DB status, which is `pending` until the worker picks it up) — a deliberate, documented distinction, not an inconsistency, and specifically chosen to avoid any response-schema change. The frontend was verified, by a fresh code trace (not assumed), to already treat `pending` identically to `processing` everywhere it branches on job status — polling continuation, the upload-queue "still working" state, and every status badge map are already exhaustively typed over the full status union, so nothing needed to change there.

**Worker defaults**: `WORKER_CONCURRENCY=5`, `WORKER_LEASE_SECONDS=180`, `WORKER_POLL_INTERVAL_MS=5000`, `WORKER_MAX_RETRIES=3` (all Zod-validated env vars with these defaults). Lease renewal fires at 50% of the lease duration (computed in `src/worker/index.ts`, not its own env var — a ratio of an already-configurable value, not an independent tuning knob). `WORKER_CONCURRENCY` slots run inside one process, each with its own claim-slot id (`${baseWorkerId}:${index}`) — Phase 1's "one id per concurrently-held job, not per process" rule (ADR 0012) applied directly.

**Graceful shutdown**: `SIGTERM`/`SIGINT` stop the worker from claiming *new* work; a job already held is always finished (submitted/polled through to a terminal state) before the process exits. Verified in `claim-loop.test.ts` via a stateful fake `shouldContinue` closure whose value flips mid-run, not merely asserted.

**Not done in this phase, deliberately**: no Dockerfile change (no new image, no new container topology decision needed yet — the worker runs via `bun run worker:start`/`worker:dev`, added to `package.json` alongside the existing `dev`/`start` scripts); the worker is not wired into the Turbo dev fan-out (no concrete existing constraint required it, and running it separately during development is the more natural default until there's a reason to bundle it); no live-Postgres or live-Azure test runs in CI (unchanged from Phase 1's own stance — real-database verification stays manual/dev-DB, not permanent CI).

## A design bug found and fixed by unit testing during this phase's own implementation, not anticipated in the design review

The claim loop's `shouldContinue()` check is intentionally consulted only while the slot is idle — checking it while a job is held would mean either abandoning an in-flight job on shutdown (violating the graceful-shutdown requirement above) or inventing a second, weaker shutdown semantic just for that branch. Implementing this against the test suite written for it surfaced a genuine defect: if a held job's `poll` never returns a terminal status (modeled directly in a test, not a hypothetical), the loop never returns to idle, `shouldContinue()` is never re-checked, and the loop runs forever — an actual out-of-memory crash was reproduced running the test suite before this was caught. This is not a flaw in the idle-only-check design itself (a real Azure operation does eventually resolve, and letting a held job run to completion regardless of a shutdown signal is the correct, intended behavior) — it was a gap in the test fixture's own mock, which needed to eventually terminate for the test to be a meaningful, terminating test at all. Fixed by making the test's mocked `poll` eventually return a terminal status, not by weakening the loop's shutdown semantics. A second, unrelated bug was found in the same pass: the graceful-shutdown test's own fake `shouldContinue` closure mutated its state *before* returning on its first call, meaning it could never actually return `true` — fixed by capturing the return value before the mutation, matching the closure's own stated intent ("signal shutdown right after the first claim").

## Two real defects found by live verification, and fixed

Everything above was verified by unit tests against injected fakes/mocks before this point — genuinely running the worker as a live process against the real development database and live Azure (the one gap the "Consequences" section below originally named) surfaced two real defects that no amount of mocked testing could have caught, since both depend on exact real-infrastructure response shapes.

**1. The worker process crashed entirely on a single unexpected polling exception.** With a live worker running against the real dev database, it claimed a pre-existing leftover row (unrelated fixture data from an earlier debugging session) whose `azure_operation_id` no longer resolved to anything real. `getAnalysisOperationStatus` correctly threw on the resulting 404 — but `checkClaimedJobProgress` had no try/catch around that call (it mirrored `getJobStatus`'s old shape, which was only safe there because Elysia's per-request error middleware caught it; a long-running worker process has no equivalent safety net). The exception propagated out of `runClaimSlot`, into `worker/index.ts`'s unguarded `Promise.all(slots)`, and killed the entire process — taking every other concurrently-held job's in-flight work down with it. **Fixed**: `runClaimSlot` now wraps its per-iteration claim/submit/poll work in a try/catch — an unexpected exception is logged with full context (slot id, job id if known, stack trace) and the slot's in-memory job tracking is cleared, with no epoch-gated write attempted from the catch block; the claimed row simply keeps whatever claim it already has until Phase 1's existing lease-expiry mechanism makes it reclaimable again. `worker/index.ts` also switched from `Promise.all` to a new `runSlots` helper (`Promise.allSettled` plus rejection logging), so one slot's own unanticipated failure can never cascade into killing healthy sibling slots either. Re-verified live: a real bad job (a temporary fixture, deleted immediately after) is now caught and logged instead of crashing the process, on both a normal run and while a `SIGTERM` was in flight.

**2. Phase 1's `claimOrRenewDocumentJob` (already committed, `275d578`) didn't actually return `null` when nothing was available to claim.** With multiple concurrent slots and only one claimable row, the losing slots received a JS object with every field set to `null` (`{ id: null, status: null, ... }`) instead of a real `null` — confirmed empirically: PostgREST serializes a SQL NULL of the RPC's composite return type (`document_jobs`) this way, not as a literal JSON `null`. `return data ?? null;` let this truthy object-of-nulls straight through. The claim loop then mistook it for a genuinely held job: `adopt()` saw `status: null` (not `"pending"`, so no submit), the poll branch saw `status: null` (not `"processing"`, so no poll either) — the slot just believed it held a phantom job forever, and since `shouldContinue()` is only ever re-checked while idle, an affected slot never checked it again, **hanging graceful shutdown indefinitely** (confirmed: `SIGTERM` was received and logged, but the process was still alive 8+ seconds later with no "all slots drained" message, requiring `SIGKILL`). **Fixed** in `documents.repository.ts#claimOrRenewDocumentJob`: `return data?.id ? data : null;` — `id` is the primary key, never null on a real claimed row, so it's the reliable discriminator PostgREST's actual response shape needs. This is a fix to already-shipped Phase 1 code, not a Phase 2 architectural change; Phase 1's own unit test for this case previously mocked a bare `data: null`, which could never have caught the real shape — it now reproduces the actual object-of-nulls response.

**Re-verified live, end to end, after both fixes**: a worker with 5 concurrent slots against a database holding exactly one claimable job correctly claims it in one slot and receives real `null` (no phantom-job log lines) in the other four; the worker stays alive through multiple idle cycles; `SIGTERM` now produces a clean `"all slots drained, exiting"` and the process exits on its own, no `SIGKILL` needed — both with a healthy job in flight and while a slot was actively hitting a real, repeated Azure error. The full acceptance path — upload → `pending` → claim → Storage download → real Azure submission → `azure_operation_id` persisted → polling → `completed` with a real extracted result → claim released → `GET /jobs/:id` still a pure read throughout — passed against the real development Supabase project and the real Azure Document Intelligence resource.

## Consequences

- `BatchFileResult`'s `"failed"` status value is now unreachable through `processZipBatch`'s own code path (submission failures used to produce it; submission no longer happens inline) but was deliberately left in the type rather than narrowed, since narrowing a response-contract type counts as a response-schema change this phase was explicitly scoped to avoid.
- The old, unconditioned `submitForAnalysis` function is gone entirely — deleted, not deprecated-in-place — since nothing calls it anymore and this project's own convention is to delete confirmed-dead code rather than leave it as a stub.
- Whoever operates this in a real deployment needs to actually run `bun run worker:start` (or `worker:dev`) as a separate long-lived process alongside the API server — nothing starts it automatically, and no process-supervision (systemd unit, container entrypoint, PM2, etc.) was decided or built this phase, consistent with the "no Dockerfile/deployment-topology change this phase" decision above.
- `checkClaimedJobProgress`'s poll cadence is fixed at `WORKER_POLL_INTERVAL_MS` regardless of how long a specific Azure operation is taking — no adaptive backoff on the poll interval itself (as opposed to the submission-retry backoff, which is adaptive). Acceptable at today's scale; revisit if poll volume ever becomes a real cost or rate-limit concern.
